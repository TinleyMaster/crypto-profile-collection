## 1. 背景与触发

### 1.1 三个缺口的同一根因

| 缺口 | 位置 | 本工单的处理 |
|---|---|---|
| **B8**：深度维度全缺、价差无数据源 | 设计文档 §7 / §12.1-B8 | **深度补齐**（本工单）；**价差仍无解**（接口无 best bid/ask 字段，仅 ±range 汇总 ⇒ 明确标注为遗留） |
| **§9.10**：「流动性门槛正确性不靠收益证明，真正需要盘口深度数据，我们没有」 | SCAN-LIQ-FILTER-001 | **现在有了**：180 天 @4h 深度历史，标定路径打开 |
| **§12.1-A 系**：回测假设「成交即拿到价格」，无滑点 | 设计文档 | 深度历史 ⇒ 可给回测补**滑点项**（阶段 B 选题） |

### 1.2 为什么深度是「执行先验」而非 alpha 主张（身份必须钉死）

- 成交额（vol7d）= **过去 7 天累计流量**，不含当前挂单；
- 深度（bids/asks_usd）= **当前盘口存量**，直接决定 X 单子能否被吃掉；
- 对「X 单子吃不吃得下」这个问题，深度是**直接度量**，成交额只是
  依赖「流量 ≈ k × 存量」假设的**间接代理**；
- ⇒ 用深度做**执行过滤**（这单能不能下）是**先验论证即可**，不需 holdout；
  ⚠️ 但若用深度**选币**（把某些币从池里永久剔除）= alpha 主张，仍需验证——
  本工单**不做选币**，只做**单信号级的执行经济性标定**。

### 1.3 与现役门槛（SCAN-LIQ-FILTER-001）的关系

现役门槛：`vol7d ≥ X/ρ`（X=300 U、ρ=1bp ⇒ 300 万），7 天常态日均成交额。
本工单**第一阶段不动它**，只产出标定结论：
1. `vol7d` 与 `±1% 深度` 的截面关系（k 系数是否稳定 ⇒ 成交额是不是合格的代理）；
2. 单笔 X=300 U 在池内各币的**真实参与度**（占 ±1% 深度的 bp）；
3. 「成交额说留、深度说剔」与反向的**分歧集**（代理误判样本）。

⇒ 阶段 B 才据标定结论决定是否把门槛真值化（另起授权）。

|---|---|---|

### 2.3 第三轮 probe 结果（2026-09-30 实测）

1. **`start_time`/`end_time` 生效**：窗口 2026-08-01~08-05 ⇒ 精确返回 08-01 00:00 → 08-04 20:00（24 点）。
   ⚠️ 与 `liquidation/history`「时间参数被忽略」的行为**不同** ⇒ 本端点可精确补窗口。
2. **range 多档累积曲线**（BTC 同一时点，买盘/卖盘 USD）：
   ±0.25% = 1.32亿/0.61亿 → ±1% = 3.37亿/1.74亿 → ±2% = 6.00亿/3.96亿 → ±5% = 8.60亿/5.97亿 → ±10% = 9.94亿/7.75亿。
   **环带边际深度**：0.25→0.5% 区间 3.34 亿/%，递减至 5→10% 区间 0.27 亿/% ⇒ 深度集中于近端（可作滑点估算素材）。
3. **聚合端 `exchange_list='ALL'` 可用**：BTC ±1% 聚合买盘 5.94 亿（vs 单所 Binance 3.37 亿）。
4. **`limit` 真实上限**：500/1000/2000 分别回 500/1000/**1080** ⇒ 被 180 天上限截断；回填用 `limit=2000` 单请求全覆盖。

## 3. 全池真值对照（阶段 A 核心证据，2026-09-30 实测，373/373 覆盖）

> 口径：深度 = 近 7 天每桶 `min(bids_usd, asks_usd)` 的中位数（取双侧较弱一侧，双向都要能进出）；
> vol7d = 与线上 `_load_vol7d_avg` 同口径的 7 天常态日均成交额。n=373（池内 7 天有量全量）。

### 3.1 分布对照

| 分位 | ±1% 深度（中位） | vol7d（日均成交额） |
|---|---|---|
| p10 | 2.2 万 | 68.8 万 |
| p25 | 3.6 万 | 195.5 万 |
| p50 | **6.0 万** | 626.1 万 |
| p75 | 13.0 万 | 2,652 万 |
| p90 | 52.3 万 | 1.03 亿 |
| p100 | 1.65 亿 | 90.71 亿 |

### 3.2 门槛对撞（X=300 U、ρ=1bp ⇒ 门槛同为 300 万）

| 门槛口径 | 保留 | 剔除 |
|---|---|---|
| vol7d（现役代理） | 252 / 373 | 121 |
| **深度（真值）** | **9 / 373** | **364（97.6%）** |
| 两者一致保留 | 9 | — |

- ⚠️ **成交额留·深度剔 = 243 个**（代理高估可执行性）；深度留·成交额剔 = **0**。
- 最典型样本：**QNTUSDT vol7d 9.96 亿（近 10 亿日成交），±1% 深度仅 18.1 万**——
  「高成交、低深度」币是成交额口径**结构性看不见**的（成交集中在做市商高频对倒，盘口挂单薄）。

### 3.3 真实参与度（300 U 单笔占 ±1% 深度）

| 分位 | 参与度 |
|---|---|
| p10 | 5.74 bp |
| p50 | **50.12 bp** |
| p90 | 135.18 bp |
| p100 | 334.07 bp |

⇒ 现役 ρ=1bp 是**机构对日成交额**的参与度标准，套到**盘口深度**口径上严约 50 倍（p50）。
**两个口径的 X/ρ 不可直接互套。**

### 3.4 截面关系（成交额是不是合格的代理）

- k = depth/vol7d：p10 = 26bp / p50 = **107bp** / p90 = 563bp（跨 21 倍）；
- 秩相关 = **0.668**（n=373）。
- ⇒ 成交额与深度仅**中度相关且比例极不稳定**：用成交额估深度，误差是**数量级**的 ⇒
  **成交额不是合格的深度代理**（这是本工单存在的根本理由）。

### 3.5 判读（三条，按身份分开）

1. **深度数据的正确用途是横截面识别「高成交低深度」可疑币**（QNT 类）+ 给成交额代理标定误差范围，
   **不是**换一个更狠的门槛——「深度门槛剔 97.6%」是因为 ρ=1bp 对深度口径过严（§3.3），
   且静态深度是瞬时存量（做市商毫秒级补单），按线性模型 300 U 在中位币的滑点仅 ~0.25bp。
2. **对 300 U 级别的小单笔，常态盘口下执行冲击很小**；真正的执行风险在**异动瞬间的深度崩塌**
   （撤单），4h 桶只能部分反映（含异动时刻的桶深度会被拉低）⇒ 阶段 D 的实时接入需用**当期**快照补。
3. **选币红线不变**：本数据不得用于「把币永久剔出池子」（§9.8 已否决同类 alpha 路线）；
   它服务的是**单信号级**的执行经济性标注与成交额代理的校准。

## 4. 设计方案

### 4.1 表结构（`fix_081_orderbook_depth_history.sql`）

参照 `biz.liquidation_history`（fix_069）的既有模式：

```sql
CREATE TABLE IF NOT EXISTS biz.orderbook_depth_history (
    symbol          TEXT        NOT NULL,   -- 本库合约码（BTCUSDT），与 asset_klines / liquidation_history 同口径
    interval        TEXT        NOT NULL,   -- 4h（本期只采 4h；粒度地板）
    range_pct       NUMERIC(5,2) NOT NULL,  -- 深度档 1.00 = ±1%；进 PK，禁混桶
    ts              TIMESTAMPTZ NOT NULL,   -- 区间起点（UTC，interval 对齐）
    bids_usd        NUMERIC(24,2),          -- ±range 内累计买单挂单 USD
    asks_usd        NUMERIC(24,2),
    bids_quantity   NUMERIC(28,6),
    asks_quantity   NUMERIC(28,6),
    fetched_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    PRIMARY KEY (symbol, interval, range_pct, ts)
);

COMMENT ON TABLE biz.orderbook_depth_history IS
  'CoinGlass 单所（Binance）盘口深度历史：±range_pct 价格区间内累计挂单 USD。'
  '⚠️ 仅供标定/回测消费，禁止接入 scan_daemon 实时判定；'
  '⚠️ 无 best bid/ask 字段 ⇒ 价差维度不可由本表得出；'
  '⚠️ 4h 桶粒度 ⇒ 不可用于 5m/1h 级实时执行判断。';
```

- **单所 Binance 口径**：与 `asset_klines` / `asset_derivatives` 同所，免跨所混算；
  聚合端（`aggregated-*`）本期**不采**（无消费点，避免写而不读）。
- `range_pct` 进 PK：多档深度共存、禁混桶（同 liquidation 的 `interval`/`exchange_scope` 教训）。
- 不纳入 `prune_scan_data`（回测资产）。

### 4.2 回填脚本 `scripts/bin/phase_backfill_ob_depth.py`

参照 `phase_backfill_liq_history.py` 的成熟模式：

| CLI | 语义 |
|---|---|
| `--probe` | 套餐边界复验（不写库）：合约码 ✓ / 基码 ✗ / 1h 403 / range 多档 / aggregated 基码 |
| `--dry-run` | 只算请求数与预计耗时 |
| `--symbols BTCUSDT,...` | 指定币；默认全池 = `biz.asset_klines` 近 3 天有 1h 条的 symbol |
| `--days 180` | 回填窗口（@4h 单请求即全覆盖，limit=4500） |
| `--range 1` | 深度档（默认 1 = ±1%；多档 = 多轮请求） |
| `--resume` | 游标续跑（复用 `biz.liquidation_backfill_cursor`？**否**——语义不同，单独游标表或进程内游标） |

- 请求数 = 币数 × 档数（294 × 1 = 294 次 ≈ **12 分钟** @2.5s gap）；
- 错峰：不与 scheduler 的三条 coinglass 日频作业（01:10/02:10/03:10）重叠；手动回填白天跑即可（daemon coin-list 仅 0.2 req/min）。

### 4.3 标定脚本 `workbench/calib_ob_depth_vs_vol.py`（只读）

产出三张表（均**描述性**，不进判定）：
1. **分布对照**：深度 vs vol7d 的 p10/p50/p90；
2. **截面关系**：`depth / vol7d` 的分布（k 系数稳定度）+ 秩相关；
3. **分歧集**：四象限（成交额留/剔 × 深度留/剔）+ 单笔 X=300 U 的真实参与度分布。

## 6. 风险与红线

| 项 | 说明 |
|---|---|
| **不接实时** | 阶段 A 只落库 + 只读标定；scan_daemon 零改动。实时接入是阶段 D，另授权 + 影子期 |
| **4h 粒度错配** | 信号是 1h 级 ⇒ 深度只能回答「这个币**常态**够不够深」，不能回答「**此刻**够不够」。阶段 D 的实时接入必须接受这个上限，或配合当期 Binance depth 快照补齐 |
| **无价差字段** | B8 的「价差过滤」**本工单不解**（接口无 best bid/ask）；只解「深度过滤」 |
| **额度共享** | 与 daemon coin-list / 三条日频 coinglass 作业共享 30 req/min ⇒ 回填 2.5s gap 错峰 |
| **深度≠可吃量** | 静态盘口是上界（异动瞬间撤单 ⇒ 真实可吃 ≤ 静态）⇒ 标定结论只能当**必要条件**读 |
| **缺失≠0** | 接口缺数据 ⇒ NULL 入库，禁补 0（既有纪律） |
| **选币红线** | 深度数据**不得**用于「把某些币从池里永久剔除」（那是 alpha 主张，§9.8 已否决同类路线） |

## 8. 阶段 C：回测补滑点（2026-09-30，PO 授权「按你说的办」后执行）

**触发**：§3 全池对照证明「成交额 ≠ 深度」，而 SCAN-LIQ-FILTER-001 §9.10 的结论是
「滑点验证需要盘口深度数据，我们没有 ⇒ 验证上限是机制自洽」。阶段 A 落库 30.96 万行
@4h 深度后，这个「没有」已解除 ⇒ 用**历史深度**给回测信号补滑点项，量化
「小币正收益在真实成交下还剩多少」。

### 8.1 模型（必须随表声明，是下界偏乐观的估计）

- **线性深度模型**：±1% 单侧累计挂单 D（USD），吃 X 美元单的价格冲击
  `impact_bp ≈ 100 × X / D`（深度区间内均匀假设 ⇒ 消耗占比 f=X/D，位移 = f×1%）；
- 往返 = 买入吃 asks + 卖出吃 bids，双边相加；
- **无前视**：每笔信号取 `ts ≤ entry 时刻` 的最近 4h 快照（`bisect` 定位）；
- 覆盖外的信号（缺快照）单独计数不混入；
- **局限**：①均匀假设偏乐观（真实盘口近密远疏）；②静态快照是 MM 毫秒补单后的
  瞬时存量，实际可吃 ≤ 静态；③单边 X>D 时模型失效（unfillable，剔除计数）。

**实现**：`backtest_liq_layer.py` 扩展 `--slip`（复用同源触发逻辑，不新开脚本）；
信号记录存 `d_ask/d_bid`（±1% 单侧深度），滑点按 X 现算 ⇒ 同一批信号可出 X 敏感度。

## §10 阶段 D：实时深度采集（2026-09-30 晚，PO 拍板方案 A「一次上」后交付）

**身份**：纯影子。对**本轮被流动性闸门评估过的触发币**（含 low 被剔组，为攒
「low vs pass」异动时刻深度对照）在信号时刻拉 Binance fapi `/fapi/v1/depth`，
聚合落 `biz.scan_depth_log`。**不拦截、不降权、零影响信号主链路**。

**实现**（全部在 `scan_daemon.py`，复用 `_http_get` 全局限频/429/418 退避）：
- 采集位置：信号/过滤日志 `commit()` **之后** ⇒ 采集失败绝不拖垮扫描轮；
- 对象按轮去重（set），逐币一次调用（`limit=500`，weight=10，全局限速兜底）；
- `_aggregate_depth` 纯函数：mid / spread_bp / d_ask±1% / d_bid±1% /
  **cov_ask_pct / cov_bid_pct**（实际覆盖半径）/ levels；
- 单币失败记 `status='error'` 行、空响应记 `empty`（失败也是数据）；落库失败 rollback 放弃本轮；
- 建表挂惰性 `_ensure_liq_filter_table`（幂等 DDL + ALTER 补列），随首轮回自愈。

**⚠️ REST 覆盖半径坑（runtime 实测发现，比代码本身更值钱）**：
REST depth 单次最多 1000 档，**大币 ±1% 远超档位可达范围**——BTC 500 档仅覆盖 ±0.07%，
若直接拿 d 值当"±1% 深度"，会把「没采到」当「深度薄」。故 cov 列强制同落，
分析侧规则：**cov < 1% 时 d 只代表覆盖带内累计；cov ≥ 1% 才是真 ±1% 全量**。
小币实测 cov 远超 1%（AVNT ±119%/±27.7%、MAGMA ±17%），其 ±1% 值与 CG 快照
（7.05 万 / 3.57 万）同量级交叉吻合 ⇒ 口径互验通过。
**附带收获**：best bid/ask 随 depth 免费拿到 ⇒ spread_bp 落库，**B8 价差半边在实时侧闭环**
（CG 历史快照无 best bid/ask 的缺口只限历史，实时不再缺）。

**新增表**：`biz.scan_depth_log`（captured_at / symbol / trigger_count / pool /
mid_price / spread_bp / d_ask_1pct / d_bid_1pct / cov_ask_pct / cov_bid_pct / levels / status / err）
