## 1. 背景与问题

### 1.1 现状

盘面异动扫描系统每天发出 0~176 条实时告警（`biz.scan_signal.alerted_at IS NOT NULL`），
但**发出去之后没有任何自动化的后验统计**：

| 已有 | 缺失 |
|------|------|
| 实时告警邮件（`scan_daemon._render_alert_email`） | 告警发出后 T+1h/4h/12h/24h 的实际涨跌 |
| 信号明细落库（`biz.scan_signal` 含 `vol_ratio`/`price_chg_pct`/`oi_chg_pct`/`timeframe`/`scenario`/`context_tags`） | 按日聚合的胜率、赔率、盈亏比 |
| 邮件里「历史同场景」后验（`_scenario_priors`，12h 口径、按 `(p_dir, oi_dir)` 分组） | 行情环境（振幅/波动占比）与信号表现的**交叉表** |
| 场景回测（`backtest_scan_scenarios.py`，离线、按场景聚合、含阈值 sweep） | 每日自动跑、并对外报警的**失配探测器** |

**后果**：2026-09-22（上海日）发出 73 条告警，T+1h 胜率仅 35.6%、均净收益 −0.21%、PF 0.84（**负期望**），
直到次日人工复盘才被发现。**整整一天的负期望无人拦截。**

### 1.2 核心问题

- 今天这批告警，**期望是正还是负**？——发信时不知道，次日也不知道（无自动统计）。
- 阈值（量比 2.0、涨幅 2.0/3.0%、OI 分档）在当前行情下**是不是太松/太紧**？——无量化判据。
- 告警数从 36 条（09-21）暴增到 176 条（09-23），是**行情给了更多机会**，还是**门槛被变相放松**？——无法区分。
- 中长窗口（T+24h）胜率 48.6% 看着接近一半，但**多少来自 BTC beta、多少来自信号 alpha**？——未拆分。
  （期间 BTC 同方向 T+24h 胜率在单边上行日 09-18/09-21 是 100%、在单边下行日 09-23 是 0%
  ⇒ 中长窗口的「正」几乎不构成信号质量证据。）

### 1.3 目标

建立「**告警 → 多窗口结局 → 每日胜率/赔率 → 阈值-行情失配判定**」的自动闭环：

```
scan_daemon 告警(alerted_at)
      │
      ▼
① 结局结算：T+1h/4h/12h/24h 方向对齐净收益 + BTC beta 对照
      │
      ▼
② 日报聚合：当日胜率/赔率/PF/盈亏平衡胜率 + 行情环境指标
      │
      ▼
③ 失配判定：告警数异动 × 胜率跌破盈亏平衡线 × 边缘桶占比
      │
      ▼
④ 每日邮件（当日值 + 近 3 日滚动 + 与阈值常量的对照）
```

**一句话**：让「阈值是否匹配当前行情」从**事后人工复盘**变成**每日自动报警的数字**。

**规律**

- **当日整体值是多策略混合，必须先分层再读**：09-23 的 T+1h 59.1% / +0.08% 是
  `main/S1` 64 条（**35.9% / PF 0.85**，多头在单边下跌日全亏）与
  `accumulation/BRK` 112 条（**72.3% / PF 1.39**，做空在同一日全赚）的加权平均；
  两个池期望一正一负，整体值落在 +0.08% 只是**恰好在噪声量级上相互抵消**，不代表系统健康
  ⇒ 04-06 方案新增「分层（池口径）」小节，且**邮件主题一律用 3 日滚动值**；
- **T+1h 的正负本身不可读**：5 个有样本交易日中 3 天负（09-17 −0.34% / 09-21 −0.07% / 09-22 −0.21%）、
  2 天正（09-18 +1.38% / 09-23 +0.08%），幅度全在 ±1.4% 内，与 ±0.1% 双边费同量级；
- **regime 的效应体现在 T+4h 及更长窗口**，而非 T+1h：09-18 T+4h→T+24h 一路走高（+1.99%→+18.42%），
  09-21 T+4h 起转正（+1.56%），09-22 的 T+4h 仍为负（−0.33%），09-23 越拉越长越负（−0.05%→−5.75%）；
- **单边下跌日告警量最高（176 条）**：多空两侧策略在同一根大阴线里同时触发（main 做多 + BRK 做空），
  告警量异动并不等于「阈值被放宽」，也可能是**行情把两边都打亮**；
- **n≤10 的窗口不可读**：09-22 的 T+24h 只因新增 1 条样本（+63% 的极端值）就从 −4.03% 翻到 +2.71%
  —— 这正是「单日胜率标准误 ±6~12pt」的直观后果，也是判定只用近 3 日滚动的原因；
- 09-19 / 09-20 告警 0 条（daemon 无输出），其 regime 行仅作环境记录，不参与统计，
  **且不计入「前 N 个有告警日均值」**（否则会把均值压低、把异动倍数放大）。

且**收紧阈值也裁不到它们**（收紧只会把样本从低档挪走），故一律不进「该收紧哪个阈值」名单。


### 2.4 ⚠️ 性能约束（必须遵守）

`biz.asset_klines` 虽有 `(symbol, interval, open_time DESC)` 索引，但**整表拉取会因跨区链路超时**
（实测 240s+ 未返回）。因此：

- 取价必须**在 SQL 侧用 `LATERAL` / 相关子查询算好**，只回传结果行（参照 `_scenario_priors` L1352-1374 的写法）；
- **禁止**把 K 线拉到 Python 再算（`backtest_scan_scenarios.load_klines` 那种全量拉取只适合离线回测，不适合每日任务）。

**取价周期的数据覆盖**（决定 §4.4 的口径选择）：

| 周期 | 覆盖 | 用途 |
|------|------|------|
| `5m` | 全部告警样本（实测 195/195 命中） | **主口径**：基线取 `alerted_at` 前最后一根 5m 棒收盘价 ⇒ 入场价≈告警时刻价 |
| `1h` | 全量 | **兜底**：`alerted_at` 前 2h 内无 5m 数据时退回；同时用于行情环境指标（振幅/波动占比） |

> 5m 命中率之所以是 100%，是因为扫描器本身就在消费 5m 采样；但仍保留 1h 兜底，
> 以便 `asset_klines` 5m 回填断档时不至于整行 `no_data`。所选周期落库在 `kline_iv` 列，**可审计**。

### 3.2 三个时间维度

| 环节 | 频率 | 内容 |
|------|------|------|
| 结局结算 | 每小时（cron `5 * * * *`） | 把已到期窗口的 `outcome_state` 推进一级，只处理 `outcome_state <> 'resolved'` |
| 日报聚合 | 每日 08:10（Asia/Shanghai） | 聚合昨日（及近 3 日滚动）→ 落 `scan_edge_daily` / `scan_edge_bucket` |

### 3.3 为什么不改造现有早报

`send_daily_brief.py`（66KB）承担大盘/资金流/催化剂等 10 个模块的渲染，职责已饱和；
告警后验是**另一个数据域**（信号质量，不是市场状态），且需要**独立的历史回填与趋势表**。
故采用**独立脚本 + 独立表 + 独立邮件**，只在 `build_daily_brief.py` 里加一行「告警质量摘要」（读 `scan_edge_daily` 最新一行），
避免两套逻辑互相污染。详见 §9。

## 4. 详细设计

### 4.1 表 1：`biz.scan_signal_outcome`（逐信号多窗口结局）

```sql
CREATE TABLE IF NOT EXISTS biz.scan_signal_outcome (
    signal_id       BIGINT PRIMARY KEY REFERENCES biz.scan_signal(id) ON DELETE CASCADE,
    symbol          TEXT NOT NULL,
    pool            TEXT,
    scenario        TEXT,
    timeframe       TEXT,
    p_dir           TEXT,                          -- up / down（方向对齐基准）
    alerted_at      TIMESTAMPTZ,                   -- 告警时刻（= 决策起点）
    kline_iv        TEXT,                          -- 取价周期：5m（主）/ 1h（兜底）——口径可审计
    base_time       TIMESTAMPTZ NOT NULL,          -- 基线 K 线 open_time（<= alerted_at 的最后一根该周期棒）
    base_px         NUMERIC(24,8),                 -- 基线收盘价（≈ 告警时刻价）

    -- 方向对齐净收益（%，已扣 0.1% 双边费）
    aligned_ret_1h  NUMERIC(10,4),
    aligned_ret_4h  NUMERIC(10,4),
    aligned_ret_12h NUMERIC(10,4),
    aligned_ret_24h NUMERIC(10,4),

    -- BTC 同方向同窗口收益（beta 对照，%）
    btc_ret_1h      NUMERIC(10,4),
    btc_ret_4h      NUMERIC(10,4),
    btc_ret_12h     NUMERIC(10,4),
    btc_ret_24h     NUMERIC(10,4),

    -- 超额（= aligned_ret - btc_ret，正=信号有 alpha）
    excess_1h       NUMERIC(10,4),
    excess_4h       NUMERIC(10,4),
    excess_12h      NUMERIC(10,4),
    excess_24h      NUMERIC(10,4),

    -- 途中风险（在 1h 高低价上取，方向对齐，负值=不利）
    mae_24h         NUMERIC(10,4),                 -- 24h 内最大不利偏移（%，夹到 <=0）
    mfe_24h         NUMERIC(10,4),                 -- 24h 内最大有利偏移（%）
    sl_hit_24h      BOOLEAN,                       -- 是否触及 stop_loss_pct（该列为 NULL 时本列 NULL）
    sl_pct_snapshot NUMERIC(8,2),                  -- 冗余快照（该列是 09-21 后才有）

    -- 结算状态
    outcome_state   TEXT NOT NULL DEFAULT 'pending',
                    -- pending(未到 24h) / resolved(已结算 24h) / no_data(无 K 线或无 p_dir)
    last_window     SMALLINT NOT NULL DEFAULT 0,   -- 已结算的最大窗口小时数（0/1/4/12/24）
    bars_n          SMALLINT,                      -- 24h 窗口内可用该周期 K 线数
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX IF NOT EXISTS idx_scan_outcome_state
    ON biz.scan_signal_outcome (outcome_state, alerted_at DESC);
CREATE INDEX IF NOT EXISTS idx_scan_outcome_alerted
    ON biz.scan_signal_outcome (alerted_at DESC);

COMMENT ON TABLE biz.scan_signal_outcome IS '盘面告警逐信号多窗口结局（方向对齐净收益 + BTC beta 对照），供胜率赔率日报消费';
```

**结算规则**

- **取价周期**：`alerted_at` 前 2h 内有 5m K 线 → `kline_iv='5m'`，否则 `'1h'`。
  **同一行的 4 个窗口与 BTC 对照共用同一周期**，保证间隔一致、可比。
- 基线：`base_time` = `alerted_at` 时刻**最后一根**该周期 K 线的 `open_time`，`base_px` = 其 `close_px`。
- 终点：`alerted_at + N hours` 时刻**最后一根**该周期 K 线的 `close_px`。
- `net = (px1 − px0)/px0 × 100 × (+1 if p_dir='up' else −1) − 0.1`。
  **扣费在对齐之后**（与 `backtest_scan_scenarios.scan_symbol` 同口径）。写成 `(raw − 0.1)` 再取反会让做空信号赚到手续费。
- 只对 `p_dir IN ('up','down')` 计算；`p_dir` 为空（如 `BRK` 部分行）或无基线 K 线 → `outcome_state='no_data'`。
- `outcome_state='resolved'` ⇔ `last_window >= 24`；未满 24h 的行 `pending`，**只写已到期窗口**。
- **未到期窗口写 NULL，绝不混入日报统计**（`last_window` 闸门，同 `catalyst_outcome` 的教训）。

> ⚠️ **为什么不用「1h 已收盘棒」**：1h 棒 `open_time <= alerted_at` 的 `close_px` 是**该小时收盘**价，
> 即告警后最多 60 分钟的价。对突破类信号等于「晚进场一小时」，且终点会落在告警后 1.5~2h 而非恰好 1h ——
> 实测把 09-17 的 T+1h 胜率从 47.1% 压到 29.4%（系统性负偏，不可交易）。
> 改用 5m 后 09-17/09-18/09-22 与独立复算逐日吻合（47.1% / 56.2% / 35.6%）。

### 4.4 脚本 1：`scripts/bin/collect_scan_outcome.py`

- 调度：cron `5 * * * *`（每小时第 5 分钟，纯 UTC 计算，与上海日无关）
- 入参：`--days 7`（回看窗口，默认 7）、`--backfill-from YYYY-MM-DD`（首次回填 / 覆盖 `--days`）、
  `--force`（**重算已 resolved 的行**，口径修复后回填历史用）、`--cost`、`--dry-run`、`--json`
- 逻辑：
  1. 选候选：`scan_signal` 中满足 §2.2 告警口径、且（无 outcome 行 或 `outcome_state <> 'resolved'`）的信号，
     限定 `alerted_at >= 起点`；`--force` 时摘掉 resolved 守卫；
  2. **单条 SQL** 用 `WITH cand` + 10 个 `LEFT JOIN LATERAL` 一次性算完：基线、4 个窗口价、BTC 4 个窗口价、
     24h 高低价与 bar 数。周期选择在 `cand` 里定：

```sql
WITH cand AS (
    SELECT sg.id AS signal_id, sg.symbol, sg.p_dir, sg.alerted_at, sg.pool, sg.scenario,
           sg.timeframe, sg.stop_loss_pct,
           (CASE WHEN EXISTS (
                     SELECT 1 FROM biz.asset_klines k
                      WHERE k.symbol = sg.symbol AND k.interval = '5m'
                        AND k.open_time <= sg.alerted_at
                        AND k.open_time > sg.alerted_at - INTERVAL '2 hours')
                 THEN '5m' ELSE '1h' END) AS iv        -- ← 5m 为主、1h 兜底（§2.4）
      FROM biz.scan_signal sg
      LEFT JOIN biz.scan_signal_outcome o ON o.signal_id = sg.id
     WHERE sg.alerted_at IS NOT NULL
       AND (sg.pool = 'main' OR (sg.pool = 'accumulation' AND sg.scenario = 'BRK'))
       AND sg.status <> 'invalid'
       AND sg.alerted_at >= %s
       AND (o.signal_id IS NULL OR o.outcome_state <> 'resolved')   -- --force 时摘掉本行
)
SELECT c.*, b.open_time AS base_time, b.close_px AS base_px,
       w1.close_px AS px_1h, w4.close_px AS px_4h,
       w12.close_px AS px_12h, w24.close_px AS px_24h,
       bb.close_px AS btc_base_px, b1.close_px AS btc_px_1h,
       b4.close_px AS btc_px_4h, b12.close_px AS btc_px_12h, b24.close_px AS btc_px_24h,
       agg.low_24h, agg.high_24h, agg.bars_n
  FROM cand c
  LEFT JOIN LATERAL (          -- 基线：<= alerted_at 的最后一根
      SELECT k.open_time, k.close_px FROM biz.asset_klines k
       WHERE k.symbol = c.symbol AND k.interval = c.iv AND k.open_time <= c.alerted_at
       ORDER BY k.open_time DESC LIMIT 1) b ON TRUE
  LEFT JOIN LATERAL (          -- 终点：<= alerted_at + 1h 的最后一根（4h/12h/24h 同构）
      SELECT k.close_px FROM biz.asset_klines k
       WHERE k.symbol = c.symbol AND k.interval = c.iv
         AND k.open_time <= c.alerted_at + INTERVAL '1 hour'
       ORDER BY k.open_time DESC LIMIT 1) w1 ON TRUE
  -- …（w4 / w12 / w24 与 BTC 的 bb/b1/b4/b12/b24 共 9 个同构 LATERAL，此处省略）
  LEFT JOIN LATERAL (          -- 24h 途中风险（仅该币，不含 BTC）
      SELECT MIN(k.low_px) AS low_24h, MAX(k.high_px) AS high_24h, COUNT(*) AS bars_n
        FROM biz.asset_klines k
       WHERE k.symbol = c.symbol AND k.interval = c.iv
         AND k.open_time > b.open_time
         AND k.open_time <= c.alerted_at + INTERVAL '24 hours') agg ON TRUE
 ORDER BY c.alerted_at
```

  3. Python 侧（纯函数，可离线单测）：
     `aligned_ret()` 方向对齐 + 扣费、`mae_mfe()` 夹负、`matured_windows()` 未到期闸门、
     `settle_row()` 整行结算（未到期窗口写 NULL、`last_window` 递推、`sl_hit_24h`）；
  4. `UPSERT ... ON CONFLICT (signal_id) DO UPDATE` 写入；
  5. 打印汇总：`候选 / resolved / pending / no_data / 写入行数` + 逐日 4 窗口胜率与均收益。

> 实现注记：`aligned_ret` 的扣费位置有专门单测（`test_scan_edge_metrics.py` 前两条），
> 因为该符号错误不会报错、只会让空头样本静默变好。

### 4.5 脚本 2：`scripts/bin/build_scan_edge_report.py`

- 调度：cron `10 8 * * *`（Asia/Shanghai 08:10，早于 `daily_brief_email` 09:00）
- 入参：`--date YYYY-MM-DD`（默认昨日上海日）、`--days 7`、`--dry-run`、`--json`
- 逻辑：
  1. **样本闸门**：读当日 `scan_signal_outcome`（按 `(alerted_at AT TIME ZONE 'Asia/Shanghai')::date` 切日），
     `matured_n` = T+1h 已到期的行数，`pending_n` = 其余。`matured_n < 10` → `sample_ready=FALSE`，
     报告头打「样本不成熟」并**跳过失配判定**（只展示不报警）。
  2. **多窗口指标**：对 1/4/12/24h 各算 胜率/赔率/PF/均收益/盈亏平衡胜率（公式见 §5）。
  3. **beta 对照**：同窗口取 `btc_ret_*` 的方向对齐胜率与均值，算出 `excess_avg_24h`。
  4. **行情环境**：从 `asset_klines`（BTCUSDT 1h）算当日 `btc_amp_pct`、`btc_1h_gt05_ratio`；
     从 `fear_greed_daily` / `global_metric_daily` 取 `fgi` / `cap_trend_pct`；
     按 §5.4 规则打 `regime_label`。
  5. **近 3 日滚动**：读 `scan_edge_daily` 前 2 行 + 当日，算 `roll3_*`；
     **规则 A/B 的分母同时取两套**：`prev7_alerts_avg` = 最近 7 个 **有告警日**（`alerts_n > 0`）
     的均值，有效日 < 3 时置 `None` ⇒ 规则 A/B **不做判定**（宁可不报，不可虚报）。
     ⚠️ 0 告警日（daemon 无输出，如 09-19/09-20）不是「没机会」，计入会把均值压低、
     把异动倍数放大（09-23 实测：含 0 值日均值 23.7 ⇒ 7.4 倍；剔除后 35.5 ⇒ **5.0 倍**）；
  6. **分桶**：按 §4.3 的 8 个维度切桶，写 `scan_edge_bucket`，并挑出 `edge=TRUE` 的桶汇总为 `edge_buckets`。
     三层过滤，每一层都对应一类「报了也没用」的桶：
     - ⚠️ **单值维度不携带区分信息**：某维度当日只有一个桶时（如 `confidence` 全为 `high`、`regime` 全为 `range`）
       强制 `edge=FALSE`，否则「占比 100% 且负期望」会天天误报；
     - ⚠️ **上限开口桶排除**（`vol_ratio>6` / `price_chg>8` / `oi_chg>6`）：收紧阈值只会把样本
       从低档挪走，**永远裁不到这些桶** ⇒ 把它们列为「该收紧的阈值」是给不出去的建议；
     - ⚠️ **同义桶去重**：同一批样本被两个维度重复报出（`scenario=S1` 与 `pool=main` 的
       `n`/胜率/PF/占比 完全相同）时，按 `DIM_DEDUPE_ORDER` 优先级只保留一个，
       并把被丢弃者回写 `edge=FALSE`（保证落库、邮件、探针三处一致）。
       但 `scenario=BRK` 与 `scenario=S1` 虽然同维度，样本集不同 ⇒ 不会被误并。
  7. **失配判定**：跑 §5.5 的规则 A~E，写 `mismatch_flag` / `mismatch_rules` / `severity` / `conclusion`。
  8. `UPSERT` 进 `scan_edge_daily`（`ON CONFLICT (report_date) DO UPDATE`），分桶表先 `DELETE` 当日再插入
     （保证重跑幂等、不留残桶）。

### 4.6 脚本 3：`scripts/bin/send_scan_edge_report.py`

- 调度：cron `20 8 * * *`
- 与 `send_scan_signal_brief.py` 同构：`get_settings(require_database=True)` → `get_connection` →
  读 `scan_edge_daily`（当日一行）/ `scan_edge_bucket`（当日全部桶）/ 当日各窗口样本数 / 近 5 日趋势
  → `render_html()` → `EmailNotifier(settings).send(subject, html, from_name="盘面告警质量")`
- 主题：`【告警质量日报】MM-DD 3日滚动 T+1h 胜率 xx% · PF x.xx · <OK/WATCH/HIGH>`
  —— **必须用 3 日滚动值**，因为 `severity` 的判据就是滚动口径，两者同源才不自相矛盾：
  09-23 当日混合口径 59.1% / PF 1.10（其中 112 条是 `accumulation-BRK` 空头、`main` 池仅 35.9%），
  滚动口径 44.5% / PF 0.96 ⇒ 若主题写当日值，收件人只看主题会以为系统健康。
  当日值仍有完整展示（正文多窗口表 + 分层表）。
- 头部标注 **各窗口已到期样本数**（`T+1h 176 / T+4h 176 / T+12h 73 / T+24h 30`）而非单一
  「成熟 / 未到期」——后者按 T+1h 口径算，会被读成「四个窗口都有 176 条」；
- 生成时间固定 **北京时间**（`datetime.now(SH)`，`SH = UTC+8`）：容器 `TZ=UTC`，
  用 `astimezone()` 会让同一字段在容器/本机各自渲染成不同时刻（`00:20` vs `11:45`），
  且收件人无从判断时区。
- 支持 `--date YYYY-MM-DD`（补发某日；缺省取 `MAX(report_date)`）与 `--dry-run`（只打印 HTML）
- **只读不写**：数据一律由脚本 2 产出，避免两处各算一套口径

## 5. 计算公式

### 5.1 基础量（逐信号，窗口 w ∈ {1,4,12,24}h）

```
raw_w       = (px_w - px_0) / px_0 × 100             # 原始涨跌 %
aligned_w   = raw_w × (+1 if p_dir='up' else -1)      # 方向对齐
net_w       = aligned_w - COST,  COST = 0.1           # 扣双边费（与 backtest 同口径）
btc_net_w   = btc_raw_w × (same dir as p_dir) - COST  # BTC 同方向同窗口
excess_w    = net_w - btc_net_w                       # 超额（alpha）
```

> ⚠️ **扣费的顺序不能颠倒**。必须先按 `p_dir` 对齐毛收益，再减 `COST`：
> `aligned = raw × dir` 然后 `net = aligned − COST`。
> 若写成 `net = (raw − COST) × dir`，做空信号会**赚到 0.1% 手续费**（净收益虚增 0.2pp），
> 在多空混杂的样本里足以把接近 0 的期望判成正 —— 且不会报任何错。该口径有专门单测锁定。
> 参考实现：`backtest_scan_scenarios.scan_symbol`（`ret = ret_long if direction=='up' else -ret_long`，随后 `ret - cost`）。

### 5.2 核心指标（按日/按桶聚合）

| 指标 | 公式 | 说明 |
|------|------|------|
| 胜率 `win_w` | `count(net_w > 0) / n` | 平盘（=0）计入负 |
| 平均盈利 `avg_win_w` | `mean(net_w \| net_w > 0)` | |
| 平均亏损 `avg_loss_w` | `mean(net_w \| net_w < 0)`（负值） | |
| **赔率 `odds_w`** | `avg_win_w / abs(avg_loss_w)` | **平均盈利 ÷ 平均亏损**；一侧为空记 NULL（**不得记 ∞**） |
| **盈亏平衡胜率 `be_w`** | `1 / (1 + odds_w)` | **胜率低于它 ⇒ 期望为负**（判定主指标） |
| **盈亏比 `pf_w`** | `sum(net_w \| >0) / abs(sum(net_w \| <0))` | 总盈利 ÷ 总亏损 |
| 均收益 `avg_w` | `mean(net_w)` | 期望值 |
| 期望判定 | `win_w < be_w` ⇔ `avg_w < 0` | 两者等价，报告中同时展示以互相校验 |

> **为何同时要赔率和 PF**：赔率是「单笔幅度比」，PF 是「总额比」，两者在样本量差异大时给出不同信号。
> 实测 09-22 T+1h：赔率 1.51、PF 0.84 —— **胜率 35.6% 远低于平衡线 39.8%，且总额亏损大于盈利**；
> 若只看赔率（>1）会误判为「赔率不错、只是运气差」。**必须三个一起看**：胜率（频次）/ 赔率（幅度）/ PF（总额）。

### 5.3 样本量与置信

日样本 n=16~73，**单日胜率的标准误约 ±6~12 个百分点**，因此：

- 报告**同时给出**「当日值」与「近 3 日滚动值」；
- **失配判定只用滚动值**（`roll3_*`），当日值仅作展示与趋势参考；
- `roll3_win_1h < roll3_be_1h` 连续满足 → 才升级为 `severity='high'`。

### 5.4 行情环境分类 `regime_label`

| 标签 | 判据（当日 BTC，按上海日切 1h 棒） |
|------|-----------------------------------|
| `trend`（趋势） | `btc_amp_pct >= 4.0` **且**（`btc_1h_gt05_ratio >= 0.35` **或** `|btc_chg_pct| >= 2.0`） |
| `range`（横盘低波动） | `btc_amp_pct < 3.0` **且** `btc_1h_gt05_ratio < 0.20` |
| `mixed` | 其余（含缺行情数据的兜底） |

> **该维度是当前 `_build_regime` 缺失的「无趋势/低波动」判据**（现有只判 BTC 1h 方向、FGI、市值趋势，横盘时三者全不触发）。
>
> ⚠️ **`|btc_chg_pct| >= 2.0` 这个分支是 P2-9 补的**：单边涨跌日的分钟级持续单向、小时级回撤少，
> 「小时 |涨跌|>0.5% 占比」天然偏低（09-23 仅 16.7%），只按占比判会让这类日子落成 `mixed`
> ⇒ **只在 `range` 生效的规则 B 永远拿不到单边行情**。加上日涨跌分支后 09-23 由 `mixed` → `trend`。

**实测 7 日分布（⚠️ 未经验证，仅作展示与分桶维度）**

| 日期 | BTC 涨跌 | 振幅 | >0.5% 占比 | 判定 | T+1h |
|------|---------:|-----:|-----------:|------|------|
| 09-17 | +1.32% | 2.42% | 10.5% | range | 47.1% / −0.34% |
| 09-18 | +5.13% | 6.49% | 16.7% | trend（日涨跌分支） | 56.2% / +1.38% |
| 09-19 | +1.14% | 1.82% | 4.2% | range | — （0 告警） |
| 09-20 | −0.90% | 2.29% | 4.2% | range | — （0 告警） |
| 09-21 | +6.19% | 7.21% | 29.2% | trend（日涨跌分支） | 38.9% / −0.07% |
| 09-22 | +0.57% | 2.71% | 16.7% | range | 35.6% / −0.21% |
| 09-23 | −2.79% | 4.10% | 16.7% | trend（日涨跌分支） | 59.1% / +0.08% |

**必须诚实记录的两个事实**（否则会把该维度当已验证参数用）：

1. **7 日内 5 天有样本，`range` 2 天 / `trend` 3 天**，分布不算偏；但 `trend` 的判定
   全靠「日涨跌」分支命中（占比分支 7 日内零命中，阈值 0.35 偏高）⇒ 该分支是否有效
   **尚无独立样本佐证**，`mixed` 也未在任何一天实际出现。
2. **`range` 内部并不齐**：同为 `range`，09-17 的 T+1h 是 47.1%（期内最佳），09-22 只有 35.6%；
   而 `trend` 里 09-21 是 38.9%、09-23 是 59.1%（但后者是空头池撑起来的，见 §2.3）。
   因此 **regime 与告警质量的关系尚无统计支撑**（每格样本 1~3 天）。按项目惯例，该维度属**锚定参数**，
   需预留 ≥30 天、多 regime、日级 t≥2 的样本外期验证后才可写入拦截逻辑；
   **在此之前它只用于报告展示与分桶，规则 B 的命中不得作为「已知因果」解读**。

### 5.5 失配判定规则

| ID | 规则 | 含义 |
|----|------|------|
| **A** | `roll3_alerts_avg > prev7_alerts_avg × 1.5` 且 `roll3_win_1h < roll3_be_1h` | **阈值-行情失配**：告警量激增 + 期望转负（09-22/09-23 的典型形态） |
| **B** | `regime_label='range'` 且 `alerts_n >= prev7_alerts_avg` 且 `roll3_pf_1h < 1.0` | **横盘市信号天然失效**：应在横盘时抑制/收紧（⚠️ regime 未验证，见 §5.4） |
| **C** | 存在桶满足 `n >= 5` 且 `win_1h < be_1h` 且 `share >= 0.2`（且非上限开口桶、非同义桶） | **边缘桶**：给出「该收紧哪个阈值」的具体坐标 |
| **D** | `timeframe='15m'` 桶**自身**连续 2 日 `win_1h < be_1h`（`n >= 5`） | **周期退化**：建议横盘期抑制 15m 通道 |
| **E** | `n_24h >= 10` 且 `win_24h > be_24h`（**先确认 T+24h 是正期望**）且 `btc_win_24h > 0.5` 且 `\|excess_avg_24h\| < 0.5%` | **纯 beta 贡献**：中长窗口胜率不构成信号质量证据 |

`severity`：命中 A 或 B → `high`；仅命中 C/D/E → `watch`；均未命中 → `ok`；`sample_ready=FALSE` → 直接 `ok`（只展示不判定）。

> **规则 A/B 的 `prev7_alerts_avg` 只统计「有告警日」**（`alerts_n > 0`，最近 7 个），有效日 < 3 则规则 A/B 不判定（§4.5 步骤 5）。

**两处判据修订（P0-2 / P2-8）**

- **规则 E 必须先确认正期望**：旧判据 `btc_win_24h - win_24h < 0.10` 且 `excess_avg_24h < 0.5%`
  **没有「正期望」这个前提** —— 09-23（`win_24h` 20.0% ≪ `be_24h` 49.3%、BTC 同向胜率 0%、超额 −3.24pp）
  竟命中「中长窗口**正期望**主要来自 beta」，输出与实际方向**完全相反**。修订后加了
  `win_24h > be_24h`（正期望）与 `btc_win_24h > 0.5`（beta 确实赚钱）两道门，并要求 `n_24h >= 10`。
- **规则 D 不再依赖「边缘桶」**：旧判据要求 `timeframe=15m` 入选边缘桶（`share >= 0.2`），
  而占比门槛回答的是「值不值得收紧阈值」，与「该通道是否连续失效」无关 ——
  09-23 的 15m 桶胜率 20.0%、PF 0.34，占比 19.89%（**差 0.11pp**）未入选 ⇒ 旧写法整体漏报。
  现改为直接看 15m 桶自身是否负期望。

**实跑结果（7 日）**

| 日期 | severity | 命中规则 | 3 日滚动 T+1h 胜率 / 平衡线 / PF |
|------|----------|----------|----------------------------------|
| 09-17 | WATCH | C | 47.1% / 53.0% / 0.79 |
| 09-18 | OK | — | 51.7% / 37.7% / 2.61 |
| 09-19 | OK | —（0 条告警） | 51.7% / 37.8% / 2.61 |
| 09-20 | OK | —（0 条告警） | 56.2% / 22.5% / 4.42 |
| 09-21 | WATCH | C | 38.9% / 40.6% / 0.93 |
| 09-22 | **HIGH** | A / B / C | 37.3% / 40.2% / 0.88 |
| 09-23 | **HIGH** | A / C / D | 44.5% / 45.7% / 0.96 |

> 规则 A 在 09-22（告警 73 条 = 最近 3 个有告警日均值 23.0 的 3.2 倍）与
> 09-23（176 条 = 35.5 的 5.0 倍）均命中，说明「告警量异动 + 滚动期望转负」这一组合
> **能自动复现人工复盘发现的失配日**。
> 09-21 只判 WATCH（告警 36 条 = 8.2 的 4.4 倍，但滚动胜率 38.9% 与平衡线 40.6% 仅差 1.7pt），
> 属**阈值边缘**，符合「宁可漏报不误报」的设计取向。
> 09-23 相对于 v1.3 的旧输出有三处变化：规则 **E 不再命中**（判据加了正期望前提）、
> 规则 **B 退出**（regime 由 `range` → `trend`，见 §5.4）、规则 **D 新命中**（15m 桶连续 2 日负期望）。

`conclusion` 示例（09-23 实跑）：
`"阈值-行情失配（规则 A/C/D）；告警 176 条 = 最近 4 个有告警日均值 35.5 的 5.0 倍；3 日滚动 T+1h 胜率 44.5% < 盈亏平衡线 45.7%、PF 0.96；边缘桶 scenario=S1(胜率 35.9%/占 36.4%)。"`

> ⚠️ 本日报**只输出判定，不改任何阈值、不拦截任何告警**（与轧空影子模式同原则）。
> `severity=high` 的含义是「该人来看一眼并决定是否调阈值」，不是「系统已自动收紧」。

## 8. 风险与注意

| 风险 | 说明 | 对策 |
|------|------|------|
| **取价口径漂移** | 用「1h 已收盘棒」会把 T+1h 胜率系统性压低 17.7pt（09-17 实测 47.1%→29.4%），且入场价不可交易 | 固定 5m 为主 / 1h 兜底，所选周期落 `kline_iv` 列可审计；探针断言「存在 5m 取价行」 |
| **扣费符号错** | `(raw − cost)` 再按方向取反 ⇒ 做空赚手续费、空头虚增 0.2pp，且不报错 | 扣费固定在对齐之后；探针前两条专门锁定该边界 |
| **样本量小** | 日 n=17~79，单日胜率标准误 ±6~12pt | 判定只用近 3 日滚动；`matured_n < 10` 时 `sample_ready=FALSE` 只展示不报警 |
| **选择偏置** | 样本限 `alerted_at IS NOT NULL`，而告警本身依赖 regime 顺风（`_scenario_priors` docstring 已自述「正期望是该口径的必然结果」） | 报告中显式标注「仅含已告警样本，非无偏基准」；beta 对照行强制并列 |
| **beta 混淆** | 全样本 T+24h 信号胜率 48.6%，而同期 BTC 同方向胜率在**单边上行日 09-18/09-21 是 100%、单边下跌日 09-23 是 0%** ⇒ 中长窗口的「正」几乎不是信号质量证据，只是跟随 BTC 方向 | 强制输出 `btc_win_24h` / `excess_avg_24h`，规则 E 拦截「纯 beta」误判（v1.4 已加 `win_24h > be_24h` 前提，避免负期望日反被判为 beta 归因） |
| **regime 判据未验证** | 7 日内 `trend` 判定**全部由 `abs(btc_chg_pct) >= 2.0` 分支命中**（振幅/波动占比分支零命中）；`mixed` 在 7 日内从未出现；同为 `range` 的 09-17（47.1%）与 09-22（35.6%）差异极大 | 该维度只用于展示与分桶；规则 B 命中不得当作因果（§5.4），需 ≥30 天样本外验证 |
| **`stop_loss_pct` 覆盖不全** | 该列 2026-09-21 08:40 UTC 才落库，之前样本恒 NULL | `sl_hit_24h` 留 NULL；不参与胜率口径，仅作旁证 |
| **时区** | `report_date` 必须固定 Asia/Shanghai，而结算用 UTC | 表内只存 DATE（已按上海日切分）；SQL 用 `AT TIME ZONE 'Asia/Shanghai'` 切日 |
| **未到期行混入** | 会系统性高估胜率（未到期样本天然偏「还没跌」） | `last_window` 闸门 + `pending_n` 显式展示（同 `catalyst_outcome` 教训） |
| **跨区链路超时** | `asset_klines` 整表拉取 240s+ 不返回 | 取价一律 `LATERAL` 子查询在 SQL 侧算好（§4.4） |
| **「报警」变「噪声」** | 天天 `high` 会脱敏（当前 7 日中已 2 天 HIGH） | 规则 A/B 用滚动值 + 前 7 日均值倍数；同一规则连续 3 日命中才升级 `high`（P2 再评估） |
| **阈值改动** | 本方案**不改任何阈值常量** | 只输出「哪个桶负期望、占多少」，阈值调整仍走人工决策（与轧空影子模式同原则） |
