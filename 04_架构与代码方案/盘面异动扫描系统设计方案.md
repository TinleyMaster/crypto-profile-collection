# 盘面异动扫描系统设计方案

> 版本：v1.1（2026-09-24）
> 日期：2026-09-16 初稿 / 2026-09-24 现行版
> 目标：批量扫描加密代币盘面异动，识别高确定性机会，输出可执行观察清单。
>
> **本文只描述系统的「当前」口径与实现**——不含历史修订记录、不含已被取代的参数值、不含「原实现如何」的对照说明。
> 凡标注「**实测**」的为 prod 只读查询结果；凡标注「**未实现**」的是设计里有但代码里没有的东西。
> 未解决的缺口与待决策项统一收敛在 **§12.1**。

---

## 1. 背景与目标

现有系统已具备：CMB/CMC 行情日线、衍生品资金面快照（funding/OI/CVD 24h 聚合）、催化剂、KOL、解锁、链上监控、恐惧贪婪指数、板块资金流等数据与采集脚本，且已有 `auto_trade_signal.py` 交易执行链路和 `backtest_opportunities.py` 回测框架。

本方案在其之上新增一套**盘面异动扫描系统**，定位为"研究辅助"，输出盘面观察清单与信号，不直接自动下单。

**核心设计原则：**

1. 低成本粗筛优先：全市场先跑价量粗筛，命中者才拉 OI/CVD 做深度校验，控制算力与 API 消耗。
2. 双池并行：主异动扫描池 + 蓄势埋伏观察池，互补漏检。
3. 回测先行：8 个深度校验场景必须经历史回测标定后，才作为信号可信度依据。
4. 数据自积累：OI/CVD/清算等依赖时间序列的指标，从现在开始持续采样入库。
5. 回测结论必须接受线上检验：回测（§8）与线上结果闭环（§8.1）**并列展示**，二者冲突时以线上实测为准并触发失配处置，不得只引用样本内数字。

### 3.2 需要新建的表

**① OI/CVD 采样历史表 `biz.oi_cvd_snapshot`**（蓄势池与 OI↑↓ 判定的数据前提）

```sql
CREATE TABLE IF NOT EXISTS biz.oi_cvd_snapshot (
    symbol       TEXT           NOT NULL,
    ts           TIMESTAMPTZ    NOT NULL,          -- 采样时间
    exchange     TEXT           NOT NULL DEFAULT 'binance',
    oi_usd       NUMERIC(24,2),                    -- OI 总价值（USDT）
    cvd_5m_usd   NUMERIC(24,2),                    -- 本采样窗口净主动成交（正=主动买盘强）
    cvd_1h_usd   NUMERIC(24,2),                    -- 近 1h 累计 CVD（写后回填）
    vol_5m_usd   NUMERIC(24,2),                    -- 本采样窗口总成交额
    source       TEXT           NOT NULL DEFAULT 'realtime',  -- realtime / backfill（fix_057 加列，fix_059 回标）
    PRIMARY KEY (symbol, exchange, ts)
);
CREATE INDEX IF NOT EXISTS idx_oi_cvd_snapshot_ts ON biz.oi_cvd_snapshot (ts DESC);
CREATE INDEX IF NOT EXISTS idx_oi_cvd_snapshot_sym_ts ON biz.oi_cvd_snapshot (symbol, ts DESC);
CREATE INDEX IF NOT EXISTS idx_oi_cvd_snapshot_source_ts ON biz.oi_cvd_snapshot (source, ts DESC);
```

采样频率建议：每 5 分钟一次（与 5m 周期对齐），5m/1h 的 OI 变化率与 CVD 由历史序列现算，而非依赖 24h 快照。

> **`source` 列的用途（实测）**：区分「5m 实时采样」与「1h 历史回填」。两者**不可混用**——
> 主池算「近 2 桶 OI 变化」只取 `source='realtime'`（回填行会污染）；蓄势池 ACC 需要「连续 ≥12 个小时桶」，
> **刻意不过滤** `source`（回填行正好补停摆/部署窗口的小时桶）。
> 保留期：`OI_CVD_RETENTION_DAYS = 90`（528 币 × 288 桶/天 ≈ **15 万行/天**，90 天 ≈ 1350 万行）。

**② 爆仓滚动窗口快照表 `biz.liquidation_snapshot`**（**轧空扫描实际使用的爆仓源**；另一张 `biz.liquidation_events` 见下方说明）

```sql
CREATE TABLE IF NOT EXISTS biz.liquidation_snapshot (
    symbol            TEXT         NOT NULL,        -- 合约符号（如 BTCUSDT；含中文名合约，CoinGlass 能对上）
    ts                TIMESTAMPTZ  NOT NULL,        -- 采样时间（5min 桶）
    source            TEXT         NOT NULL DEFAULT 'coinglass',
    liq_usd_1h        NUMERIC(24,2),                -- ⚠️ 滚动 1h 窗口快照（非整点累计）
    liq_usd_4h        NUMERIC(24,2),
    liq_usd_12h       NUMERIC(24,2),
    liq_usd_24h       NUMERIC(24,2),
    long_liq_usd_1h   NUMERIC(24,2),                -- 多单爆仓（价格下跌被强平）
    short_liq_usd_1h  NUMERIC(24,2),                -- 空单爆仓（价格上涨被强平）
    long_liq_usd_4h   NUMERIC(24,2),
    short_liq_usd_4h  NUMERIC(24,2),
    long_liq_usd_24h  NUMERIC(24,2),                -- 后加（fix_068）：24h 多空分列
    short_liq_usd_24h NUMERIC(24,2),                -- 后加（fix_068）
    fetched_at        TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
    PRIMARY KEY (symbol, ts)
);
CREATE INDEX IF NOT EXISTS idx_liq_snapshot_ts ON biz.liquidation_snapshot (ts DESC);
CREATE INDEX IF NOT EXISTS idx_liq_snapshot_sym_ts ON biz.liquidation_snapshot (symbol, ts DESC);
```

> **消费口径（必须遵守）**：各 `*_liq_usd_*` 列是 CoinGlass 的**滚动窗口累计值**。
> 消费侧**取绝对值**（`liq_usd_1h` = 最近 1 小时爆仓额），**严禁跨桶差分**——相邻两次滚动快照相减得到的是
> 「新滚入 − 滚出」（平稳时≈0、回落时常为负），再 `max(…,0)` 截断即假 0（曾把 25.6 万 U 空头爆仓显示为 `+0.000%`）。
> 迁移与注释见 `scripts/migrations/fix_056_squeeze_scan.sql`；24h 多空分列由 `fix_068_liquidation_snapshot_24h_split.sql` 追加
> （**实测**：近 3h 17,391 行双列 100% 非空 ⇒ 已全量生效）。

**③ 信号输出表 `biz.scan_signal`**（主池 + 蓄势池统一出口，供回测与观察清单消费）

```sql
CREATE TABLE IF NOT EXISTS biz.scan_signal (
    id           BIGSERIAL PRIMARY KEY,
    signal_ts    TIMESTAMPTZ    NOT NULL,
    symbol       TEXT           NOT NULL,
    pool         TEXT           NOT NULL,          -- 'main' / 'accumulation' / 'squeeze'
    scenario     TEXT,                             -- S1..S8 / ACC / BRK / SQZ_<CONCLUSION>
    timeframe    TEXT,                             -- 5m/15m/1h（主池多周期共振级别）
    p_dir        TEXT, price_chg_pct NUMERIC(8,2),
    vol_state    TEXT, vol_ratio      NUMERIC(8,2),
    oi_dir       TEXT, oi_chg_pct     NUMERIC(8,2),
    cvd_dir      TEXT,
    cvd_usd      NUMERIC(20,2),                    -- CVD 窗口净额（fix_060）
    cvd_ratio    NUMERIC(12,6),                    -- 净额 / 同窗口成交额
    funding_rate NUMERIC(12,8),
    confidence   TEXT,                             -- high/medium/low
    context_tags TEXT[],                           -- 市场环境标签（regime）
    detail       JSONB,                            -- 轧空判定 metrics / 结论 / 原因（fix_056）
    trigger_price NUMERIC(24,8),                   -- 入场位 = 触发周期收盘价
    stop_loss_pct NUMERIC(8,2),                    -- 失效位幅度% = 2×ATR(14)/参考价，夹 [8%,20%]
    breakout_px  NUMERIC(24,8),                    -- 延续确认位 = 触发根方向侧极值（fix_061）
    alerted_at   TIMESTAMPTZ,                      -- 后加：告警去重（同币 12h 冷却）
    alert_suppressed_at     TIMESTAMPTZ,           -- 后加（fix_060）：跨池互斥（main⇄squeeze）压制时刻
    alert_suppressed_reason TEXT,                  -- 后加（fix_060）：压制原因
    exec_state   TEXT,                             -- 后加（fix_046）：执行层状态，dry-run/已执行
    executed_at  TIMESTAMPTZ,                      -- 后加（fix_046）：最近一次执行处理时间
    status       TEXT NOT NULL DEFAULT 'active',   -- active/confirmed/expired
    expired_at   TIMESTAMPTZ,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

> 说明：粗筛候选池、蓄势池无需单独建表持久化，作为内存态/临时态处理即可；落库的是最终信号与历史采样。
>
> **`status` 取值口径 = `active / confirmed / expired`**（与列名 `expired_at`、`biz.squeeze_track` 的终态一致）。
> 退出机制：`scan_daemon` 任务 `expire_signals`（30min）把 `pool='main'` 与 `accumulation/BRK` 超 **24h**、
> `accumulation/ACC` 超 **7 天** 的 `active` 置 `expired` 并写 `expired_at = signal_ts + TTL`
> （确定性截止时刻，不写 `NOW()`）。时机语义来源见 §6.3。
> **入场位 / 失效位**：主池与 BRK 生产者均落 `trigger_price`（= 触发周期收盘价）与 `stop_loss_pct`
> （= `2×ATR(14)` / 参考价，夹 `[8%, 20%]`），消费者见 §6.3 第 3 条。
> **`active → confirmed` 延续确认**：`breakout_px` 列（迁移 `fix_061`）+ `scan_daemon` 任务 `confirm_signals`（30min）。
> `breakout_px` = 触发根方向侧极值（与 `trigger_price` 同根，无未来信息、恒在入场价正确一侧）；
> `signal_ts` 后 **6h** 内一根**已收盘** 1h 收盘价越位 ⇒ `confirmed`。
> `confirmed` 是**质量升格**（仍在可动作集合）**而非入场门槛**——依据见 §6.3 第 3 条。

**④ 结果闭环与质量日报三表（迁移 `fix_066_scan_edge_report.sql`，设计依据见 `告警胜率赔率日报方案_2026-09-23.md`）**

`scan_signal` 只记「发过什么信号」，不回答「这些信号后来怎么样了」。本组三表补上这个闭环：

| 表 | 主键 | 职责 |
|---|---|---|
| `biz.scan_signal_outcome` | `signal_id` | 逐信号多窗口结局：`aligned_ret_1h/4h/12h/24h`（**方向对齐净收益，已扣 0.1% 双边费**）、`btc_ret_*`（同向同窗口 beta 对照）、`excess_*`（= aligned − btc，正 = 有 alpha）、`mae_24h`/`mfe_24h`、`sl_hit_24h` + `sl_pct_snapshot`、`outcome_state`（`pending`/`resolved`/`no_data`）、`last_window`（已结算的最大窗口，**未到期行不得混入日报统计**）、`kline_iv`（取价周期 5m 主 / 1h 兜底） |
| `biz.scan_edge_daily` | `report_date`（上海日） | 日报聚合：`win_*`/`odds_*`/`be_*`/`pf_*`/`avg_*`（多窗口）、`btc_win_24h`/`btc_avg_24h`/`excess_avg_24h`、行情环境（`btc_chg_pct`/`btc_amp_pct`/`btc_1h_gt05_ratio`/`fgi`/`cap_trend_pct`/`regime_label`）、近 3 日滚动（`roll3_alerts_avg`/`roll3_win_1h`/`roll3_be_1h`/`roll3_pf_1h`，**失配判定只用滚动值**）、样本成熟度（`matured_n`/`pending_n`/`sample_ready` = `matured_n>=10`）、失配判定（`mismatch_flag`/`mismatch_rules` A~E/`severity` `ok`·`watch`·`high`/`conclusion`） |
| `biz.scan_edge_bucket` | (`report_date`,`dim`,`bucket`) | 当日 × 维度 × 桶诊断：`dim ∈ {vol_ratio, price_chg, oi_chg, timeframe, scenario, regime, confidence, pool}`，含 `share`（占当日告警数比例）与 `edge`（`n>=5` 且 `win_1h<be_1h` 且 `share>=0.2`）⇒ 定位「该收紧哪个阈值」的具体坐标 |

**实测规模（2026-09-24 只读）**：`scan_signal_outcome` 328 行（main 185 / accumulation 143），其中 **202 行已 `resolved`**、其余仍在到期中（**squeeze 池 0 行**，见 §10.8）；
`scan_edge_daily` 7 天、`scan_edge_bucket` 93 行。

> **闭环口径要点**：① 结算基准是 `alerted_at`（决策起点）而非 `signal_ts`；② 基线取「`<= alerted_at` 的最后一根 K 线收盘价」；
> ③ 强制输出 BTC beta 对照，避免把单边行情下的跟随收益误读为信号 alpha（§8.1）；④ 未到期（`outcome_state='pending'` / `sample_ready=FALSE`）**不得参与失配判定**。

## 4. 主异动扫描池（核心管线）

### 4.1 L0 市场环境过滤（新增，必须）

扫描结果脱离市场环境没有意义。只有环境允许时才采信对应方向信号：

- **BTC 方向/主导率**：BTC 近 1h/4h 方向；BTC.D 趋势。
- **恐慌贪婪指数**（已有数据）：极端恐慌时多头信号降权，空头信号升权。
- **总市值趋势**：市场总市值处于上升段才采信多头信号。
- **板块资金流**（已有 `sector_flow_daily`）：标的所在板块净流入时加分。

输出 `context_tags`，随信号落库。

### 4.2 L1 粗筛（多周期通道；⚠️ 设计所称"共振"未实现，见下）

**设计意图**是「升档共振」（多周期方向一致才升级）；⚠️ **线上实现并非共振**——`_l1_screen` 是各周期独立判定、取最高 level，跨周期方向一致性检查**未实现**（见下）：

| 级别 | 条件（**实测阈值，与代码一致**） | 处理 |
|---|---|---|
| 候选（level 1） | 5m 价量异动（价格 ±**1.5%**、量 ≥2× 近 20 根均值） | 触发后被调用侧 `if l1["level"] < 2: continue` **丢弃**（等效"只观察"） |
| 入池（level 2） | **15m 单周期**价量异动（价格 ±**2.0%**、量 ≥2×） | 进入 L2 深度校验（tag `lv2_15m`） |
| 高置信（level 3） | **1h 单周期**价量异动（价格 ±**3.0%**、量 ≥2×，tag `lv3_1h`） | 进入 L2 |

- ⚠️ **1h 阈值「两处不同值」的口径澄清**
  回测 `backtest_scan_scenarios.py` 与独立脚本 `phase_scan_main_pool.py` 用
  **4.0%**，线上 `scan_daemon.py::task_scan_main_pool` 用 **3.0%**。**它们不是同一个量**：
  - **回测口径** = 单周期「1h 单根涨跌幅 ≥ 阈值」即触发（`interval='1h'` 逐根判，无 5m/15m 通道）；
  - **线上口径** = 三周期**各自独立成通道**：`_l1_screen` 遍历 1h/15m/5m，任一周期满足
    `|chg| >= PRICE_THR[iv] and vol_ratio >= 2.0` 即入选并取 `LEVEL_RANK` 最高者；
    调用侧 `if l1["level"] < 2: continue` ⇒ **15m(2.0%) 与 1h(3.0%) 都能单独把币送进 L2**。

  故把线上 1h 改成 4.0 **无法复现**回测 4.0 档的效果：回测里被 4.0 滤掉的「1h 涨 3~4%」样本，
  在线上多数已先被 15m 通道（2.0%）捕获入池，改 1h 几乎不削减那批样本，也拿不到那部分期望提升
  （回测 3.0→4.5 档 24h 净均 +5.13%→+6.66% 是针对**单周期**口径测出来的）。
  ⇒ **线上 1h 阈值保持 3.0**；`4.0` 仅为单周期回测口径，不可直接搬到多周期线上（代码内已加同口径注释）。
  多周期阈值（5m/15m）**没有回测支撑**（见 §12.1）。

- 量能判定用"当前周期成交额 vs 近 N 周期均值"（N = 20），避免用 24h 快照。量比阈值 `VOL_RATIO_THR = 2.0`
  在 §8 第三轮扫参里**几乎无边际贡献**（仅削减信号量），定位是流动性护栏而非质量过滤。
- **触发根选择：优先已收盘条** —— 每个周期的判定根取
  **「最近一根已收盘条（`open_time + 周期时长 <= now`，值稳定 ⇒ 判定可复现），不合格才回退最新
  未收盘条（保持及时性）」**；`_l1_screen` 返回 `bar_idx` 指向被判定那一根，`trigger_price` /
  `breakout_px` / `stop_loss_pct`（含 ATR 窗口）全部锚定到该根。
  依据：`scan_klines` 每 5min UPSERT 覆盖未收盘条 ⇒ 一根条的「终值可用且仍是最新根」窗口仅约 2~5 分钟，
  而主池扫描每 15min 一轮 ⇒ 只看最新根会让「能否看到收盘终值取决于相位」。离线量化（6 天 / 280 币，
  用 5m 重建触发条在 +5/+10/+15 分钟的快照）：真异动条（终值 `|chg|≥2%` 且 `vr≥2.0`）**1719** 根中，
  **53.5% 只有收盘才越阈**（+5min 11.9% / +10min 30.1% / 收盘 53.5% / 条内始终不满足 4.5%）。
  prod 单快照回放：新规则 L1(level≥2) 命中 9 / 旧规则 5，补回 4 条且全部过 L2、不在冷却内，反向 0 条 ⇒ 漏检率 ≈44%。
  该修法**会提升信号量**（属预期，非回归）；去重仍由主池 6h 冷却承担，未新增机制。
  自测：`05_代码与脚本/workbench/test_scan_l1_closed_bar.py`。
- ⚠️ **「三周期方向必须一致才升级」未实现**：`_l1_screen` 对 1h/15m/5m
  **各自独立**判定（`|chg| >= PRICE_THR[iv] and vol_ratio >= 2.0`），把达标的最高 `LEVEL_RANK` 写进 `best`，
  **没有任何跨周期方向一致性检查**；`context_tags` 也只携带**触发的那个周期**的标签
  （`lv{level}_{iv}`，见 `task_scan_main_pool`）。因此：
  - 「5m 单独异动只观察」是靠调用侧 `level < 2` 丢弃实现的；
  - **15m 或 1h 任一达标即可单独入池，不要求彼此同向**——即同一条 1h 级信号，其 15m/5m 可能正好反向。
  真正实现共振需改 `_l1_screen` 并需回测支撑（见 §12.1，本轮不动代码）。
- ⚠️ **「1h 同向 → 信号权重 ×2」未实现**：`scan_signal` 无权重列，1h 共振只以 `context_tags` 里的
  `lv3_1h` 标签体现，不参与置信度计算（置信度规则见 §4.3）。若要真正加权重需先加列/改公式。
- **资金费率不参与 L1 粗筛**：费率是 8h 结算的慢变量，与分钟级异动时间维度不匹配；且行情启动初期费率通常仍处中性区间，作为触发条件会漏掉早期行情。费率仅作为 L2 拥挤度辅助标签。

### 4.3 L2 深度校验（8 场景）

**指标定义（本方案补充口径要求）：**

- P：当前周期价格方向（与 L1 一致）。
- VOL：放量 / 缩量（当前成交额 vs 近 20 周期均值）。
- OI：⚠️ **不是「本周期」OI 变化方向**——`_compute_l2` 取的是 `oi_rows[-1]` 与 `oi_rows[-1-OI_RISE_BARS]`，
  即**最近 2 个 5m 实时桶**，与 L1 触发根（`l1["bar_idx"]`）**无关**。价格锚在触发根、OI/CVD 锚在最新桶，
  两者时间轴可错位数十分钟（触发根优先已收盘条，见 §4.2）⇒ 严格说该维度是「**判定时刻的近 2 桶 OI 方向**」，
  而非「触发根所在周期的 OI 方向」。属**已知口径缺陷，本轮只登记不改代码**（§12.1-B18）。
  ⚠️ **口径（实测）：`oi_dir` 是二值无阈值**——`OI_RISE_BARS = 2`，取最近 2 桶 OI 对比，涨即 `up`、跌即 `down`。
  prod 实测存在 `oi_chg_pct = +0.06%` 仍被判 `high` 的样本，即 `P↑OI↑` 里的「OI↑」**不含幅度门限**。
  这是**刻意与回测保持一致**（`backtest_scan_scenarios.py` 同为二值），改动需两侧同步 ⇒ 目前无 OI 幅度/加速度分档（见 §12.1-B5）。
- CVD：本周期累计成交量差方向（正 = 主动买盘强）。
- funding（资金费率）：辅助**拥挤度风险标签**，**不参与任何筛选/触发**。8h 结算一次、慢变量；正数 = 多头持仓拥挤、多头持续付息；负数 = 空头持仓拥挤、空头持续付息。仅在 L2 用于评估反转/过热风险。

**场景编号（`scenario` 列）—— 两套编码来源，语义不同，必须按来源理解：**

**① 现役主池生产者 `scan_daemon._compute_l2`（线上唯一在产的口径）**：只用 `(p_dir, oi_dir)` 两维，
**CVD / VOL 不参与判定**（CVD 只落 `cvd_dir`/`cvd_usd`/`cvd_ratio` 供渲染；VOL 采信与否由 L1 量比承担）：

| # | P | OI | 解读 | 信号 |
|---|---|---|---|---|
| S1 | ↑ | ↑ | 价涨 + OI 增 = 新开多仓 | 多头进攻 |
| S2 | ↓ | ↑ | 价跌 + OI 增 = 新开空仓 | 空头扎实 |
| S3 | ↑ | ↓ | 价涨 + OI 减 = 多头平仓 / 空头回补 | 多头减仓 |
| S4 | ↓ | ↓ | 价跌 + OI 减 = 多头止损离场 | 空头兑现 |

**② 独立脚本 `phase_scan_main_pool.py`（未被 daemon 调度，其历史行仍在库内）**：按 `(p_dir, oi_dir, cvd_dir)`
三维落**设计口径的 8 场景**：

| # | P | OI | CVD | VOL | 解读 | 信号 |
|---|---|---|---|---|---|---|
| S1 | ↑ | ↑ | ↑ | ↑ | 现货买盘强 + 合约新开多仓，真实多头进攻 | 多头趋势延续 |
| S2 | ↑ | ↑ | ↓ | ↑ | 现货主动卖，上涨靠合约杠杆，诱多 | 警惕回调（空头候选） |
| S3 | ↓ | ↑ | ↓ | ↑ | 现货砸盘 + 合约新开空单，真实空头 | 空头趋势延续 |
| S4 | ↓ | ↑ | ↑ | ↑ | 现货承接，下跌由合约空头砸出，诱空 | 存在反弹潜力 |
| S5 | ↑ | ↓ | ↑ | ↑ | 合约平仓 + 现货买入，获利了结 | 反弹近尾声 |
| S6 | ↑ | ↓ | ↓ | ↑ | 空头回补，非新多进场 | 修复反弹 |
| S7 | ↓ | ↓ | ↓ | ↑ | 空头止盈平仓，跌势衰竭 | 衰竭信号 |

> ⚠️ **同一编号在两套里的含义相反**（如 `S2`：① = 价跌+OI 增「空头扎实」，② = 价涨+OI 增+CVD↓「诱多」）⇒

**资金费率拥挤度标签（附加层、不参与触发；编号按上表 ② 的设计口径）：**

| 场景 | 附加费率标签 |
|---|---|
| S1 | 费率持续大幅正 → 多头过热，警惕短期回调；费率中性/小幅正 → 健康多头行情 |
| S2 | 高正费率 → 多头极度拥挤，诱多概率进一步放大 |
| S3 | 费率持续大幅负 → 空头过热，警惕空头回补反弹；费率中性/小幅负 → 健康空头行情 |
| S4 | 高负费率 → 空头极度拥挤，诱空概率进一步放大 |
| S5 | 高正费率叠加 → 多头集中兑现，反转风险升高 |
| S6 | 负费率叠加空头平仓 → 反弹力度更强 |
| S7 | 高负费率叠加空头平仓 → 见底反弹概率提升 |
| S8 | 高负费率加持 → 抛压释放，反弹潜力更大 |

> **定位说明（为什么费率不进 L1 粗筛）：**
> 1. 费率是 **8h 结算一次**的慢变量，而价量/OI/CVD 是分钟级高频数据，时间维度不匹配，不适合做异动触发条件。
> 2. 行情刚启动时费率往往还在中性区间，等行情走一段后才变为大幅正/负；拿费率当触发条件只能抓到行情后半段，错过启动点。
> 3. 费率极端值更多是**风险预警信号**（拥挤/过热），不是异动发生信号。

**判定增强（设计意图，⚠️ 均未实现）：**

1. 叠加资金费率拥挤度：极端正/负费率时放大诱多/诱空概率 —— 目前只有文本标签、无阈值判定（§12.1）。
2. 叠加实时清算：近期同方向大额清算进一步验证杠杆挤压叙事 —— 爆仓维无历史、未接入（§12.1）。
3. **OI 二阶信息**：OI 是加速抬升还是减速 —— 无分档（§12.1-B5）。
4. **CVD 状态切换**：CVD 由负翻正（或反之）单独标记 —— 未实现。

**置信度分级（依据 §8 标定）：**

> 标定依据（§8）：仅 P↑OI↑ 组合稳定正期望（24h 净 +5.24%、盈亏比 2.01）；P↓\* 空头侧全部负期望；1h 短窗口被成本吃光。**多头优先、空头默认降级。**
> ⚠️ **该分级尚未被线上检验通过**：线上结果闭环已连续 3 天报「阈值-行情失配」（09-21 `watch`、09-22/09-23 `high`），
> 09-23 全样本 T+24h 均值 **−5.75%**、平均超额 **−3.24%**（BTC 同期 −2.51%），边缘桶集中在 `scenario=S1`、`timeframe=15m`。
> ⇒ 本分级当前应理解为**待验证假设**，详见 §8.1。

**实际公式（`task_scan_main_pool`，与上文标定一致）**：

```text
if   direction == "up"   and oi_dir == "up":  confidence = high if regime.long_fav  else medium
elif direction == "up":                       confidence = medium                  # P↑OI↓
elif oi_dir == "up":                          confidence = high if regime.short_fav else medium  # P↓OI↑（空头侧对称通道）
else:                                         confidence = medium if regime.short_fav else low    # P↓OI↓
```

- 高：`P↑OI↑` **且** L0 环境顺风（`long_fav`）。这里的「多周期共振」在实现里只是 `level ≥ 2`，
  即**「15m 或 1h 任一周期达标」**——**既不要求 5m 参与，也不要求 1h 共振**（实测 high 里 `lv2_15m` 占多数；见 §4.2）；
  「窗口取 4h/24h」在信号表**无对应字段**，不参与分级（窗口只是回测口径，见 §8）。
- 中：`P↑OI↓`（24h 才转正）；以及 `P↑OI↑` 但 L0 不顺风时降为中。
- 低/降级：**只有 `P↓OI↓`** 在 `short_fav` 为假时降为 `low`；`P↓OI↑` 不顺风时仍是 `medium`、顺风时可直接 `high`
  （实测存在 `P↓OI↑ high`，regime 由 BTC 1h/恐慌贪婪/总市值三项共同判定）。`P↑OI↓` 恒为 `medium`，不进告警。
- ⚠️ **「空头默认降级」与「告警层只推 high」自相矛盾（已知设计冲突，登记不改代码）**：
  线上 `scan_daemon` 走的是**多空对称通道**——`direction=='down' and oi_dir=='up'` 在 `regime["short_fav"]` 为真时
  **直接给 `high`**（代码内注释的自陈理由是「原实现 down 最高只能到 medium，做空通道数学上不可达、下跌行情一封邮件都收不到」）；
  而告警层 `_load_alert_candidates` **只筛 `confidence='high'`**。两条合起来 ⇒ **空头信号确实会进告警邮件**，
  这与 §8 标定结论 2「空头侧全部负期望、空头默认降级」以及 §9「执行层只做多」**直接冲突**。
  「`short_fav` 是硬门」不能当兜底：`short_fav` 由 BTC 1h 上涨 / FGI 贪婪 / 总市值上行**任一**触发（§12.1-B25），
  单边上涨 regime 下它常为假，但一旦为真（如 09-22 横盘前的趋势段）空头 high 即进告警。见 §12.1-B19。
- 告警层只看 `confidence='high'` 且 `pool='main' OR (pool='accumulation' AND scenario='BRK')`（§6）。
- 待验证：CVD 维拆分无历史源，需 WebSocket 流式积累后补标定；样本仅 21 天，需随 OI 窗口拉长复验（§12.1-A1/A2）。

## 5. 蓄势埋伏观察池（旁路）

**触发条件（全部满足）：**

1. 价格波动小：**仅判 1h**（最近一根 1h 收盘涨跌幅 `|chg1h| < PRICE_QUIET_THR`=1.5%；实现里**不判 15m**）。
2. 成交量无明显放大：成交额 < 近 20 周期均值 1.5 倍。
3. **OI 连续多周期持续上行**：基于 `oi_cvd_snapshot` 历史序列，如近 12 个 1h 周期 OI 抬升占比 ≥70% 且累计变化 >5%。
4. （可选）同步跟踪资金费率，观察蓄势阶段多空是否提前拥挤——仅作观察，不作为进出池条件。

**增强判定（可选：同步抓取资金费率，观察蓄势阶段多空是否提前拥挤）：**

- 叠加 funding 区分吸筹/派发：
  - OI↑ + funding 接近 0 或小幅正 → 多空均衡吸筹，偏多头潜力；
  - OI↑ + funding 大幅负 → 空头持续建仓，存在逼空潜力；
  - OI↑ + funding 大幅正 → 多头拥挤，警惕派发。
- 蓄势时长记录：进入蓄势池的时间戳，超时（如 7 天）未突破自动出池。

**转主池触发：**

- 后续出现放量（量比 ≥3×）+ 价格突破（突破蓄势区间上/下沿），自动转入主池 L2 校验，标记 `pool='accumulation', scenario='BRK'`。
- BRK 的候选集 = **近 7 天内** `status='active' AND scenario='ACC'` 的币（即 ACC 落库后 7 天内一直具备转 BRK 资格）。
- **ACC 冷却与去重**：`ACC_COOLDOWN_H = 24` —— 冷却期内已有 active ACC 的币不再重复入池，返回值加
  `acc_skipped_cooldown`。若无此冷却，同一币只要仍满足 ACC 条件就会每轮（30min）插入新行
  （实测未加冷却时累计 **807 行只有 123 个不同币**，约 6.6× 重复）。
  §6 第 2 条的「同币冷却 6h」**只在主池落地**（`_in_cooldown_main`），蓄势池靠本条独立冷却。

## 6. 信号合成：去重 / 冷却 / 生命周期 / 催化层加分

1. **去重与升级**：同币 5m/15m/1h 多周期触发时，保留最高级别一条，其余挂起为佐证。
2. **冷却**：同币信号触发后冷却 N 小时，冷却期内只记录不重复预警。
   主池 `_in_cooldown_main`（`--cooldown-h` 默认 **6h**）；蓄势池 ACC `ACC_COOLDOWN_H = 24`（§5 末条）；
   告警层另有一道 **12h** 冷却（`COOLDOWN_H=12`）。
3. **生命周期**：`active → confirmed（越过 breakout_px）→ expired（超时）`。
   `scan_daemon` 任务 `expire_signals`（30min）把超期的 `active`/`confirmed` 置 `expired` 并写 `expired_at`：

   | 池 / 场景 | TTL | 依据 |
   |---|---|---|
   | `main`（S1..S8） | 24h | §8 结论 3「1h 窗口全档位期望 <0.6%（成本吃光），24h 为主窗口 → 警报语义即『24h 持有观察』」 |
   | `accumulation` BRK | 24h | 同上（BRK 是行动信号，与主池同窗口） |
   | `accumulation` ACC | 7 天 | 与 `ACC_BRK_CANDIDATE_DAYS=7` 对齐——BRK 候选集要求「近 7 天内 active 的 ACC」，提前过期会让这批币永远等不到突破判定 |

   两处消费侧均筛 **`status IN ('active','confirmed')`**：`_load_alert_candidates`、
   `phase_execute_scan_signal.load_candidates`（后者另加 `--require-confirmed`，默认关）。
   轧空池的 `confirmed` 行不参与（它记的是「已判定事件」，有独立的 `biz.squeeze_track` 状态机）——
   `expire_signals` 的 `pool` 条件天然排除。
   ⚠️ **同一枚举 `confirmed` 在库内承载两种语义（已知问题，见 §12.1-B24）**：main/BRK 的 `confirmed` = **越位升格**
   （由 `confirm_signals` 写入，可再迁 `expired`）；squeeze 的 `confirmed` = **判定事件已落库**（生产者直接写死，
   **实测 45 行 status 恒为 `confirmed`、永不迁移**，其生命周期由 `biz.squeeze_track` 的 `tracking`/`judged`/`expired` 承担）
   ⇒ **按 `status` 直接聚合会混桶**，须带 `pool` 条件。
   **入场 / 失效位**：主池与 BRK 两条生产者路径均落 `trigger_price`（= 触发周期收盘价）与
   `stop_loss_pct`（= `2×ATR(14)` / 参考价，夹 `[8%, 20%]`），渲染层与执行层均已消费。
   **`confirmed`（延续确认）**：`breakout_px` = **触发根方向侧极值**（`up→high_px`/`down→low_px`，与
   `trigger_price` 同根 ⇒ 无未来信息、且因 `high ≥ close ≥ low` 恒在入场价正确一侧）；
   `confirm_signals`（30min，错峰 480s）判定「`signal_ts` 后 **6h** 内存在一根**已收盘** 1h 条的收盘价越位」，
   升格为 `confirmed`。BRK 直接落 `confirmed`（本身就是突破事件，不走 `confirm_signals`）。
   `confirmed` 是**质量升格**（仍在可动作集合、告警加徽章），**不是入场门槛**——
   回放显示「等越位再入场」会把 24h 期望从 +1.56% 做低到 **+1.36%**（越位位离入场价中位 2.31%），
   与催化层 d3「等价格确认=追高」同源；W=6h 未越位组 24h 仍 **+1.62% 正期望**，故**不提前作废**。
   ⚠️ 该结论的样本仅 **90 条 / 3 个交易日 / 单边上涨 regime**（§12.1-A1）。
4. **催化层共振（展示层，不参与打分）**：盘面信号与以下既有数据共振时，在告警邮件中并列展示——
   - 催化剂事件（`biz.catalyst_impact` 正/负向）
   - KOL 信号（`kol_auto_trade_log` / KOL 监控）
   - 代币解锁压力（`unlock_watchlist`）
   - 链上大额转账监控（`onchain_transfer_log`）
   **实现现状（实测）**：共振**只在告警时点计算**（`task_scan_alert` 内查 catalyst/KOL，窗口 `CATALYST_DAYS=KOL_DAYS=7`），
   **不落库、不进入 `scan_signal` 的任何评分字段** —— 即「共振加分」未落地，实际是「告警邮件里带上下文」（§12.1）。

**双层告警：**

> 时序分层依据：解锁/链上转账等**领先型**信息先于盘面（可提前埋伏）；KOL/突发新闻等**滞后型**信息后于盘面（仅作确认）。因此告警分两层，盘面触发时两类信号碰撞。

| 层 | 脚本 | 机制 |
|---|---|---|
| 事件预置层（先行） | `phase_build_event_watchlist.py`（每 6h，scheduler 注册） | 未来 14 天解锁（`unlock_watchlist`）+ 近 7 天链上大额转账 ≥$10M（`onchain_transfer_log`，过滤稳定币/封装/质押噪音）→ `biz.event_watchlist` |
| 盘面触发层 | **`scan_daemon.py` 的 `task_scan_alert`**（每 5 分钟，错峰 +3min） | 新 high 置信主池信号（P↑OI↑ 标定最优组合）或蓄势 BRK high → 共振核查（事件预置=埋伏型 / 催化剂+KOL=确认型）→ 实时邮件，同币 12h 冷却，`scan_signal.alerted_at` 去重（`NEW_WINDOW_MIN=20` 分钟窗口） |

> 交付渠道：**实时邮件**；`send_scan_signal_brief.py` 不在调度内（仅保留脚本备查）。
> 盘面触发层的运行入口是 `scan_daemon.py` 内的 `task_scan_alert`（常驻进程，见 §11）。

## 7. 过滤规则与系统盲区

1. **流动性过滤（量化阈值）**：24h 成交额下限 ≥ **500 万 USDT**（实现在 `_get_24h_quote_volume()` +
   `--min-vol-usd 5000000`，对 K 线/OI/轧空三条采集与扫描统一生效）。刷量/小盘代币直接剔除。
   **尚未实现的另两项过滤**：`asset_liquidity` 表过滤——表**有数据（实测 116 行）但扫描链路零引用**
   （属「表已建、消费侧未接」，不是「无数据」）；价差（spread）过滤——**无数据源**（见 §12.1-B8）。
2. **缩量场景**：无论组合如何，只标记不预警。
3. **资金费率定位**：仅做拥挤度辅助判断，**不作为筛选触发条件**，避免过滤掉行情早期启动机会。
   （实现细节：`_lookup_funding` 走「符号候选序列」，未命中写 **NULL 不写 0**，避免"无数据"被当成"费率为零"。）
4. **数据源口径**：CVD 明确现货 or 合约口径，跨交易所归一化（`cvd_ratio`）；避免误读。
   ⚠️ **已知跨源不一致（代码注释已自陈，仅披露未修正）**：轧空的爆仓比例分子是 **CoinGlass 全交易所**爆仓额、
   分母是 **币安** 24h 成交额 → 比例**系统性偏高**，所有 `*_LIQ_RATIO` 阈值必须按此混合口径理解与标定。
5. **盲区声明**：
   - 消息面冲击、解锁事件、链上大额转账 → 由催化层共振覆盖，但该层数据本身有滞后
     （且如上 §6.4：只在告警邮件里展示，不参与打分）。
   - funding 结算点（00/08/16 UTC）前后 OI/CVD 噪声大，扫描结果标记该时段。
   - **爆仓只有「滚动窗口快照」一种粒度**（CoinGlass 套餐下限 4h，只能 5min 轮询；WS 通路 0 行），
     故"某分钟爆了多少"不可知，「实时清算验证」只能靠代理指标（见 §12.1）。
   - **采集允许缺桶**：5m 采样在停摆/部署窗口会断行，实测近 6h 覆盖率（2026-09-24）= 5m K 线 **72/72**、
     OI 实时 **62/72**、爆仓 **67/72**。因爆仓列是滚动窗口（每行自包含），**缺桶不污染指标**，消费侧取「最近一条 ≤ 容差」即可；
     但会漏掉恰落在缺口的极值（见 §10.9）。
6. **合规声明**：所有指标仅为盘面数据分析参考，不构成投资建议。

   故本表的「信号量约减少 40%」与 4.0 档期望，**只对单周期口径成立**；把线上 1h 改成 4.0 并不能复现这些效果
   （被 4.0 滤掉的「1h 涨 3~4%」样本在线上多数已被 15m 通道捕获）。同理，本表的 5m/15m 阈值**从未被标定**。
3. **窗口策略不变**：1h 窗口全档位期望 <0.6%（成本吃光），24h 为主窗口 → 警报语义为"24h 持有观察"，不做日内短打。
4. **实施**：`backtest_scan_scenarios.py --sweep` 作为复校工具，CVD 数据到位后重跑复核。

**复验机制：** `scan_oi_backfill` 每周维护 30 天 OI 窗口 + 实时 5m 采样持续积累；随窗口拉长定期重跑 `backtest_scan_scenarios.py` 复核结论稳定性，CVD 维待 WebSocket 流式落地后按同框架扩展。

## 10. 轧空行情扫描（Squeeze Scan，2026-09-21 新增）

与主池（§4）、蓄势池（§5）并列的**第三个检测池**：针对「价格快速拉升 + 空头被迫平仓」的轧空行情，
输出**行情性质判定**（落库）；邮件告警**当前处于影子模式**（只落库不发信，见 §10.8）。定位与 §1 一致——**只做数据监控与告警，不含任何下单逻辑**。

### 10.1 三阶段

| 阶段 | 内容 | 落点 |
|---|---|---|
| ① 轮询扫描 | 短窗口涨幅 + 放量初筛 → OI/爆仓/CVD 三重轧空确认 → 入跟踪队列 | `task_scan_squeeze` 阶段 1 |

> **中文名合约实测可用（2026-09-21）**：池内有 `龙虾USDT`/`哈基米USDT`/`币安人生USDT`/`我踏马来了USDT`/`牛来USDT`
> 等非 ASCII 符号，`base_symbol()` 只剥 `USDT/USDC/BUSD/USD` 后缀、不假设 ASCII，CoinGlass 侧**能对上同名 symbol**
> （实测 `龙虾USDT` 在 `liquidation_snapshot` 30 个桶全覆盖），故无需额外映射规则——但下游若要接 `core.asset` 需另做映射。

### 10.6 判定规则（`evaluate_battle`，互斥分支）

```text
big_long_liq = (long_liq_ratio is not None) and long_liq_ratio >= LONG_LIQ_RATIO_THR
d_oi_pct     = 回撤窗口 OI 变化率（%，基于 peak 时刻基准桶）
cvd_ratio    = 回撤窗口净主动成交 / 窗口成交额 ∈ [-1, 1]

# ── 前置闸门：覆盖率不足直接不判定（不落库、不发邮件）──
if 窗口 5m OI 桶覆盖率 < MIN_WINDOW_COVERAGE:  -> 留 tracking（stats.insufficient_coverage）

if   cvd_known and liq_known and cvd_ratio <= CVD_SELL_STRONG and big_long_liq:
                                                       -> short_win    # 多头踩踏
elif oi_known  and liq_known and d_oi_pct  <= OI_EXIT_PCT and not big_long_liq:
                                                       -> profit_take  # 多头止盈离场/趋势衰竭
elif oi_known  and cvd_known and liq_known and d_oi_pct > OI_EXIT_PCT \
     and cvd_ratio >= CVD_BUY_MILD and not big_long_liq:
                                                       -> long_win     # 新多承接
       （若 top_ratio_chg < 0，即大户持仓多空比下降 → 降级为 churn，疑似换手）
else:                                                 -> churn        # 震荡消化
```

> ⚠️ **「缺失 ≠ 为 0」策略（必须保留）**：三个关键输入
> `d_oi_pct` / `cvd_ratio` / `long_liq_ratio` 任一为 `None` 时：
> 1. **不得静默补 0 后照常判定**——补 0 会让"无爆仓数据"无条件满足 `not big_long_liq`，
>    从而把**缺数据误判成** `profit_take` / `long_win`；
> 2. 依赖该维度的分支一律**不成立**：`long_liq_ratio is None` 时禁止 `profit_take` / `long_win`
>    （这两条的前提是「**确知**无多单踩踏」）；`short_win` 需 `cvd` + `long_liq` 已确知；
> 3. 缺失维度写进 `metrics['data_missing']`、文案显式标注、**降级为 `churn`（无方向）**，不新增结论枚举。

四个结论与邮件标签：

| conclusion | 标签 | 含义 |
|---|---|---|
| `long_win` | 多头胜（新多承接） | 持仓维持 + 主动买占优，新多头接住了抛压 |
| `short_win` | 空头胜（多头踩踏） | 主动卖强 + 大额多头爆仓 |
| `profit_take` | 多头止盈离场（趋势衰竭） | OI 快速下降（多头离场）且无多头爆仓 |
| `churn` | 多空平局（震荡消化） | 其余（含大户多空比下降的疑似换手） |

方向判据来自**大户持仓多空比变化 `top_ratio_chg`** 与**主动买卖比 `taker_ratio`**；
**OI 只承担「持仓是维持还是离场」这一件事**，不承担方向。

> ⚠️ **方向判据的冷启动与基准口径（2026-09-24 实测）**：`biz.long_short_ratio` 现为 **2,482 行 / 35 币**
> （2026-09-21 03:55 → 2026-09-24 03:25 UTC）——因为该表**只对入队后的跟踪币采集**，币数随入队次数线性增长。
> 由此带来两个风险：
> 1. **基准桶可能取错**：入队时若只拉 `limit=20`（≈100min），而**峰值出现在入队之前**（拉升走完才被扫到），
>    `top_ratio_chg` 的基准就落在错误位置 → 方向判据失真。**已改**为入队拉 `limit=100`（≈8h，见 §10.10.7），
>    并把「基准桶 = peak 桶」写进判定口径。
> 2. **维度缺失会被降级**：拉不到多空比时 `top_ratio_chg = None`，按 §10.6 原则不阻止判定，
>    但方向证据只剩 `cvd_ratio`，结论更容易落到 `churn`（如实测 NEARUSDT 一例即 `churn`）。
>
> ⚠️ **样本量仍远不足以标定**：35 币 ≠ 35 个独立样本（同一币入队多次会重复计数），且全部集中在 72 小时内
> ⇒ §10.10 的燃料判定阈值**仍只能前向积累**（§12.1-C7）。

### 10.10 拉升期结构分解与轧空衰竭判定（**影子模式**）

§10.1 的三阶段回答「**冲高回撤后**多空谁赢了」；本节回答另一个问题——「**拉升期**这波由什么驱动、轧空的弹药还剩多少」。两者**并存**：本节挂在阶段 2 的跟踪循环里，**不替换** §10.6 的 `evaluate_battle`。

**交付形态（当前）**：`status='tracking'` 期间**每轮评估**（时效性即价值：行情还在拉升或刚见顶时就要能提示），结果落 `biz.squeeze_track.metrics['fuel']`。**影子模式、不发信**：阈值全为未标定初值、`dL`/`dS` 与买平/卖平均为代理口径（见 §10.10.8）。

**开信后的形态（待 §10.10.8 三项待办完成）**：独立早警邮件（`pool='squeeze'`、`scenario='SQZ_FUEL_<VERDICT>'`）、达标即发。⚠️ 与 §10.8 的判定邮件**解耦**，同一币可能先后收到两封 ⇒ 必须并入 §6 的跨池互斥口径（`CROSS_POOL_MUTE_MIN`），不能各发各的。

| 4 | 主动平仓量/主动开仓量 | ❌ 无 open/close 标记 | ⚠️ 代理 |
| 5 | CVD | `biz.oi_cvd_snapshot.cvd_5m_usd`（aggTrades 自算） | ✅ 真值 |
| 6 | 空头爆仓金额 | `biz.liquidation_snapshot.short_liq_usd_1h`（CoinGlass 滚动 1h 绝对值） | ✅ 真值（滚动窗口，非分段增量） |

⚠️ **第 3、4 项无真值源，且与套餐档位无关**：

- **第 3 项**：Binance 免费端点 `/futures/data/topLongShortPositionRatio` 只返回 `longAccount`/`shortAccount`（**占比**，和为 1），无绝对名义额；CoinGlass **多空比全系列在 HOBBYIST 下 404**（客户端 docstring 已实测记录），**升级套餐拿到的也只是与 Binance 同源的比值**，仍非绝对量。
- **第 4 项**：`aggTrades` 的 `isBuyerMaker` 只标记**谁是主动方**，**不区分开仓/平仓**；`takerlongshortRatio` 只给主动买/卖**量比**。HOBBYIST 可用的 `taker-buy-sell-volume/history` 最小粒度 **4h**、且同样是主动买/卖量而非开/平分类 ⇒ 对分钟级轧空判定不可用。
- ⇒ **代理口径是本方案唯一可行路径**，邮件必须显式标注（见 10.10.6）。

#### 10.10.2 两个代理口径的推导（均**无需改表**）

**① 大户多/空仓分解**：占比可由已存比值反推，故 `biz.long_short_ratio` **不必新增列**：

```text
r          = top_position_ratio            （已落库）
longShare  = r / (1 + r)                   （= Binance longAccount）
shortShare = 1 / (1 + r)                   （= Binance shortAccount）
L_proxy    = oi_usd × longShare            （大户多仓代理量）
S_proxy    = oi_usd × shortShare           （大户空仓代理量）
```

⚠️ **代理量的语义边界**：它等于「OI × 占比」，只有在**「大户占 OI 的份额在窗口内稳定」**这一假设下，其**相对变化**才可读。它**不是**大户真实绝对仓位，跨币不可比 ⇒ 只做**同币同窗口内 `dL` / `dS` 的符号与相对幅度**判断。

**② 主动平仓/开仓**：用 `OI 变化 × CVD 方向` 四象限反推（免费数据下唯一路径）：

| | CVD > 0（主动买） | CVD < 0（主动卖） |
|---|---|---|
| **OI ↓** | 买平（空头回补）✅ 轧空特征 | 卖平（多头离场） |
| **OI ↑** | 新多开仓（假轧空） | 新空开仓 |

窗口内按 5m 桶分类后取占比 `btc_share`（buy-to-close 桶数 / 有效桶数）。

#### 10.10.3 判定规则（纯函数 `crypto_research.analysis.squeeze_fuel`）

窗口固定 `W = [surge_start_ts, now]`（与 §10.6 的 `[peak_ts, now]` **不同窗口，勿混用**）。

```text
dOI = OI_last / OI_first - 1                   （窗口首尾，非回撤窗口口径）
dL  = L_proxy_last / L_proxy_first - 1
dS  = S_proxy_last / S_proxy_first - 1
dR  = r_last - r_first                         （比值变化，仅作展示）
liq_peak  = max(short_liq_usd_1h within W)
liq_decay = short_liq_usd_1h_last / liq_peak    （<1 即萎缩；liq_peak 未越阈时该量无意义）
cvd_divergence = 价格在 W 内创新高，但累计 CVD 未创新高
cvd_ratio_W    = Σ cvd_5m_usd / Σ vol_5m_usd

# ── 前置闸门（10.10.5）：不过 → mixed，记 data_missing，不出方向 ──

if   dOI >= +OI_UP_THR   and dS >= +SHORT_ADD_THR:            -> short_rebuild
elif dOI >= +OI_UP_THR   and dL >= +LONG_ADD_THR:             -> long_pump
elif dOI <= -OI_DOWN_THR and dS <= -SHORT_CUT_THR and dL >= -LONG_FLAT_THR:
        if liq_peak >= SQZ_SHORT_LIQ_RATIO_MIN and liq_decay <= LIQ_DECAY_THR \
           and cvd_divergence:                                -> sqz_fuel_exhausting
        else:                                                 -> sqz_fuel_active
else:                                                         -> mixed
```

优先级即书写顺序（**先判 OI 升**的两类，再判 OI 降的两类，`mixed` 兜底）——这样「多头主动开仓拉盘」这个假信号在结构上不可能落进 `sqz_fuel_*`。

**结论语义与邮件标签**：

| verdict | 标签 | 含义 |
|---|---|---|
| `sqz_fuel_exhausting` | **轧空弹药耗尽** | 空头持续平仓止损推高比值 + OI 净降（无新增空头对手盘）+ 空头爆仓萎缩 + CVD 背离 |
| `sqz_fuel_active` | 轧空进行中（弹药尚存） | 同为平仓驱动，但空头爆仓仍在高位 |
| `long_pump` | 多头主动开仓拉盘 | OI 升 + 大户多仓代理升、空仓不降 ⇒ **比值上升非空头平仓所致，不是轧空** |
| `short_rebuild` | 新增空头进场 | OI 升 + 大户空仓代理升 ⇒ 轧空被承接 |
| `mixed` | 结构不明 | 其余（含数据缺失降级） |

> ⚠️ 需求点名的假信号「大户大量开多、空单不动 → 比值也涨」由 `long_pump` 单列承接；这正是「**必须同时看多仓/空仓两个序列、不能只看比值**」的落地点。
>
> ⚠️ **证据强度**：`dL` / `dS` 与「买平/卖平」均来自 §10.10.2 的**代理口径**（非真值源），其成立前提（大户占 OI 份额在窗口内稳定、四象限可代表开平仓）**尚未验证**（见 §12.1-C6）。故本节结论的强度低于真值源，邮件必须按 10.10.6 显式标注口径。

#### 10.10.4 阈值常量（`analysis/squeeze_fuel.py`，**全为经验初值**）

| 常量 | 初值 | 含义 |
|---|---|---|
| `OI_UP_THR` / `OI_DOWN_THR` | +0.3% / -0.3% | 窗口 OI 净增/净减分界 |
| `SHORT_ADD_THR` / `SHORT_CUT_THR` | +3% / -3% | 大户空仓代理量增减分界 |
| `LONG_ADD_THR` / `LONG_FLAT_THR` | +3% / -1% | 大户多仓代理量「显著加仓」/「基本持平」分界 |
| `LIQ_DECAY_THR` | 0.5 | 空头爆仓衰减比上限（当前 / 窗口峰值 ≤ 此值视为萎缩） |

| `MIN_FUEL_BUCKETS` | 3 | W 内有效 5m 桶数下限 |

### 12.1 已知缺口清单（按类别与风险排序）

**A 类 · 科学有效性（决定当前置信度分级与执行结论是否成立）**

- **A4 成本模型偏乐观（双重低估）**：回测与结局结算的成本口径都只有**双边 taker 0.1%**，

- **C10 文档与代码一致性无自动校验**：本轮已清理文档中所有被取代的表述，但文档与线上代码仍靠人工同步（B4 这类口径分叉即由此产生）⇒ 新增/修改参数时须同步文档与 `scan_daemon.py` 注释。
- **C11 主池告警静默丢失（补发未做）**：`_load_alert_candidates` 的 20min 窗口在 alert 任务停摆 >20min 时会把未告警的 high 信号**永久滤掉**（`alerted_at` 恒 NULL，与「超窗作废」不可区分）。只读检测已并入停摆邮件，**补发未做**（需先定义「补发有效性」边界）。
- **C12 主池邮件剩余缺口**：regime 三阈值中两个近乎死条件（`btc_1h` / `fgi` / `cap_trend`），收紧属标定决策；BRK 通道代码可达但 0 产出（保留分支、靠 stats 观测）；历史先验（中位/胜率/n）未落库。
- **C13 「标定结论已生效」类论断需逐条回查**：凡写「已按回测标定落地」的参数（阈值、权重、冷却），都需确认 ① 改的是**线上调度的那份代码**（`scan_daemon.py`）而非长年不跑的独立脚本；② 回测口径与线上口径**是同一个量**。

## 13. 风险与局限

- 免费数据源有 30 天 OI 窗口限制，长历史依赖自积累，回测样本前期受限。
- ~~清算历史缺失，空头侧场景回测只能近似验证（可接 CoinGlass `liquidation/history` 4h+ 缓解，见 §12.1）~~ → **已接入（2026-09-24）**：CoinGlass `liquidation/history` 4h **分段增量**落 `biz.liquidation_history`（180 天，仅标定/回测），口径与滚动快照严格分离（§10.5）。
- 免费 API 限频（Binance `/futures/data/*` weight 限制），全市场高频采样需设计节流与分批；`scan_squeeze` 判定轮还会对 tracking 币（`TRACK_QUEUE_MAX=12`）按需拉价格与多空比，扩容该上限时须同步评估 weight。
- 所有信号均为概率性参考，需配合严格风控（仓位/止损/冷却）使用。

**CoinGlass 依赖项（2026-09-21 新增，本系统唯一付费数据源）：**

- **套餐粒度硬约束**：HOBBYIST 只支持 **4h 及以上**，1h 及以下返回 `code=403 + upgrade_required=STANDARD`；注意 **HTTP 状态始终 200**，业务错误只在 body 的 `code` 里，易被误判成网络故障。因此 **1h 爆仓只能靠 `liquidation/coin-list` 滚动快照高频轮询**——它是 S1 判定与轧空邮件数值的唯一来源。
- **滚动快照不可细粒度回测（已被 `liquidation_history` 补齐）**：`coin-list` 是自包含快照而非历史序列，只能自 2026-09-21 起靠轮询积累；且**严禁跨桶差分**（差值是「新滚入 − 滚出」，平稳时≈0、回落为负，截断即假 0，见 §10.6）。⇒ 原先「爆仓维历史回测能力接近于零」的结论**已作废**：4h 历史接口（`liquidation/history` / `aggregated-history`）已回填 180 天到 `biz.liquidation_history`（**分段增量**，与滚动快照不可换算，只进标定/回测）。
- **密钥单点**：`COINGLASS_API_KEY` 缺失时 `CoinGlassClient.__init__` 直接抛错，`scan_squeeze` 整轮失败。需确保告警链路能区分「密钥失效」与「无数据」两类成因。
- **口径混合（现役 = 口径 A）**：比值分子为 CoinGlass **全交易所**爆仓额、分母为 Binance **24h 成交额**，属混合口径（§10.5 已披露，未做归一）。2026-09-24 起并列给出**口径 B**（Binance 单所 **4h 分段增量** ÷ 同一 4h 墙钟区间成交额），仅用于给 A 的**偏高幅度下界**；A/B **不可换算、不可相加**，比值**不得**进同一分布/同一分位（§10.5）。
- **限频与可用性**：官方定价页 30 req/min（≈43,200 次/天）。线上 daemon 仅 `scan_liquidation` 每 300s 一次 `coin-list` = **288 次/天（0.7%）**；实测突发额度约 1.3 req/s 连续 30 次无 429，但**不可依赖**，一律按 30/min 预算。历史回填按 **24 req/min**（`min_request_gap=2.5s`，留 6 req/min 余量）：180 天 ÷ 4h = 1080 点/币，按 `limit` 上限 1000 估为 2 次/币 ⇒ 单口径 **1054 次**、双口径 **2108 次** ≈ **88 分钟**（≫ 容器实例寿命实测 ≈74.6 min ⇒ 必然跨执行窗口，故有游标表 + `--resume`）。
- 依赖 CoinGlass 服务可用性：其故障会导致轧空池全链停摆（主池 / 蓄势池不受影响）。
