## 1. 背景与问题

### 1.1 现状

盘面异动扫描系统每天发出 0~73 条实时告警（`biz.scan_signal.alerted_at IS NOT NULL`），
但**发出去之后没有任何自动化的后验统计**：

| 已有 | 缺失 |
|------|------|
| 实时告警邮件（`scan_daemon._render_alert_email`） | 告警发出后 T+1h/4h/12h/24h 的实际涨跌 |
| 信号明细落库（`biz.scan_signal` 含 `vol_ratio`/`price_chg_pct`/`oi_chg_pct`/`timeframe`/`scenario`/`context_tags`） | 按日聚合的胜率、赔率、盈亏比 |
| 邮件里「历史同场景」后验（`_scenario_priors`，12h 口径、按 `(p_dir, oi_dir)` 分组） | 行情环境（振幅/波动占比）与信号表现的**交叉表** |
| 场景回测（`backtest_scan_scenarios.py`，离线、按场景聚合、含阈值 sweep） | 每日自动跑、并对外报警的**失配探测器** |

**后果**：2026-09-22（上海日）发出 73 条告警，T+1h 胜率仅 35.6%、均净收益 −0.21%、PF 0.84（**负期望**），
直到次日人工复盘才被发现。**整整一天的负期望无人拦截。**

### 1.2 核心问题

- 今天这批告警，**期望是正还是负**？——发信时不知道，次日也不知道（无自动统计）。
- 阈值（量比 2.0、涨幅 2.0/3.0%、OI 分档）在当前行情下**是不是太松/太紧**？——无量化判据。
- 告警数从 12 条暴增到 73 条，是**行情给了更多机会**，还是**门槛被低波动变相放松**？——无法区分。
- 中长窗口（T+24h）胜率 56.4% 看起来不错，但**多少来自 BTC beta、多少来自信号 alpha**？——未拆分。
  （同期 BTC 同方向 T+24h 胜率 100%，即中长窗口的「正」几乎不构成信号质量证据。）

### 1.3 目标

建立「**告警 → 多窗口结局 → 每日胜率/赔率 → 阈值-行情失配判定**」的自动闭环：

```
scan_daemon 告警(alerted_at)
      │
      ▼
① 结局结算：T+1h/4h/12h/24h 方向对齐净收益 + BTC beta 对照
      │
      ▼
② 日报聚合：当日胜率/赔率/PF/盈亏平衡胜率 + 行情环境指标
      │
      ▼
③ 失配判定：告警数异动 × 胜率跌破盈亏平衡线 × 边缘桶占比
      │
      ▼
④ 每日邮件（当日值 + 近 3 日滚动 + 与阈值常量的对照）
```

**一句话**：让「阈值是否匹配当前行情」从**事后人工复盘**变成**每日自动报警的数字**。

### 2.4 ⚠️ 性能约束（必须遵守）

`biz.asset_klines` 虽有 `(symbol, interval, open_time DESC)` 索引，但**整表拉取会因跨区链路超时**
（实测 240s+ 未返回）。因此：

- 取价必须**在 SQL 侧用 `LATERAL` / 相关子查询算好**，只回传结果行（参照 `_scenario_priors` L1352-1374 的写法）；
- **禁止**把 K 线拉到 Python 再算（`backtest_scan_scenarios.load_klines` 那种全量拉取只适合离线回测，不适合每日任务）。

**取价周期的数据覆盖**（决定 §4.4 的口径选择）：

| 周期 | 覆盖 | 用途 |
|------|------|------|
| `5m` | 全部告警样本（实测 195/195 命中） | **主口径**：基线取 `alerted_at` 前最后一根 5m 棒收盘价 ⇒ 入场价≈告警时刻价 |
| `1h` | 全量 | **兜底**：`alerted_at` 前 2h 内无 5m 数据时退回；同时用于行情环境指标（振幅/波动占比） |

> 5m 命中率之所以是 100%，是因为扫描器本身就在消费 5m 采样；但仍保留 1h 兜底，
> 以便 `asset_klines` 5m 回填断档时不至于整行 `no_data`。所选周期落库在 `kline_iv` 列，**可审计**。

### 3.2 三个时间维度

| 环节 | 频率 | 内容 |
|------|------|------|
| 结局结算 | 每小时（cron `5 * * * *`） | 把已到期窗口的 `outcome_state` 推进一级，只处理 `outcome_state <> 'resolved'` |
| 日报聚合 | 每日 08:10（Asia/Shanghai） | 聚合昨日（及近 3 日滚动）→ 落 `scan_edge_daily` / `scan_edge_bucket` |

### 3.3 为什么不改造现有早报

`send_daily_brief.py`（66KB）承担大盘/资金流/催化剂等 10 个模块的渲染，职责已饱和；
告警后验是**另一个数据域**（信号质量，不是市场状态），且需要**独立的历史回填与趋势表**。
故采用**独立脚本 + 独立表 + 独立邮件**，只在 `build_daily_brief.py` 里加一行「告警质量摘要」（读 `scan_edge_daily` 最新一行），
避免两套逻辑互相污染。详见 §9。

## 4. 详细设计

### 4.1 表 1：`biz.scan_signal_outcome`（逐信号多窗口结局）

```sql
CREATE TABLE IF NOT EXISTS biz.scan_signal_outcome (
    signal_id       BIGINT PRIMARY KEY REFERENCES biz.scan_signal(id) ON DELETE CASCADE,
    symbol          TEXT NOT NULL,
    pool            TEXT,
    scenario        TEXT,
    timeframe       TEXT,
    p_dir           TEXT,                          -- up / down（方向对齐基准）
    alerted_at      TIMESTAMPTZ,                   -- 告警时刻（= 决策起点）
    kline_iv        TEXT,                          -- 取价周期：5m（主）/ 1h（兜底）——口径可审计
    base_time       TIMESTAMPTZ NOT NULL,          -- 基线 K 线 open_time（<= alerted_at 的最后一根该周期棒）
    base_px         NUMERIC(24,8),                 -- 基线收盘价（≈ 告警时刻价）

    -- 方向对齐净收益（%，已扣 0.1% 双边费）
    aligned_ret_1h  NUMERIC(10,4),
    aligned_ret_4h  NUMERIC(10,4),
    aligned_ret_12h NUMERIC(10,4),
    aligned_ret_24h NUMERIC(10,4),

    -- BTC 同方向同窗口收益（beta 对照，%）
    btc_ret_1h      NUMERIC(10,4),
    btc_ret_4h      NUMERIC(10,4),
    btc_ret_12h     NUMERIC(10,4),
    btc_ret_24h     NUMERIC(10,4),

    -- 超额（= aligned_ret - btc_ret，正=信号有 alpha）
    excess_1h       NUMERIC(10,4),
    excess_4h       NUMERIC(10,4),
    excess_12h      NUMERIC(10,4),
    excess_24h      NUMERIC(10,4),

    -- 途中风险（在 1h 高低价上取，方向对齐，负值=不利）
    mae_24h         NUMERIC(10,4),                 -- 24h 内最大不利偏移（%，夹到 <=0）
    mfe_24h         NUMERIC(10,4),                 -- 24h 内最大有利偏移（%）
    sl_hit_24h      BOOLEAN,                       -- 是否触及 stop_loss_pct（该列为 NULL 时本列 NULL）
    sl_pct_snapshot NUMERIC(8,2),                  -- 冗余快照（该列是 09-21 后才有）

    -- 结算状态
    outcome_state   TEXT NOT NULL DEFAULT 'pending',
                    -- pending(未到 24h) / resolved(已结算 24h) / no_data(无 K 线或无 p_dir)
    last_window     SMALLINT NOT NULL DEFAULT 0,   -- 已结算的最大窗口小时数（0/1/4/12/24）
    bars_n          SMALLINT,                      -- 24h 窗口内可用该周期 K 线数
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX IF NOT EXISTS idx_scan_outcome_state
    ON biz.scan_signal_outcome (outcome_state, alerted_at DESC);
CREATE INDEX IF NOT EXISTS idx_scan_outcome_alerted
    ON biz.scan_signal_outcome (alerted_at DESC);

COMMENT ON TABLE biz.scan_signal_outcome IS '盘面告警逐信号多窗口结局（方向对齐净收益 + BTC beta 对照），供胜率赔率日报消费';
```

**结算规则**

- **取价周期**：`alerted_at` 前 2h 内有 5m K 线 → `kline_iv='5m'`，否则 `'1h'`。
  **同一行的 4 个窗口与 BTC 对照共用同一周期**，保证间隔一致、可比。
- 基线：`base_time` = `alerted_at` 时刻**最后一根**该周期 K 线的 `open_time`，`base_px` = 其 `close_px`。
- 终点：`alerted_at + N hours` 时刻**最后一根**该周期 K 线的 `close_px`。
- `net = (px1 − px0)/px0 × 100 × (+1 if p_dir='up' else −1) − 0.1`。
  **扣费在对齐之后**（与 `backtest_scan_scenarios.scan_symbol` 同口径）。写成 `(raw − 0.1)` 再取反会让做空信号赚到手续费。
- 只对 `p_dir IN ('up','down')` 计算；`p_dir` 为空（如 `BRK` 部分行）或无基线 K 线 → `outcome_state='no_data'`。
- `outcome_state='resolved'` ⇔ `last_window >= 24`；未满 24h 的行 `pending`，**只写已到期窗口**。
- **未到期窗口写 NULL，绝不混入日报统计**（`last_window` 闸门，同 `catalyst_outcome` 的教训）。

> ⚠️ **为什么不用「1h 已收盘棒」**：1h 棒 `open_time <= alerted_at` 的 `close_px` 是**该小时收盘**价，
> 即告警后最多 60 分钟的价。对突破类信号等于「晚进场一小时」，且终点会落在告警后 1.5~2h 而非恰好 1h ——
> 实测把 09-17 的 T+1h 胜率从 47.1% 压到 29.4%（系统性负偏，不可交易）。
> 改用 5m 后 09-17/09-18/09-22 与独立复算逐日吻合（47.1% / 56.2% / 35.6%）。

## 5. 计算公式

### 5.1 基础量（逐信号，窗口 w ∈ {1,4,12,24}h）

```
raw_w       = (px_w - px_0) / px_0 × 100             # 原始涨跌 %
aligned_w   = raw_w × (+1 if p_dir='up' else -1)      # 方向对齐
net_w       = aligned_w - COST,  COST = 0.1           # 扣双边费（与 backtest 同口径）
btc_net_w   = btc_raw_w × (same dir as p_dir) - COST  # BTC 同方向同窗口
excess_w    = net_w - btc_net_w                       # 超额（alpha）
```

> ⚠️ **扣费的顺序不能颠倒**。必须先按 `p_dir` 对齐毛收益，再减 `COST`：
> `aligned = raw × dir` 然后 `net = aligned − COST`。
> 若写成 `net = (raw − COST) × dir`，做空信号会**赚到 0.1% 手续费**（净收益虚增 0.2pp），
> 在多空混杂的样本里足以把接近 0 的期望判成正 —— 且不会报任何错。该口径有专门单测锁定。
> 参考实现：`backtest_scan_scenarios.scan_symbol`（`ret = ret_long if direction=='up' else -ret_long`，随后 `ret - cost`）。

### 5.2 核心指标（按日/按桶聚合）

| 指标 | 公式 | 说明 |
|------|------|------|
| 胜率 `win_w` | `count(net_w > 0) / n` | 平盘（=0）计入负 |
| 平均盈利 `avg_win_w` | `mean(net_w \| net_w > 0)` | |
| 平均亏损 `avg_loss_w` | `mean(net_w \| net_w < 0)`（负值） | |
| **赔率 `odds_w`** | `avg_win_w / abs(avg_loss_w)` | **平均盈利 ÷ 平均亏损**；一侧为空记 NULL（**不得记 ∞**） |
| **盈亏平衡胜率 `be_w`** | `1 / (1 + odds_w)` | **胜率低于它 ⇒ 期望为负**（判定主指标） |
| **盈亏比 `pf_w`** | `sum(net_w \| >0) / abs(sum(net_w \| <0))` | 总盈利 ÷ 总亏损 |
| 均收益 `avg_w` | `mean(net_w)` | 期望值 |
| 期望判定 | `win_w < be_w` ⇔ `avg_w < 0` | 两者等价，报告中同时展示以互相校验 |

> **为何同时要赔率和 PF**：赔率是「单笔幅度比」，PF 是「总额比」，两者在样本量差异大时给出不同信号。
> 实测 09-22 T+1h：赔率 1.51、PF 0.84 —— **胜率 35.6% 远低于平衡线 39.8%，且总额亏损大于盈利**；
> 若只看赔率（>1）会误判为「赔率不错、只是运气差」。**必须三个一起看**：胜率（频次）/ 赔率（幅度）/ PF（总额）。

### 5.3 样本量与置信

日样本 n=16~73，**单日胜率的标准误约 ±6~12 个百分点**，因此：

- 报告**同时给出**「当日值」与「近 3 日滚动值」；
- **失配判定只用滚动值**（`roll3_*`），当日值仅作展示与趋势参考；
- `roll3_win_1h < roll3_be_1h` 连续满足 → 才升级为 `severity='high'`。

### 5.4 行情环境分类 `regime_label`

| 标签 | 判据（当日 BTC，按上海日切 1h 棒） |
|------|-----------------------------------|
| `trend`（趋势） | `btc_amp_pct >= 4.0` **且** `btc_1h_gt05_ratio >= 0.35` |
| `range`（横盘低波动） | `btc_amp_pct < 3.0` **且** `btc_1h_gt05_ratio < 0.20` |
| `mixed` | 其余 |

> **该维度是当前 `_build_regime` 缺失的「无趋势/低波动」判据**（现有只判 BTC 1h 方向、FGI、市值趋势，横盘时三者全不触发）。

**实测 7 日分布（⚠️ 未经验证，仅作展示与分桶维度）**

| 日期 | 振幅 | >0.5% 占比 | 判定 | T+1h | T+4h |
|------|-----:|-----------:|------|------|------|
| 09-17 | 2.42% | 10.5% | range | 47.1% / −0.34% | 35.3% / −1.28% |
| 09-18 | 6.49% | 16.7% | **mixed** | 56.2% / +1.38% | 62.5% / +1.99% |
| 09-21 | 7.21% | 29.2% | **mixed** | 38.9% / −0.07% | 58.3% / +1.56% |
| 09-22 | 2.71% | 16.7% | range | 35.6% / −0.21% | 41.1% / −0.33% |
| 09-23 | 1.01% | 0.0% | range | 41.3% / −0.25% | 55.6% / −0.29% |

**必须诚实记录的三个事实**（否则会把该维度当已验证参数用）：

1. **7 日内无一天判为 `trend`**：09-18/09-21 振幅虽达 6.49%/7.21%，但「小时 |涨跌|>0.5% 占比」
   只有 16.7%/29.2%（涨幅集中在少数小时），未达 0.35 阈值 ⇒ 判 `mixed`。`trend` 分支当前是**死分支**。
2. **`range` 内部并不齐**：同为 `range`，09-17 的 T+1h 是 47.1%（5 日最佳），09-22 只有 35.6%。
3. 因此 **regime 与告警质量的关系尚无统计支撑**（每格样本 1~5 天）。按项目惯例，该维度属**锚定参数**，
   需预留 ≥30 天、多 regime、日级 t≥2 的样本外期验证后才可写入拦截逻辑；
   **在此之前它只用于报告展示与分桶，规则 B 的命中不得作为「已知因果」解读**。

### 5.5 失配判定规则

| ID | 规则 | 含义 |
|----|------|------|
| **A** | `roll3_alerts_avg > 前 7 日均值 × 1.5` 且 `roll3_win_1h < roll3_be_1h` | **阈值-行情失配**：告警量激增 + 期望转负（09-22/09-23 的典型形态） |
| **B** | `regime_label='range'` 且 `alerts_n >= 前 7 日均值` 且 `roll3_pf_1h < 1.0` | **横盘市信号天然失效**：应在横盘时抑制/收紧（⚠️ regime 未验证，见 §5.4） |
| **C** | 存在桶满足 `n >= 5` 且 `win_1h < be_1h` 且 `share >= 0.2` | **边缘桶**：给出「该收紧哪个阈值」的具体坐标 |
| **D** | `timeframe='15m'` 桶连续 2 日 `win_1h < be_1h` | **周期退化**：建议横盘期抑制 15m 通道 |
| **E** | `btc_win_24h - win_24h < 0.10` 且 `excess_avg_24h < 0.5%` | **纯 beta 贡献**：中长窗口胜率不构成信号质量证据 |

`severity`：命中 A 或 B → `high`；仅命中 C/D/E → `watch`；均未命中 → `ok`；`sample_ready=FALSE` → 直接 `ok`（只展示不判定）。

**实跑结果（7 日）**

| 日期 | severity | 命中规则 | 3 日滚动 T+1h 胜率 / 平衡线 / PF |
|------|----------|----------|----------------------------------|
| 09-17 | WATCH | C | 47.1% / 53.0% / 0.79 |
| 09-18 | OK | — | 51.7% / 37.7% / 2.61 |
| 09-19 | OK | —（0 条告警） | 51.7% / 37.8% / 2.61 |
| 09-20 | OK | —（0 条告警） | 56.2% / 22.5% / 4.42 |
| 09-21 | WATCH | C | 38.9% / 40.6% / 0.93 |
| 09-22 | **HIGH** | A / B / C | 37.3% / 40.2% / 0.88 |
| 09-23 | **HIGH** | A / B / C / D | 38.6% / 42.6% / 0.85 |

> 规则 A 在 09-22（告警 73 条 = 前 7 日均值 13.8 的 5.3 倍）与 09-23（53 条 = 23.7 的 2.2 倍）均命中，
> 说明「告警量异动 + 滚动期望转负」这一组合**能自动复现**人工复盘发现的失配日。
> 09-21 只判 WATCH（告警 36 条 = 8.2 的 4.4 倍，但滚动胜率 38.9% 与平衡线 40.6% 仅差 1.7pt），
> 属**阈值边缘**，符合「宁可漏报不误报」的设计取向。

`conclusion` 示例（09-22 实跑）：
`"阈值-行情失配（规则 A/B/C）；行情横盘低波动（BTC 振幅 2.71%、小时|涨跌|>0.5% 占比 16.7%）；告警 73 条 = 前 7 日均值 13.8 的 5.3 倍；3 日滚动 T+1h 胜率 37.3% < 盈亏平衡线 40.2%、PF 0.88；边缘桶 scenario=S1(胜率 35.6%/占 80.8%)、pool=main(胜率 35.6%/占 80.8%)、timeframe=15m(胜率 34.3%/占 47.9%)。"`

> ⚠️ 本日报**只输出判定，不改任何阈值、不拦截任何告警**（与轧空影子模式同原则）。
> `severity=high` 的含义是「该人来看一眼并决定是否调阈值」，不是「系统已自动收紧」。

## 8. 风险与注意

| 风险 | 说明 | 对策 |
|------|------|------|
| **取价口径漂移** | 用「1h 已收盘棒」会把 T+1h 胜率系统性压低 17.7pt（09-17 实测 47.1%→29.4%），且入场价不可交易 | 固定 5m 为主 / 1h 兜底，所选周期落 `kline_iv` 列可审计；探针断言「存在 5m 取价行」 |
| **扣费符号错** | `(raw − cost)` 再按方向取反 ⇒ 做空赚手续费、空头虚增 0.2pp，且不报错 | 扣费固定在对齐之后；探针前两条专门锁定该边界 |
| **样本量小** | 日 n=17~79，单日胜率标准误 ±6~12pt | 判定只用近 3 日滚动；`matured_n < 10` 时 `sample_ready=FALSE` 只展示不报警 |
| **选择偏置** | 样本限 `alerted_at IS NOT NULL`，而告警本身依赖 regime 顺风（`_scenario_priors` docstring 已自述「正期望是该口径的必然结果」） | 报告中显式标注「仅含已告警样本，非无偏基准」；beta 对照行强制并列 |
| **beta 混淆** | T+24h 信号胜率 56.4%，而同期 BTC 同方向胜率 100% ⇒ 中长窗口的「正」几乎不是信号质量证据 | 强制输出 `btc_win_24h` / `excess_avg_24h`，规则 E 拦截「纯 beta」误判 |
| **regime 判据未验证** | 7 日内 `trend` 分支零命中；同为 `range` 的 09-17（47.1%）与 09-22（35.6%）差异极大 | 该维度只用于展示与分桶；规则 B 命中不得当作因果（§5.4），需 ≥30 天样本外验证 |
| **`stop_loss_pct` 覆盖不全** | 该列 2026-09-21 08:40 UTC 才落库，之前样本恒 NULL | `sl_hit_24h` 留 NULL；不参与胜率口径，仅作旁证 |
| **时区** | `report_date` 必须固定 Asia/Shanghai，而结算用 UTC | 表内只存 DATE（已按上海日切分）；SQL 用 `AT TIME ZONE 'Asia/Shanghai'` 切日 |
| **未到期行混入** | 会系统性高估胜率（未到期样本天然偏「还没跌」） | `last_window` 闸门 + `pending_n` 显式展示（同 `catalyst_outcome` 教训） |
| **跨区链路超时** | `asset_klines` 整表拉取 240s+ 不返回 | 取价一律 `LATERAL` 子查询在 SQL 侧算好（§4.4） |
| **「报警」变「噪声」** | 天天 `high` 会脱敏（当前 7 日中已 2 天 HIGH） | 规则 A/B 用滚动值 + 前 7 日均值倍数；同一规则连续 3 日命中才升级 `high`（P2 再评估） |
| **阈值改动** | 本方案**不改任何阈值常量** | 只输出「哪个桶负期望、占多少」，阈值调整仍走人工决策（与轧空影子模式同原则） |
