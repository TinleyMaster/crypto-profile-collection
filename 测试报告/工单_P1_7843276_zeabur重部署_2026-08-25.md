# 工单 · P1 · 7843276 行情分区可见性 · zeabur 强制重部署

> 优先级：P1·高
> 问题类型：Docker 层缓存导致代码未更新（zeabur 显示已部署，但容器内运行的仍是旧代码）
> 影响面：所有资产研究页的行情表现分区
> 现状：BTC 仅 3 天、VOOx/RCATx 0 天、correlation common_days=2
> 目标：BTC ≥ 90 天、correlation ≥ 30 天、长尾资产至少有历史回填

---

## 一、根因

代码层修复已合入 main（commit `7843276` — `fix: 行情读取层统一合并 cmc + cmc_historical 双分区`），
zeabur 控制台也显示部署了该 commit，但**容器内实际运行的仍是旧代码**。

### 实证

| 验证项 | 预期（新代码） | 实际（线上 API） | 结论 |
|---|---|---|---|
| BTC 行情天数（days=90） | ≥ 90 天（cmc + cmc_historical 合并） | 3 天（仅 cmc 快照） | 旧代码行为 |
| RCATx 行情天数 | ≥ 10 天（cmc_historical 回填） | 0 天 | 旧代码行为 |
| prod DB 直接查 BTC cmc_historical | 91 天（2026-05-26 ~ 2026-08-24） | — | 数据存在，排除数据问题 |

**结论**：线上 API 行为与"只查 `source_code = 'cmc'` 单分区"的旧逻辑完全吻合，说明 `db_stats.py` 未更新。

### 最可能原因：Docker 层缓存

Dockerfile 中 `COPY 05_代码与脚本/workbench/*.py /app/` 这一层如果命中缓存，
即使 git 拉了新代码，容器内的 Python 文件也不会被替换。

zeabur 的"重新部署"默认可能复用镜像层缓存，导致代码文件未更新。

---

## 二、修复动作

### 方案 A：zeabur 控制台强制重新部署（推荐，最快）

1. 进入 zeabur 控制台 → 项目 → `crypto-profile-collection` 服务
2. 找到「重新部署」或「Redeploy」按钮
3. **关键**：勾选「不使用缓存」或「Clear cache」选项（如有），强制全量重建
4. 等待部署完成（约 2~5 分钟）

> 如果 zeabur 没有"清除缓存"选项，见方案 B。

### 方案 B：进入容器手动更新 + 重启

如果强制重部署不可用，直接在容器内替换文件并重启：

```bash
# 1. 进入容器（zeabur 控制台 → 服务 → 终端/Shell）
# 或 zeabur CLI：
zeabur service shell

# 2. 确认当前代码版本
cd /app
grep -c "cmc_historical" workbench/db_stats.py
# 旧代码：0；新代码：≥ 10

# 3. 拉取最新代码
git -C /app pull origin main 2>/dev/null || true
# 如果 /app 不是 git 仓库（Dockerfile 只 COPY 文件），则跳过，用方案 A

# 4. 验证文件已更新
grep -c "cmc_historical" workbench/db_stats.py
# 期望 ≥ 10

# 5. 重启 gunicorn（supervisord 管理）
supervisorctl restart gunicorn
# 或
kill -HUP $(cat /tmp/gunicorn.pid 2>/dev/null) 2>/dev/null || pkill -HUP gunicorn
```

## 四、预防措施

为避免后续部署再次出现缓存问题，建议：

1. **Dockerfile 优化**：在 COPY 代码前加一个 `ARG` 或 `LABEL` 使缓存失效，例如：
   ```dockerfile
   ARG BUILD_TIMESTAMP=unknown
   LABEL build.timestamp=$BUILD_TIMESTAMP
   COPY 05_代码与脚本/workbench/*.py /app/
   ```
   部署时传入不同的 BUILD_TIMESTAMP 即可强制该层及之后所有层重建。

2. **健康检查端点**：新增 `/api/version` 端点返回 git commit hash，部署后可快速验证代码版本。
