# 解锁规则表设计与自动推算方案

## 一、目标

这套方案解决的是：

- DefiLlama Unlock 接口不可稳定使用时，如何自己维护解锁数据
- 如何把“官方已验证解锁”和“根据白皮书推算的解锁”分开存
- 如何让 n8n / SQL 自动生成未来解锁事件

核心原则：

- **官方事实优先**
- **推算结果必须显式标记为 estimated**
- **规则表和事件表分离**

## 二、推荐的数据结构

### 1）解锁规则表：`coin_unlock_rules`

用途：

- 存“怎么解锁”
- 不存每一期具体事件

建议建表：

```sql
CREATE TABLE coin_unlock_rules (
    id SERIAL PRIMARY KEY,
    coin_symbol VARCHAR(32) NOT NULL,
    bucket_name VARCHAR(64) NOT NULL,
    beneficiary_type VARCHAR(64),
    source_type VARCHAR(32) NOT NULL DEFAULT 'estimated',
    confidence_level VARCHAR(16) NOT NULL DEFAULT 'medium',
    source_url TEXT,
    source_note TEXT,

    total_supply NUMERIC,
    allocation_ratio NUMERIC,
    allocation_amount NUMERIC,

    tge_date DATE,
    tge_unlock_ratio NUMERIC DEFAULT 0,
    tge_unlock_amount NUMERIC,

    cliff_months INT DEFAULT 0,
    vesting_months INT DEFAULT 0,
    unlock_frequency VARCHAR(16) DEFAULT 'monthly',
    unlock_method VARCHAR(16) DEFAULT 'linear',

    start_date DATE,
    end_date DATE,

    is_active BOOLEAN DEFAULT TRUE,
    created_at TIMESTAMP DEFAULT NOW(),
    updated_at TIMESTAMP DEFAULT NOW()
);
```

### 2）解锁事件表：`coin_unlock_events`

你现有表建议补几个字段，不然无法区分“官方事实”和“推算值”。

建议新增：

```sql
ALTER TABLE coin_unlock_events
ADD COLUMN source_type VARCHAR(32) DEFAULT 'official',
ADD COLUMN confidence_level VARCHAR(16) DEFAULT 'high',
ADD COLUMN source_url TEXT,
ADD COLUMN calc_method VARCHAR(64),
ADD COLUMN assumption_note TEXT,
ADD COLUMN rule_id INT;
```

建议字段含义：

- `source_type`
  - `official`
  - `estimated`
- `confidence_level`
  - `high`
  - `medium`
  - `low`
- `calc_method`
  - `manual`
  - `whitepaper_linear_vesting`
  - `research_inferred`

## 三、规则表怎么填

### 示例：团队解锁

假设白皮书写的是：

```text
总量 10 亿
团队 20%
TGE 解锁 0%
12 个月 cliff
之后 24 个月线性释放
```

那规则表填法可以是：

```text
coin_symbol       = BANK
bucket_name       = team
beneficiary_type  = team
source_type       = estimated
confidence_level  = medium
total_supply      = 1000000000
allocation_ratio  = 0.20
allocation_amount = 200000000
tge_date          = 2025-04-01
tge_unlock_ratio  = 0
tge_unlock_amount = 0
cliff_months      = 12
vesting_months    = 24
unlock_frequency  = monthly
unlock_method     = linear
start_date        = 2026-04-01
end_date          = 2028-03-31
```

## 四、从规则表推算事件表的逻辑

## 逻辑拆解

一条规则通常拆成两段：

1. TGE 当日解锁
2. cliff 结束后的线性 / 分段释放

### 推算公式

#### 1）分配总量

如果 `allocation_amount` 为空，则：

```text
allocation_amount = total_supply * allocation_ratio
```

#### 2）TGE 解锁量

如果 `tge_unlock_amount` 为空，则：

```text
tge_unlock_amount = allocation_amount * tge_unlock_ratio
```

#### 3）剩余待解锁量

```text
remaining_locked = allocation_amount - tge_unlock_amount
```

#### 4）每期线性释放量

月频线性时：

```text
period_unlock_amount = remaining_locked / vesting_months
```

## 五、推荐的 SQL 生成思路

如果你以后想直接在 PostgreSQL 里批量生成未来月度事件，推荐用：

- `generate_series`
- `interval '1 month'`

示意 SQL：

```sql
WITH base AS (
    SELECT
        id AS rule_id,
        coin_symbol,
        bucket_name,
        beneficiary_type,
        source_type,
        confidence_level,
        source_url,
        COALESCE(
            allocation_amount,
            total_supply * allocation_ratio
        ) AS final_allocation_amount,
        tge_date,
        COALESCE(
            tge_unlock_amount,
            COALESCE(allocation_amount, total_supply * allocation_ratio) * COALESCE(tge_unlock_ratio, 0)
        ) AS final_tge_unlock_amount,
        cliff_months,
        vesting_months,
        unlock_frequency,
        unlock_method
    FROM coin_unlock_rules
    WHERE is_active = TRUE
),
schedule AS (
    SELECT
        b.*,
        (b.final_allocation_amount - b.final_tge_unlock_amount) AS remaining_locked,
        (b.tge_date + (b.cliff_months || ' month')::interval)::date AS linear_start_date
    FROM base b
)
SELECT
    coin_symbol,
    (linear_start_date + (gs.n || ' month')::interval)::date AS unlock_date,
    bucket_name AS unlock_type,
    remaining_locked / NULLIF(vesting_months, 0) AS unlock_amount,
    NULL::numeric AS unlock_ratio_total,
    NULL::numeric AS unlock_ratio_circulating,
    NULL::numeric AS unlock_value_usd,
    beneficiary_type,
    GREATEST(
        remaining_locked - ((gs.n + 1) * (remaining_locked / NULLIF(vesting_months, 0))),
        0
    ) AS remaining_locked,
    'medium' AS risk_level,
    'whitepaper_estimated' AS data_source,
    source_type,
    confidence_level,
    source_url,
    'whitepaper_linear_vesting' AS calc_method,
    'Auto generated from coin_unlock_rules' AS assumption_note,
    rule_id
FROM schedule
CROSS JOIN LATERAL generate_series(0, vesting_months - 1) AS gs(n);
```

上面这段不是最终生产 SQL，但已经够你搭 MVP。

## 六、n8n 里怎么搭

推荐单独做一个子工作流：

**子工作流：解锁规则推算 → coin_unlock_events**

### 节点顺序

1. `When executed by another workflow`
2. `Postgres - 读取 coin_unlock_rules`
3. `Loop Over Items`
4. `Code - 生成该规则对应的解锁事件数组`
5. `Split Out`
6. `Postgres - INSERT INTO coin_unlock_events`

### Code 节点逻辑

每条规则做这些事：

1. 算 `allocation_amount`
2. 算 `tge_unlock_amount`
3. 算 `remaining_locked`
4. 根据 `cliff_months + vesting_months` 生成每月事件
5. 输出数组给下游批量写入

### 什么时候适合用 n8n，什么时候适合用 SQL

- 币种少、规则还在频繁改：先用 `n8n Code`
- 规则稳定、币种开始变多：再迁移到 `SQL generate_series`

## 七、推荐的写入策略

### 1）官方事件

如果你手工从项目公告、TGE 文档、基金会公告确认了某个解锁事件：

- `source_type = official`
- `confidence_level = high`
- `calc_method = manual`

### 2）推算事件

如果是根据白皮书规则推出来的：

- `source_type = estimated`
- `confidence_level = medium`
- `calc_method = whitepaper_linear_vesting`

这样后续你做可视化、预警、投研结论时，不会把“推算值”误当成“已验证事实”。

## 八、适合你的最小 MVP

如果你现在只做最小可用版，我建议先只支持这 3 类规则：

1. `TGE 一次性解锁`
2. `cliff + monthly linear`
3. `无 cliff + monthly linear`

先不要碰这些复杂情况：

- milestone vesting
- 非线性分段
- DAO 治理投票后动态调整
- 多次重置起算时间

因为这些复杂规则很容易把自动化做脏。

## 九、我建议你怎么落地

最稳顺序：

1. 先建 `coin_unlock_rules`
2. 先手动录 1 个币种的 2-3 条规则
3. 用 n8n Code 节点生成 `estimated unlock events`
4. 写入 `coin_unlock_events`
5. 跑通后再考虑批量化

## 十、一句话结论

你完全可以不用外部 Unlock API，改成：

**白皮书 / 官方公告 / 研报交叉验证 -> 录入解锁规则表 -> 自动推算事件表**

这条路线的优点是：

- 可控
- 可解释
- 更适合白名单研究体系

缺点是：

- 需要你先做人工规则录入
- 必须严格区分 `official` 和 `estimated`
