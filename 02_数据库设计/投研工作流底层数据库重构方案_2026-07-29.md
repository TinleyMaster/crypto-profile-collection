# 投研工作流底层数据库重构方案（2026-07-29）

## 1. 这次为什么要重构

你现在的系统已经把“抓取 -> 入库 -> 上传知识库”跑通了，但数据库底层设计还停留在第一阶段，核心问题有 4 个：

1. `coin_basic` 承担了过多职责：既是资产主表，又是跨源映射表，还是文档入口表。
2. `cmc_id / coingecko_id / defillama_slug` 被塞进同一行，但这 3 个源的语义并不对齐。
3. API 原始返回没有完整沉淀，导致很多字段没有被利用，也很难回放和补算。
4. `DefiLlama` 更偏 **protocol** 语义，`CMC / CoinGecko` 更偏 **asset/token** 语义，强行塞进单表会越来越别扭。

所以这次重构的目标不是“继续给 `coin_basic` 加字段”，而是把数据库改成：

- **源数据先分开沉淀**
- **标准化实体再统一映射**
- **`coin_basic` 退化为消费层映射表**
- **文档、行情、协议指标都挂在标准实体上**

---

## 2. 先说结论：新的底层分 5 层

推荐在 PostgreSQL 里直接分 schema：

1. `sys`：系统配置与采集运行日志
2. `raw`：API 原始响应层
3. `src_cmc` / `src_cg` / `src_llama`：各来源解析层
4. `core`：标准实体层（asset / protocol / chain / mapping）
5. `biz`：业务消费层（`coin_basic`、文档、时序指标、候选池、跟踪池）

这 5 层里，**真正的主键不再是 `cmc_id`**，而是内部统一主键：

- `core.asset.asset_id`
- `core.protocol.protocol_id`
- `core.chain.chain_id`

也就是说，`cmc_id` 以后只是一个 **source id**，不是全系统根主键。

## 3. 设计原则

### 3.1 原始响应必须先落地

所有 API 请求先写入 `raw.api_response`，再解析到来源表。  
这样有 3 个好处：

- 字段新增时可以回放旧数据，不需要重新抓全量
- 采集失败时可以追溯到具体请求和响应
- 后面要加新解析逻辑，不会被旧库结构卡死

### 3.2 一个来源一套表，不跨源互相覆盖

例如：

- `src_cmc.cmc_asset_info`
- `src_cg.cg_coin_detail`
- `src_llama.llama_protocol`

这些表都只保存“这个源自己说了什么”，不做跨源融合。

### 3.3 资产、协议、链分开建模

至少分 3 类实体：

- `asset`：可交易币种 / token / coin
- `protocol`：协议 / 项目 / dApp / 基础设施
- `chain`：公链 / L2 / sidechain

**关键点：不要再把 `defillama_slug` 直接视为 `coin_basic` 的天然字段。**  
因为 `DefiLlama` 很多记录是协议，不一定和一个 token 一一对应。

### 3.4 `coin_basic` 只做消费层映射，不做底层事实表

以后 `coin_basic` 的定位应该是：

- 给 n8n、知识库、分析脚本一个稳定入口
- 汇总当前“已确认”的主身份字段
- 作为读取方便的业务表或物化视图

而不是原始采集入库的第一站。

### 3.5 “跟踪状态”从映射表剥离

`track_status`、`remark`、人工优先级、投研负责人，这些都属于运营状态，建议从 `coin_basic` 拆到独立表：

- `biz.research_target`

这样 `coin_basic` 负责“是什么”，`research_target` 负责“我们要不要跟踪它”。

## 4. 结合 CoinMarketCap API 文档后的建模建议

你给的 `从-coinmarketcap.com-抓取详情-2026-07-29.json` 里，当前至少覆盖了 4 大类：

1. `cryptocurrency`
2. `token`（实际上是 DEX / on-chain token 体系）
3. `tools`
4. `deprecated`

据此，CMC 在数据库里不应只落成一个 `coin_basic`，而应该拆成两条主线：

### 4.1 CMC 资产主线

主要对应：

- `/v1/cryptocurrency/map`
- `/v2/cryptocurrency/info`
- `/v3/cryptocurrency/quotes/latest`
- `/v2/cryptocurrency/market-pairs/latest`
- `/v1/cryptocurrency/categories`
- `/v1/cryptocurrency/category`

这部分进入：

- `src_cmc.cmc_asset_map`
- `src_cmc.cmc_asset_info`
- `src_cmc.cmc_asset_quote_snapshot`
- `src_cmc.cmc_market_pair_snapshot`
- `src_cmc.cmc_category`
- `src_cmc.cmc_category_member`

### 4.2 CMC DEX Token 主线

主要对应：

- `/v1/dex/token`
- `/v1/dex/token/price`
- `/v1/dex/token/pools`
- `/v1/dex/security/detail`
- `/v1/dex/tokens/trending/list`

这部分不要硬塞进传统 `coin_basic`，而应该进入：

- `src_cmc.cmc_dex_token`
- `src_cmc.cmc_dex_token_price_snapshot`
- `src_cmc.cmc_dex_pool_snapshot`
- `src_cmc.cmc_dex_security_snapshot`

### 4.3 Tools 和 Deprecated 的处理

- `tools` 更像工具或参考数据，可选择性落到 `sys` 或来源参考表
- `deprecated` 不作为新系统主依赖，只保留文档，不建议作为正式采集主路径

### 5.2 `raw` 层：原始响应层

#### `raw.api_response`

这是整个系统最重要的底层表之一。

建议字段：

- `id BIGSERIAL PRIMARY KEY`
- `run_id BIGINT NOT NULL`
- `platform_code TEXT NOT NULL`
- `endpoint_code TEXT NOT NULL`
- `request_key TEXT`
- `entity_key TEXT`
- `page_key TEXT`
- `payload JSONB NOT NULL`
- `payload_hash TEXT NOT NULL`

- `request_key` 可放 `id=1,2,3` 或 `slug=uniswap`

### 5.6 `core` 层：标准实体层

这是新系统真正的核心。

#### `core.asset`

统一资产实体。

```sql
CREATE TABLE core.asset (
    asset_id BIGSERIAL PRIMARY KEY,
    canonical_symbol VARCHAR(128) NOT NULL,
    canonical_name VARCHAR(256) NOT NULL,
    asset_type VARCHAR(32) NOT NULL DEFAULT 'token',
    status VARCHAR(32) NOT NULL DEFAULT 'active',
    launch_date DATE,
    created_at TIMESTAMP NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMP NOT NULL DEFAULT NOW()
);
```

#### `core.protocol`

统一协议实体。

```sql
CREATE TABLE core.protocol (
    protocol_id BIGSERIAL PRIMARY KEY,
    canonical_name VARCHAR(256) NOT NULL,
    protocol_type VARCHAR(64),
    official_domain TEXT,
    status VARCHAR(32) NOT NULL DEFAULT 'active',
    created_at TIMESTAMP NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMP NOT NULL DEFAULT NOW()
);
```

#### `core.chain`

统一链实体。

```sql
CREATE TABLE core.chain (
    chain_id BIGSERIAL PRIMARY KEY,
    chain_name VARCHAR(128) NOT NULL,
    chain_slug VARCHAR(128),
    is_mainnet BOOLEAN NOT NULL DEFAULT TRUE,
    created_at TIMESTAMP NOT NULL DEFAULT NOW()
);
```

#### `core.asset_contract`

标准化资产合约表。

建议字段：

- `asset_id`
- `chain_id`
- `contract_address`
- `is_native`
- `is_primary`
- `decimals`
- `source_preference`

建议唯一键：

- `UNIQUE(chain_id, contract_address)`

#### `core.asset_source_map`

资产和来源 ID 的映射表。

```sql
CREATE TABLE core.asset_source_map (
    asset_id BIGINT NOT NULL REFERENCES core.asset(asset_id),
    source_code VARCHAR(32) NOT NULL,
    source_asset_key VARCHAR(256) NOT NULL,
    match_status VARCHAR(32) NOT NULL DEFAULT 'confirmed',
    match_method VARCHAR(32),
    match_confidence NUMERIC(5,2),
    is_primary BOOLEAN NOT NULL DEFAULT FALSE,
    verified_by VARCHAR(64),
    verified_at TIMESTAMP,
    created_at TIMESTAMP NOT NULL DEFAULT NOW(),
    PRIMARY KEY (source_code, source_asset_key),
    UNIQUE (asset_id, source_code, source_asset_key)
);
```

`source_asset_key` 示例：

- `cmc:1`
- `coingecko:bitcoin`
- `cmc_dex:ethereum:0xa0b8...`

#### `core.protocol_source_map`

协议和来源 ID 的映射表。

主键逻辑与 `asset_source_map` 一样。

#### `core.protocol_asset_link`

这是 DefiLlama 融入系统时非常关键的一张表。

说明：

- 一个协议可能有多个 token
- 一个 token 也可能服务于多个协议

建议字段：

- `protocol_id`
- `asset_id`
- `relation_type`，如 `governance_token` / `gas_token` / `lp_token` / `reward_token`
- `is_primary_token`
- `confidence_score`

#### `core.mapping_candidate`

人工审核候选映射队列表。

建议字段：

- `candidate_id`
- `entity_type`
- `left_source_code`
- `left_source_key`
- `right_source_code`
- `right_source_key`
- `score`
- `evidence JSONB`
- `review_status`
- `review_note`

这张表的作用是把“自动弱匹配”变成“可审计的候选队列”，而不是直接脏写。

## 6. `coin_basic` 应该怎么生成

新的 `coin_basic` 不建议手工逐条写入，而建议每日或每次映射变更后自动刷新。

推荐生成逻辑：

1. 从 `core.asset` 取主资产实体
2. 左连接 `core.asset_source_map`
3. 从 `src_cmc.cmc_asset_info` 优先拿官网 / docs / github / logo
4. 若 CMC 缺失，再用 `src_cg.cg_coin_detail` 补
5. 若资产和协议存在主关联，可把 `primary_defillama_slug` 从 `core.protocol_asset_link` 反查回来
6. 写入 `biz.coin_basic`

字段优先级建议：

- `official_website`: `CMC > CoinGecko > 人工维护`
- `docs_url`: `CMC > CoinGecko > 人工维护`
- `github_url`: `CMC > CoinGecko > 人工维护`
- `main_chain`: `CMC platform > 合约表归纳 > 人工修正`

## 7. 为什么不建议再把 `defillama_slug` 固定放在 `coin_basic` 主字段里

因为它在很多场景下不是资产 ID，而是协议 ID。

典型问题：

1. 一个协议有治理币、LP 币、奖励币，不止一个 token
2. 一个 token 可能对应多个协议关系
3. DefiLlama 更关注协议 TVL、fees、revenue，不是资产发行信息

所以更合理的设计是：

- `defillama_slug` 先落到 `src_llama.llama_protocol`
- 再通过 `core.protocol_source_map`
- 再通过 `core.protocol_asset_link`
- 最后在 `biz.coin_basic` 只回填一个“主协议 slug”作为便捷字段

这样系统语义才不扭曲。

## 9. 新旧系统的职责对照

### 旧设计

- `coin_basic`：主表、映射表、文档入口表、运营状态表
- `doc_asset`：文件表

### 新设计

- `biz.coin_basic`：消费层资产映射表

## 10. 推荐的工作流顺序

### 第一步：先建底层，不急着改业务流

1. 建 schema：`sys / raw / src_cmc / src_cg / src_llama / core / biz`
2. 建 `raw.api_response`
3. 把现有 CMC / CoinGecko / DefiLlama 工作流改成“先写 raw，再写 src”

### 第二步：补标准实体层

4. 建 `core.asset / protocol / source_map`
5. 先只做确定性强匹配：
   - 合约地址完全一致
   - 官网主域名一致
   - 明确的 source 官方映射

### 第三步：再做消费层

6. 用 SQL 或物化视图刷新 `biz.coin_basic`
7. 把 n8n 下游流程逐步从旧 `coin_basic` 切到新 `biz.coin_basic`

### 第四步：最后迁移文档流

8. `official_website / docs_url / github_url` 不再直接来自旧主表
