# 高亮信号上游缺陷 P1-1 / P1-4 整改方案

> 版本：v1.0（2026-09-23）
> 覆盖模块：`05_代码与脚本/workbench/macro_market.py`、`05_代码与脚本/scripts/bin/phase_b2_third_party_raises.py`、`05_代码与脚本/scripts/bin/fix_asset_raises_placeholder.py`、`05_代码与脚本/workbench/test_macro_market_p1_upstream.py`
> 状态：**P1-1 已实施**（待生产快照验证）；**P1-4 已实施并完成存量清理**
> 本文只描述系统的「**当前**」口径与实现——不含历史修订记录、不含已被取代的方案。

## 1. 结论

P1-1（高亮卡在 AI 门禁前缺 `asset_id`）与 P1-4（`biz.asset_raises` 挂在占位资产上）是**同一条链上的两个上游缺陷，且相互耦合**：P1-4 会把错误的 `asset_id` 塞进融资卡，P1-1 决定这些卡要不要送 AI。因此排期顺序为 **P1-4 先、P1-1 后**——先让身份正确，再放开覆盖率，否则放宽 AI 覆盖会把错误画像从「静默」放大成「每日 2 张 + 缓存污染」。

| 编号 | 缺陷 | 处置 |
|---|---|---|
| P1-1 | 币种形态高亮卡进 AI 门禁时无 `asset_id`，被整批跳过（AI 覆盖率 8/10 → 2/10） | ✅ 已实施：`asset_id` 解析前置 |
| P1-4 | `biz.asset_raises` 408 行挂在无 `canonical_symbol` 的占位资产上 | ✅ 已实施：消费侧护栏 + 存量清理 + 写入侧守卫 |

## 2. P1-1：`asset_id` 解析晚于 AI 门禁

### 2.1 现象

| 快照日 | 高亮卡数 | `_ai_skipped_no_asset` | 有 `ai_analysis_v2` |
|---|---|---|---|
| 09-12 ~ 09-15 | 10 | **0** | 6 / 7 / 8 / 8 |
| 09-16 起 | 10 | **4 ~ 5** | 2 ~ 4 |
| 09-23 | 10 | 2 | 2 |

### 2.2 根因

[macro_market.py](file:///e:/瞎搞乱搞/web3/加密货币研究报告/05_代码与脚本/workbench/macro_market.py#L4350) 中 `select_highlight_signals` 用 `dict(o)` **浅拷贝**生成同标的合并卡；若 `asset_id` 解析发生在该拷贝之后，合并卡就永久丢失 `asset_id`，而 [ai_signal_analyzer.py:3328-3350](file:///e:/瞎搞乱搞/web3/加密货币研究报告/05_代码与脚本/workbench/ai_signal_analyzer.py#L3328-L3350) 的门禁要求 `bool(asset_id)`，于是被记为 `_ai_skipped_no_asset` 整批跳过。

**关键证据**：09-23 快照中 `BP`（`asset_id=10134`）与 `SOL`（`asset_id=1814`）两张卡**同时**具备 `asset_id` 与 `_ai_skipped_no_asset=true` —— 证明缺陷是「AI 跑在回填之前」，而非「解析不到」。

**归因**（不是回归）：`5a268cb`（2026-09-15，「AI 串号防御」）引入 `_ai_skipped_no_asset` 守卫，生产 09-16 生效。在此之前无 `asset_id` 也照送 AI，产出 `v2:0:<symbol>` 缓存污染（跑但身份是错的）；守卫上线后变为「完全不跑」。同一根因、两种症状。

**附带面**：`_symbols_from_opportunity` 用 `^[A-Z0-9]{2,10}$` 收集 symbol，单字符 symbol（如 `H`，`core.asset` 中 asset_id=7994）无法进入解析集合，被误判为「聚合/宏观」跳过 AI。

### 2.3 修复

1. **解析前置**：把「为 `opportunities + excluded` 解析 `asset_id`」整块上移到 `select_highlight_signals` / `select_risk_signals` **之前**（[macro_market.py:5780-5801](file:///e:/瞎搞乱搞/web3/加密货币研究报告/05_代码与脚本/workbench/macro_market.py#L5780-L5801)），使合并卡通过浅拷贝自然继承 `asset_id`。
2. **删除事后补丁**：移除原先「AI 增强后为 highlights / risk_signals 补 `asset_id`」的兜底块（该块位置注定无用，只是掩盖症状）。
3. **单字符 symbol**：`_symbols_from_opportunity` 的 symbol 正则由 `{2,10}` 放宽为 `{1,10}`（[macro_market.py:5916](file:///e:/瞎搞乱搞/web3/加密货币研究报告/05_代码与脚本/workbench/macro_market.py#L5916)）。未命中 DB 的 target 仍返回空集合，聚合类卡片不会凭空获得身份。

`ai_signal_analyzer.py` **未改动**：门禁中 `^[A-Z0-9]{2,10}$` 保留为「无 `asset_id` 时的次级判据」，前置解析后主判据 `bool(asset_id)` 已能覆盖单字符 symbol。

### 2.4 影响面与观察口径

- AI 覆盖率预期由 2~4/10 回到 7~10/10；LLM 调用量与单次 overview 耗时上升（仍受 `ai_highlight_max`（默认 15）约束）。
- 卡片顺序会变：统一排序 `_sort_key=(ai_approved, mixed, ai_score)` 在 AI 之后生效，此前被跳过的卡保持原序，现在会参与重排。
- 「⚡ 事件驱动直通」标注比例可能上升：此前未进 AI 的事件卡现在会真跑 AI，若 AI 不背书则挂 `_ai_downgraded`。
- 日报「AI 精选高亮信号」模块卡数上升（无 AI 的卡此前整卡不展示）。
- **不涉及任何阈值 / 分数 / 配额改动**；`select_highlight_signals` 与 `select_risk_signals` 不读取 `asset_id`，故精选结果本身不变，仅 AI 阶段行为变化。

## 3. P1-4：`biz.asset_raises` 占位资产错配

### 3.1 现象

| 项 | 清理前 |
|---|---|
| 全表 | 1199 行 / 474 个资产 / **全部写入于 2026-08-16 单一批次** |
| 污染行（目标资产无 `canonical_symbol`） | **408 行 / 仅 2 个资产** |
| `asset_id=11125`（Aztec Connect，symbol `-`） | **407 行，涉及 287 个不同 `defillama_id`** |
| `asset_id=11161`（Algofi Lend） | 1 行 |

### 3.2 传播链（清理前仍在活跃）

```
biz.asset_raises.asset_id (=11125)
  → _recent_raises() 直接取该 asset_id            macro_market.py:3789
  → 融资卡 target 因 canonical_symbol='-' 回退 protocol_name   macro_market.py:5224
  → 09-23 实证：Beezie / Saturn 两张卡的 asset_id 均为 11125 且已跑 AI
  → AI 以 Aztec Connect 的身份出画像（缓存键 v2:11125:BEEZIE）
```

即卡片是「**甲协议标题 + 乙资产身份**」的嵌合体。根因是写入方 [phase_b2_third_party_raises.py](file:///e:/瞎搞搞/web3/加密货币研究报告/05_代码与脚本/scripts/bin/phase_b2_third_party_raises.py) 当时无「目标资产必须真实」的守卫，大量 DL 协议被映射到同一占位资产后原样落库。

### 3.3 三层修复

**① 消费侧护栏**（`macro_market._recent_raises`，[L3789](file:///e:/瞎搞乱搞/web3/加密货币研究报告/05_代码与脚本/workbench/macro_market.py#L3789)）
查询追加 `AND a.canonical_symbol IS NOT NULL AND TRIM(a.canonical_symbol) NOT IN ('', '-', '?')`；融资卡改为 `target = symbol or proto or "?"`，保证 target 与 `asset_id` 同源。

**② 存量清理**（新脚本 [fix_asset_raises_placeholder.py](file:///e:/瞎搞乱搞/web3/加密货币研究报告/05_代码与脚本/scripts/bin/fix_asset_raises_placeholder.py)）
默认 dry-run，`--apply` 执行：

- 自动备份整表 → `biz.asset_raises_bak_<YYYYMMDD>`
- **可信重映射**：仅以 `core.asset_source_map` 的 dl 映射（`source_asset_key = defillama_id`）为准，且目标资产必须有真实 symbol；重映射后与既有行 `(asset_id, round, raise_date)` 冲突则按重复删除
- **不做名称猜测**：同名 ≠ 同一项目（实测 `Cypher` 命中 3 个资产、`OrBit` 命中 2 个），无权威映射的行直接删除

**③ 写入侧守卫**（`phase_b2_third_party_raises.py`）
两个候选分支（全量 / `--asset-id`）均追加 `INNER JOIN core.asset` 与同一占位资产条件；新增 `count_placeholder_mapped_protocols()` 输出被守卫排除的协议数，避免「悄悄少跑」不可见。守卫与清理脚本共用同一口径字面量。

### 3.4 存量清理结果

| 指标 | 值 |
|---|---|
| 总行数 | 1199 → **803** |
| 重映射 | **12** 行（PELL×2 / TMX×1 / GAIB×2 / CAP×3 / P2P×2 / TRIA×2） |
| 删除 | **396** 行（其中 85 行在 `core.asset` 存在同名资产，仅作诊断，未参与处置） |
| 剩余占位行 | **0** |
| 备份表 | `biz.asset_raises_bak_20260923`（1199 行） |
| 被守卫排除的协议 | **6** 个（仍映射到占位资产，见 §4） |

消费侧复验：`_recent_raises(window_days=90, limit=10)` 清理后仅返回 `asset_id=7206 VVV（Venice AI）`，不再出现 11125。
