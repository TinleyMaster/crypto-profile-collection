> 优先级：P2·低
> 问题类型：数据库运维（统计信息缺失 + 死元组堆积）

> 风险等级：极低（只读操作，不锁表，不影响业务）

## 二、执行步骤

### 步骤 1：全库 ANALYZE（必做，低风险）

```sql
-- 全库 ANALYZE，更新所有表的统计信息
-- 耗时：预计 1~3 分钟（取决于数据量）
-- 锁级别：SHARE UPDATE EXCLUSIVE（不阻塞读写）
ANALYZE;
```

**验证**：
```sql
SELECT schemaname, count(*) as never_analyzed
FROM pg_stat_user_tables
WHERE last_analyze IS NULL AND last_autoanalyze IS NULL
GROUP BY schemaname
ORDER BY never_analyzed DESC;
-- 期望：0 行或接近 0
```

### 步骤 2：大表 VACUUM（可选，看死元组情况）

```sql
-- 检查当前死元组最多的表
SELECT schemaname, relname, n_dead_tup,
       pg_size_pretty(pg_total_relation_size(quote_ident(schemaname) || '.' || quote_ident(relname))) as size
FROM pg_stat_user_tables
WHERE n_dead_tup > 10000
ORDER BY n_dead_tup DESC
LIMIT 10;
```

如果有死元组 > 10 万的表，执行：
```sql
-- 对死元组多的大表执行 VACUUM（回收空间供重用，不释放磁盘给 OS）
VACUUM biz.doc_source_entry;
```

> 注意：`VACUUM FULL` 会锁表且耗时长，**不要在业务高峰期执行**。普通 `VACUUM` 无此问题。

### 步骤 3：开启 autovacuum（长期治理）

```sql
-- 检查当前 autovacuum 配置
SHOW autovacuum;
SHOW log_autovacuum_min_duration;
```

如果 autovacuum 是 off，建议开启：
```sql
ALTER SYSTEM SET autovacuum = on;
SELECT pg_reload_conf();
```

## 三、定时化方案

建议在每日调度任务中加入 ANALYZE，或者依赖 autovacuum 自动触发。

**轻量方案**：依赖 autovacuum（已开即可）
- 大部分表的统计信息由 autovacuum 自动维护
- 大表/写入频繁的表可能需要手动 ANALYZE

**主动方案**：在 `data_sync_daily` 调度末尾加一步
```python
# 在每日数据同步完成后执行
with get_db() as conn:
    conn.execute("ANALYZE")
```

## 五、补充说明

### 关于 `pg_stat_user_tables.last_analyze` 为 NULL

执行 ANALYZE 后 `last_analyze` 字段仍为 NULL，但 `pg_class.relpages` / `reltuples` 已更新，
说明**统计信息实际已写入**，查询优化器可以正常使用。

原因：执行前 `track_counts = off`，导致 `pg_stat_user_tables` 统计视图不更新分析时间戳。
`track_counts` 已开启，后续 ANALYZE 会正常记录时间戳。
