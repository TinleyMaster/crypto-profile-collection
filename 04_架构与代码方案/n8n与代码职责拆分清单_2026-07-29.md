# n8n 与代码职责拆分清单（2026-07-29）

## 1. 先说结论

这套投研系统最适合的形态不是：

- 全部写在 `n8n`
- 或全部改成代码

而是：

## `n8n 做编排，代码做处理`

更具体一点：

- `n8n` 负责调度、串联、重试、通知、人工触发、调用数据库
- `代码` 负责解析、标准化、映射、去重、抽取、规则判断

---

## 2. 一个最实用的判断标准

如果某件事满足下面任一条，优先写代码：

1. 逻辑会越来越复杂
2. 以后需要复用
3. 需要测试
4. 需要版本 diff 清晰
5. 有明显“算法 / 规则引擎 / 解析器”特征

如果某件事满足下面任一条，优先放 n8n：

1. 本质是流程编排
2. 主要是调 API
3. 需要定时执行
4. 需要失败重试
5. 需要人工触发或人工介入
6. 需要接通知、飞书、Drive、知识库

---

## 3. 按你这套系统逐项拆分

## A. 适合留在 n8n 的部分

### A1. 主调度工作流

比如：

- 每日基础档案更新
- 每日行情更新
- 每日文档抓取
- 每周巡检

这些都非常适合 `n8n`，因为它天然就是调度器。

### A2. API 请求编排

比如：

- 调 CMC `/map`
- 调 CMC `/info`
- 调 CoinGecko `/coins/{id}`
- 调 DefiLlama `/protocols`

如果只是：

- 分批调用
- 控速
- 失败重试
- 把结果写到数据库

那就继续放在 `n8n` 很合适。

### A3. 数据库读写编排

比如：

- 从 `src_cmc.cmc_asset_map` 取待补详情 ID
- 从 `biz.doc_source_entry` 取待抓取 URL
- 跑完后回写 `sys.ingest_run`

这类“读一批 -> 调接口 -> 写回去”的事情，`n8n` 很顺手。

### A4. 外部系统连接

比如：

- 飞书通知
- Google Drive 上传
- ima 知识库上传
- Webhook 回调

这些连接器式的能力，`n8n` 价值很高，不值得自己再造一遍。

### A5. 人工审核流

比如：

- 导出 `mapping_candidate`
- 人工确认后回写状态
- 对失败文档进行手动补链

这些操作在 `n8n` 中做一个半自动流程非常合适。

---

## B. 适合改成代码的部分

### B1. 原始响应解析器

比如：

- CMC `/map` 响应解析成 `src_cmc.cmc_asset_map`
- CMC `/info` 解析成 `src_cmc.cmc_asset_info`
- CoinGecko 详情解析成 `src_cg.cg_coin_detail`
- DefiLlama `/protocols` 解析成 `src_llama.llama_protocol`

这类逻辑看起来现在还简单，但很快就会出现：

- 字段兼容
- 空值处理
- 版本差异
- 特殊币种例外

所以建议逐步从 `Code` 节点迁成代码模块。

### B2. 映射逻辑

这是最应该写代码的部分。

比如：

- `CMC` 资产和 `CoinGecko` 资产的匹配
- `DefiLlama protocol` 和 `asset` 的关系判断
- 合约地址标准化
- 官网域名归一化
- 弱匹配候选打分

这些都是典型的“规则引擎”问题。  
放在 `n8n Code` 节点里，后面一定会变难维护。

### B3. 文档发现与抽取

比如：

- 从官网首页找白皮书链接
- 从 docs 页面抽取 PDF
- 从 GitHub release / docs 里找文档
- 页面跳转、多跳解析、正文抽取

这类东西很容易变成：

- 多分支规则
- 多跳递归
- 内容质量判断
- 链接去重

这类也更适合独立脚本或服务，而不是塞在 n8n 里。

### B4. 去重与规范化工具

比如：

- URL 规范化
- 域名提取
- 文本哈希
- 合约地址大小写标准化
- tags 清洗

这些都是非常适合写成工具函数的。

### B5. 复杂 SQL 生成

当你开始做：

- 多来源汇总
- 条件优先级回填
- 批量 upsert
- 审核候选批处理

SQL 会越来越长。  
这时候建议：

- SQL 仍然由数据库执行
- 但 SQL 模板和参数构造逻辑用代码维护

而不是全部手搓在 n8n 节点里。

## 4. 按新架构分层后的推荐归属

## `sys` 层

### 留在 n8n

- 创建 `ingest_run`
- 成功 / 失败回写状态

### 代码可选

- 统一封装 run log 写入函数

结论：

`sys` 层可以先放在 `n8n + SQL`，不急着代码化。

---

## `raw` 层

### 留在 n8n

- API 调用后直接写 `raw.api_response`

### 代码可选

- `payload_hash`
- `request_key`
- `entity_key`
- 稳定序列化

结论：

`raw` 层建议还是由 `n8n` 驱动，但哈希和包装逻辑逐步抽到代码里。

---

## `src_*` 层

### 初期

- 可先放在 `n8n Code` 节点 + Postgres

### 中期

- 迁到独立解析器脚本

结论：

`src_*` 是最适合逐步代码化的一层。

---

## `core` 层

### 强烈建议写代码

因为这里有：

- 实体生成
- 跨源映射
- 候选打分
- 主从关系建立
- 人工审核结果回写

这层本质就是你的“数据引擎核心”，不建议长期放 n8n。

---

## `biz` 层

### 两类拆法

#### 适合 n8n + SQL 的

- `biz.coin_basic` 刷新
- `biz.research_target` 更新
- `biz.doc_source_entry` 生成

#### 适合代码的

- `biz.doc_asset` 的复杂抽取前处理
- 内容质量评分
- 文档类型识别

结论：

`biz` 层是混合层，不需要极端。

---

## 5. 最推荐的技术分工

## n8n 负责这些

1. 调度
2. 调 API
3. 控速和重试
4. 读库取待处理任务
5. 调用代码脚本
6. 执行 SQL
7. 上传云盘 / 知识库
8. 发送通知

## 代码负责这些

1. 响应解析
2. 数据标准化
3. 映射打分
4. URL / 域名 / 合约规范化
5. 文档发现和正文提取
6. 文档分类与去重
7. 复杂汇总逻辑

## 6. 你这套系统最危险的一种走法

最危险的是：

## “表面上是工作流，实际上在 n8n 里堆了一个代码系统”

典型表现就是：

- 一个 `Code` 节点 300 行
- 同样的解析逻辑复制 5 份
- SQL 到处散落
- 匹配规则藏在不同工作流里
- 出错时不知道是流程问题还是逻辑问题

这个阶段一旦形成，后面重构成本会越来越高。

所以现在正好是最适合拆分的时候。

## 8. 最现实的演进路线

不要一上来就“重写成服务”。  
最稳的是三步走。

### 阶段1：先继续用 n8n 跑通新架构

做法：

- n8n 仍是主调度
- 解析逻辑先放 `Code` 节点

目标：

- 尽快让新 `sys/raw/src/core/biz` 跑起来

### 阶段2：把复杂 Code 节点逐步外移

做法：

- 把解析逻辑写成脚本
- n8n 用 `Execute Command` 或 HTTP 调用

目标：

- 降低工作流复杂度
- 提高可复用性

### 阶段3：保留 n8n 为控制面板

最终形态：

- `n8n` 是 orchestrator
- `代码` 是 engine
- `PostgreSQL` 是 source of truth

这就是最适合你这套系统的形态。

## 9. 最后给你的直接建议

如果只能记住一句话，就记这个：

> 所有“可视化流程”留给 n8n，所有“不可视化复杂逻辑”抽成代码。

对应到你当前项目：

- `WF_CMC_MAP_INGEST` 可以先用 n8n 搭
- 但 `CODE_PARSE_CMC_MAP` 这种东西，未来就该抽成代码函数
- `WF_CORE_MAPPING_REFRESH` 从第一天起就应该按“代码核心”来设计
