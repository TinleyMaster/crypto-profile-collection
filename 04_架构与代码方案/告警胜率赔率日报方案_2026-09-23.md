# 告警胜率赔率日报方案（阈值-行情失配早期预警）

> 版本：v1.0（设计方案，未实现）｜ 日期：2026-09-23 ｜ 状态：待评审
> 关联：盘面异动扫描系统（`scan_daemon.py` / `biz.scan_signal`）、每日早报（`build_daily_brief.py` / `send_daily_brief.py`）、
> 场景回测（`backtest_scan_scenarios.py`）、催化剂后验体系（`catalyst_outcome` 同构参考）
> 目标：**把「告警信号的实际胜率/赔率」变成每日可见的数字，并在「阈值与当前行情不匹配」时提前报警**，
> 而不是等负期望累积多日之后才由人肉复盘发现。

---

## 1. 背景与问题

### 1.1 现状

盘面异动扫描系统每天发出 17~79 条实时告警（`biz.scan_signal.alerted_at IS NOT NULL`），
但**发出去之后没有任何自动化的后验统计**：

| 已有 | 缺失 |
|------|------|
| 实时告警邮件（`scan_daemon._render_alert_email`） | 告警发出后 T+1h/4h/12h/24h 的实际涨跌 |
| 信号明细落库（`biz.scan_signal` 含 `vol_ratio`/`price_chg_pct`/`oi_chg_pct`/`timeframe`/`scenario`/`context_tags`） | 按日聚合的胜率、赔率、盈亏比 |
| 邮件里「历史同场景」后验（`_scenario_priors`，12h 口径、按 `(p_dir, oi_dir)` 分组） | 行情环境（振幅/波动占比）与信号表现的**交叉表** |
| 场景回测（`backtest_scan_scenarios.py`，离线、按场景聚合、含阈值 sweep） | 每日自动跑、并对外报警的**失配探测器** |

**后果**：2026-09-22（上海日）发出 79 条告警，T+1h 胜率仅 35.4%、均收益 −0.09%、PF 0.95（**负期望**），
直到次日人工复盘才被发现；同期 09-21 胜率 64.1%、09-18 胜率 56.2%。**整整一天的负期望无人拦截。**

### 1.2 核心问题

- 今天这批告警，**期望是正还是负**？——发信时不知道，次日也不知道（无自动统计）。
- 阈值（量比 2.0、涨幅 2.0/3.0%、OI 分档）在当前行情下**是不是太松/太紧**？——无量化判据。
- 告警数从 39 条暴增到 79 条，是**行情给了更多机会**，还是**门槛被低波动变相放松**？——无法区分。
- 中长窗口（T+24h）胜率 61.5% 看起来不错，但**多少来自 BTC beta、多少来自信号 alpha**？——未拆分。

### 1.3 目标

建立「**告警 → 多窗口结局 → 每日胜率/赔率 → 阈值-行情失配判定**」的自动闭环：

```
scan_daemon 告警(alerted_at)
      │
      ▼
① 结局结算：T+1h/4h/12h/24h 方向对齐净收益 + BTC beta 对照
      │
      ▼
② 日报聚合：当日胜率/赔率/PF/盈亏平衡胜率 + 行情环境指标
      │
      ▼
③ 失配判定：告警数异动 × 胜率跌破盈亏平衡线 × 边缘桶占比
      │
      ▼
④ 每日邮件（当日值 + 近 3 日滚动 + 与阈值常量的对照）
```

**一句话**：让「阈值是否匹配当前行情」从**事后人工复盘**变成**每日自动报警的数字**。

## 2. 数据基础（已探测验证）

### 2.1 数据源盘点

### 2.3 实测基线（201 条，2026-09-17 ~ 09-23，扣 0.1% 双边费）

**按日（上海日）**

| 日期 | 告警数 | T+1h 胜率 | T+1h 均 | BTC 日涨跌 | BTC 日振幅 | 小时\|涨跌\|>0.5% 占比 |
|------|-------:|----------:|--------:|-----------:|-----------:|----------------------:|
| 09-17 | 17 | 47.1% | −0.46% | +1.34% | 2.42% | 0% |
| 09-18 | 16 | 56.2% | +1.86% | +5.16% | 6.49% | 44% |
| 09-21 | 39 | 64.1% | +0.78% | +5.63% | 7.21% | 59% |
| 09-22 | 79 | 35.4% | −0.09% | +0.53% | 2.71% | 16% |
| 09-23 | 50 | 51.1% | −0.21% | +0.06% | 1.01% | 0% |

**规律**：大振幅趋势日胜率 56~64%，横盘低波动日 35%，**且横盘日告警数反而翻倍**。

**09-22 分桶（边缘信号是灾难）**

| 维度 | 桶 | 胜率 | n |
|------|----|-----:|--:|
| 量比 `vol_ratio` | <2.5 | 17.6% | 17 |
| | 2.5~4 | 31.2% | — |
| | 4~6 | 45.5% | — |
| | >6 | 46.2% | 13 |
| 触发涨幅 `price_chg_pct` | <3% | 31.2% | — |
| | **3~5%** | **12.5%** | — |
| | 5~8% | 50.0% | — |
| | >8% | 66.7% | — |
| OI 增速 `oi_chg_pct` | <1% | 35.0% | — |
| | 1~3% | 21.7% | — |
| | 3~6% | 28.6% | — |
| | **>6%** | **75.0%** | — |
| 周期 `timeframe` | **15m** | **28.6%** | 35 |
| | 1h | 36.8% | 38 |
| 场景 `scenario` | **S1** | **30.5%** | 59 |

`corr(触发涨幅, T+1h 收益) = +0.170` ⇒ **排除「追高」假设**，本质是「弱信号无效」。

**全样本多窗口**

| 窗口 | 胜率 | 均收益 | PF |
|------|-----:|-------:|---:|
| T+1h | 47.4% | +0.18% | 1.14 |
| T+4h | 52.0% | +0.70% | 1.41 |
| T+12h | 53.7% | +2.48% | 2.08 |
| T+24h | 61.5% | +4.22% | 1.51 |

**BTC 同方向 beta**：T+24h 胜率 96.2%、+3.01% ⇒ **中长窗口的正期望大部分是 beta，不是 alpha**。

### 2.4 ⚠️ 性能约束（必须遵守）

`biz.asset_klines` 虽有 `(symbol, interval, open_time DESC)` 索引，但**整表拉取会因跨区链路超时**
（实测 240s+ 未返回）。因此：

- 取价必须**在 SQL 侧用 `LATERAL` / 相关子查询算好**，只回传结果行（参照 `_scenario_priors` L1352-1374 的写法）；
- **禁止**把 K 线拉到 Python 再算（`backtest_scan_scenarios.load_klines` 那种全量拉取只适合离线回测，不适合每日任务）。

## 3. 总体设计

### 3.1 新增 3 张表 + 2 个脚本 + 1 处调度注册

```
┌───────────────────────────────────────────────────────────────────┐
│ 新增表1：biz.scan_signal_outcome（逐信号多窗口结局，T+1h/4h/12h/24h）│
└──────────────────────────────┬────────────────────────────────────┘
                               │ 每小时增量结算（只算未到期→到期）
                        ┌──────▼───────┐
                        │ 脚本1         │
                        │ collect_scan_ │
                        │ outcome.py    │
                        └──────┬───────┘
                               │
┌──────────────────────────────▼────────────────────────────────────┐
│ 新增表2：biz.scan_edge_daily（日报聚合 + 失配判定，按上海日一行）    │
│ 新增表3：biz.scan_edge_bucket（当日 × 维度 × 桶，供分桶诊断）        │
└──────────────────────────────┬────────────────────────────────────┘
                               │ 每日一次（08:10）
                        ┌──────▼────────┐
                        │ 脚本2          │
                        │ build_scan_    │
                        │ edge_report.py │
                        └──────┬────────┘
                               │ 渲染 + 发送
                        ┌──────▼────────┐
                        │ send_scan_edge │  （复用 EmailNotifier）
                        │ _report.py     │
                        └────────────────┘
```

### 3.2 三个时间维度

| 环节 | 频率 | 内容 |
|------|------|------|
| 结局结算 | 每小时（cron `5 * * * *`） | 把已到期窗口的 `outcome_state` 推进一级，只处理 `outcome_state <> 'resolved'` |
| 日报聚合 | 每日 08:10（Asia/Shanghai） | 聚合昨日（及近 3 日滚动）→ 落 `scan_edge_daily` / `scan_edge_bucket` |
| 邮件发送 | 每日 08:20 | 复用 `EmailNotifier`，与 09:00 早报解耦（先看告警质量，再看大盘） |

### 3.3 为什么不改造现有早报

`send_daily_brief.py`（66KB）承担大盘/资金流/催化剂等 10 个模块的渲染，职责已饱和；
告警后验是**另一个数据域**（信号质量，不是市场状态），且需要**独立的历史回填与趋势表**。
故采用**独立脚本 + 独立表 + 独立邮件**，只在 `build_daily_brief.py` 里加一行「告警质量摘要」（读 `scan_edge_daily` 最新一行），
避免两套逻辑互相污染。详见 §9。

## 4. 详细设计

### 4.1 表 1：`biz.scan_signal_outcome`（逐信号多窗口结局）

```sql
CREATE TABLE IF NOT EXISTS biz.scan_signal_outcome (
    signal_id       BIGINT PRIMARY KEY REFERENCES biz.scan_signal(id) ON DELETE CASCADE,
    symbol          TEXT NOT NULL,
    pool            TEXT,
    scenario        TEXT,
    timeframe       TEXT,
    p_dir           TEXT,                          -- up / down（方向对齐基准）
    alerted_at      TIMESTAMPTZ,                   -- 告警时刻（= 决策起点）
    base_time       TIMESTAMPTZ NOT NULL,          -- 基线 K 线 open_time（<= alerted_at 的最后一根已收盘 1h）
    base_px         NUMERIC(24,8),                 -- 基线收盘价

    -- 方向对齐净收益（%，已扣 0.1% 双边费）
    aligned_ret_1h  NUMERIC(10,4),
    aligned_ret_4h  NUMERIC(10,4),
    aligned_ret_12h NUMERIC(10,4),
    aligned_ret_24h NUMERIC(10,4),

    -- BTC 同方向同窗口收益（beta 对照，%）
    btc_ret_1h      NUMERIC(10,4),
    btc_ret_4h      NUMERIC(10,4),
    btc_ret_12h     NUMERIC(10,4),
    btc_ret_24h     NUMERIC(10,4),

    -- 超额（= aligned_ret - btc_ret，正=信号有 alpha）
    excess_1h       NUMERIC(10,4),
    excess_4h       NUMERIC(10,4),
    excess_12h      NUMERIC(10,4),
    excess_24h      NUMERIC(10,4),

    -- 途中风险（在 1h 收盘序列上取，避免用高低价造成不可复现）
    mae_24h         NUMERIC(10,4),                 -- 24h 内最大不利偏移（%，负值）
    mfe_24h         NUMERIC(10,4),                 -- 24h 内最大有利偏移（%）
    sl_hit_24h      BOOLEAN,                       -- 是否触及 stop_loss_pct（该列为 NULL 时本列 NULL）
    sl_pct_snapshot NUMERIC(8,2),                  -- 冗余快照（该列是 09-21 后才有）

    -- 结算状态
    outcome_state   TEXT NOT NULL DEFAULT 'pending',
                    -- pending(未到 24h) / resolved(已结算 24h) / no_data(无 K 线)
    last_window     SMALLINT NOT NULL DEFAULT 0,   -- 已结算的最大窗口小时数（0/1/4/12/24）
    bars_n          SMALLINT,                      -- 24h 内可用 1h 收盘数（不足则标 partial）
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX IF NOT EXISTS idx_scan_outcome_state
    ON biz.scan_signal_outcome (outcome_state, alerted_at DESC);
CREATE INDEX IF NOT EXISTS idx_scan_outcome_alerted
    ON biz.scan_signal_outcome (alerted_at DESC);

COMMENT ON TABLE biz.scan_signal_outcome IS '盘面告警逐信号多窗口结局（方向对齐净收益 + BTC beta 对照），供胜率赔率日报消费';
```

**结算规则**

- 基线：`base_time` = `alerted_at` 时刻**最后一根已收盘 1h K 线**的 `open_time`，`base_px` = 其 `close_px`。
  （只用已收盘棒：库里最新一根常是未收盘的 live 棒，同一时刻不同分钟读到不同值、不可复现 —— 与 `scan_daemon._build_regime` 同原则。）
- 终点：`base_time + N hours` 时刻**最后一根已收盘 1h 收盘价**。
- `aligned_ret = (px1 - px0)/px0 * 100 * (+1 if p_dir='up' else -1) - 0.1`。
- 只对 `p_dir IN ('up','down')` 计算；`p_dir` 为空（如 `BRK` 部分行）→ `outcome_state='no_data'`。
- `outcome_state='resolved'` 仅当 24h 窗口已到期且 `bars_n >= 24`；否则 `partial` 只写已到期窗口。
- **未到期行绝不混入日报统计**（`last_window` 闸门，同 `catalyst_outcome` 的教训）。

### 4.2 表 2：`biz.scan_edge_daily`（日报聚合 + 失配判定）

```sql
CREATE TABLE IF NOT EXISTS biz.scan_edge_daily (
    report_date      DATE PRIMARY KEY,             -- Asia/Shanghai 日
    alerts_n         INT NOT NULL DEFAULT 0,       -- 当日告警数（成熟样本口径）

    -- 多窗口胜率（0~1）
    win_1h  NUMERIC(6,4), win_4h  NUMERIC(6,4), win_12h NUMERIC(6,4), win_24h NUMERIC(6,4),
    -- 赔率 = 平均盈利 ÷ |平均亏损|
    odds_1h NUMERIC(8,4), odds_4h NUMERIC(8,4), odds_12h NUMERIC(8,4), odds_24h NUMERIC(8,4),
    -- 盈亏平衡胜率 = 1/(1+odds)
    be_1h   NUMERIC(6,4), be_4h   NUMERIC(6,4), be_12h   NUMERIC(6,4), be_24h   NUMERIC(6,4),
    -- 盈亏比 PF = 总盈利 ÷ 总亏损
    pf_1h   NUMERIC(8,4), pf_4h   NUMERIC(8,4), pf_12h   NUMERIC(8,4), pf_24h   NUMERIC(8,4),
    -- 均收益（净，%）
    avg_1h  NUMERIC(10,4), avg_4h NUMERIC(10,4), avg_12h NUMERIC(10,4), avg_24h NUMERIC(10,4),
    -- BTC beta 对照（同窗口、同方向）
    btc_win_24h  NUMERIC(6,4), btc_avg_24h NUMERIC(10,4),
    excess_avg_24h NUMERIC(10,4),

    -- 行情环境
    btc_close        NUMERIC(20,8),
    btc_chg_pct      NUMERIC(8,4),                 -- 当日涨跌（%）
    btc_amp_pct      NUMERIC(8,4),                 -- 当日振幅 (high-low)/low（%）
    btc_1h_gt05_ratio NUMERIC(6,4),                -- 小时 |涨跌|>0.5% 的占比
    fgi              INT,
    cap_trend_pct    NUMERIC(8,4),
    regime_label     TEXT,                         -- trend(趋势) / range(横盘低波动) / mixed(混合)

    -- 近 3 日滚动（判定用，抗单日小样本噪声）
    roll3_alerts_avg NUMERIC(8,2),
    roll3_win_1h     NUMERIC(6,4),
    roll3_be_1h      NUMERIC(6,4),
    roll3_pf_1h      NUMERIC(8,4),

    -- 分桶诊断摘要
    n_buckets        INT DEFAULT 0,
    edge_buckets     JSONB,                        -- 边缘桶列表 [{dim,bucket,n,win,be,share}]
    top_share_bucket JSONB,                        -- 占比最大且负期望的桶（若有）

    -- 样本成熟度
    matured_n        INT DEFAULT 0,                -- 当日已到期 24h 的样本数
    pending_n        INT DEFAULT 0,                -- 当日未到期样本数
    sample_ready     BOOLEAN NOT NULL DEFAULT FALSE,-- matured_n >= 10

    -- 失配判定
    mismatch_flag    BOOLEAN NOT NULL DEFAULT FALSE,
    mismatch_rules   TEXT[],                       -- 命中的规则 ID：A/B/C/D/E
    severity         TEXT NOT NULL DEFAULT 'ok',   -- ok / watch / high
    conclusion       TEXT,                         -- 一句话结论（中文）

    created_at       TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at       TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

### 4.3 表 3：`biz.scan_edge_bucket`（当日 × 维度 × 桶）

```sql
CREATE TABLE IF NOT EXISTS biz.scan_edge_bucket (
    report_date   DATE NOT NULL,
    dim           TEXT NOT NULL,   -- vol_ratio | price_chg | oi_chg | timeframe | scenario | regime | confidence | pool
    bucket        TEXT NOT NULL,   -- 桶标签，如 '2.5-4'、'15m'、'S1'、'range'
    n             INT NOT NULL DEFAULT 0,
    win_1h        NUMERIC(6,4),
    win_4h        NUMERIC(6,4),
    odds_1h       NUMERIC(8,4),
    be_1h         NUMERIC(6,4),
    pf_1h         NUMERIC(8,4),
    avg_1h        NUMERIC(10,4),
    avg_24h       NUMERIC(10,4),
    share         NUMERIC(6,4),    -- 该桶占当日告警数的比例
    edge          BOOLEAN NOT NULL DEFAULT FALSE,  -- 边缘桶（n>=5 且 win_1h < be_1h 且 share>=0.2）
    created_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    PRIMARY KEY (report_date, dim, bucket)
);

CREATE INDEX IF NOT EXISTS idx_scan_edge_bucket_edge
    ON biz.scan_edge_bucket (edge, report_date DESC);
```

**桶定义（与 `scan_daemon` 的阈值常量对齐，便于直接读出「阈值该往哪挪」）**

| 维度 | 桶边界 | 依据 |
|------|--------|------|
| `vol_ratio` | `<2.5` / `2.5-4` / `4-6` / `>6` | 当前 `VOL_RATIO_THR = 2.0`，实测 `<2.5` 桶胜率 17.6% |
| `price_chg` | `<3` / `3-5` / `5-8` / `>8` | 当前 `PRICE_THR = {5m:1.5, 15m:2.0, 1h:3.0}`，实测 `3-5` 桶 12.5% |
| `oi_chg` | `<1` / `1-3` / `3-6` / `>6` | `OI_FLAT_PCT = 0.5`，实测 `>6` 桶 75% |
| `timeframe` | `5m` / `15m` / `1h` | 实测 15m 28.6% |
| `scenario` | `S1`..`S8` / `ACC` / `BRK` | 实测 S1 30.5% |
| `regime` | `trend` / `range` / `mixed` | 新增维度（当前 regime 缺「无趋势」判据） |
| `confidence` | `high` / `medium` / `low` | 校验 `confidence` 是否真有区分度 |
| `pool` | `main` / `accumulation(BRK)` | 通道对比 |

### 4.4 脚本 1：`scripts/bin/collect_scan_outcome.py`

- 调度：cron `5 * * * *`（每小时第 5 分钟，Asia/Shanghai 无影响，纯 UTC 计算）
- 入参：`--days 7`（回看窗口，默认 7）、`--backfill-from 2026-09-17`（首次回填）、`--json`（只打印不写库）
- 逻辑：
  1. 选候选：`scan_signal` 中满足 §2.2 告警口径、且（无 outcome 行 或 `outcome_state <> 'resolved'`）的信号，
     限定 `alerted_at > NOW() - interval '<days> days'`；
  2. 单条 SQL（LATERAL 取价）一次性算出 1h/4h/12h/24h 的 `px0`/`px1`，**不拉 K 线明细**：

```sql
WITH cand AS (
    SELECT sg.id, sg.symbol, sg.p_dir, sg.alerted_at, sg.pool, sg.scenario,
           sg.timeframe, sg.stop_loss_pct
      FROM biz.scan_signal sg
      LEFT JOIN biz.scan_signal_outcome o ON o.signal_id = sg.id
     WHERE sg.alerted_at IS NOT NULL
       AND (sg.pool = 'main' OR (sg.pool = 'accumulation' AND sg.scenario = 'BRK'))
       AND sg.status <> 'invalid'
       AND sg.alerted_at > NOW() - make_interval(days => %(days)s)
       AND (o.signal_id IS NULL OR o.outcome_state <> 'resolved')
),
px AS (
    SELECT c.*,
           b.open_time AS base_time, b.close_px AS base_px,
           (SELECT k.close_px FROM biz.asset_klines k
             WHERE k.symbol=c.symbol AND k.interval='1h'
               AND k.open_time <= c.alerted_at + INTERVAL '1 hour'
             ORDER BY k.open_time DESC LIMIT 1)  AS px_1h,
           (SELECT k.close_px FROM biz.asset_klines k
             WHERE k.symbol=c.symbol AND k.interval='1h'
               AND k.open_time <= c.alerted_at + INTERVAL '4 hours'
             ORDER BY k.open_time DESC LIMIT 1)  AS px_4h,
           (SELECT k.close_px FROM biz.asset_klines k
             WHERE k.symbol=c.symbol AND k.interval='1h'
               AND k.open_time <= c.alerted_at + INTERVAL '12 hours'
             ORDER BY k.open_time DESC LIMIT 1)  AS px_12h,
           (SELECT k.close_px FROM biz.asset_klines k
             WHERE k.symbol=c.symbol AND k.interval='1h'
               AND k.open_time <= c.alerted_at + INTERVAL '24 hours'
             ORDER BY k.open_time DESC LIMIT 1)  AS px_24h
      FROM cand c
      LEFT JOIN LATERAL (
           SELECT k.open_time, k.close_px FROM biz.asset_klines k
            WHERE k.symbol=c.symbol AND k.interval='1h' AND k.open_time <= c.alerted_at
            ORDER BY k.open_time DESC LIMIT 1
      ) b ON TRUE
)
SELECT * FROM px;
```

  3. 同一批 SQL 取 `BTCUSDT` 的四个窗口价（`p_dir` 同方向对齐）；
  4. Python 侧算 `aligned_ret_*` / `btc_ret_*` / `excess_*`，`UPSERT` 进 `scan_signal_outcome`；
  5. `stop_loss_pct` 非空时，用 `mae_24h` 判定 `sl_hit_24h`（在 1h 收盘序列上取，`stop_loss_pct` 为空则本列留 NULL）；
  6. 打印汇总：`candidates=…, resolved=…, partial=…, no_data=…`。

### 4.5 脚本 2：`scripts/bin/build_scan_edge_report.py`

- 调度：cron `10 8 * * *`（Asia/Shanghai 08:10，早于 `daily_brief_email` 09:00）
- 入参：`--date YYYY-MM-DD`（默认昨日上海日）、`--days 7`、`--dry-run`、`--json`
- 逻辑：
  1. **样本闸门**：读当日 `scan_signal_outcome`，只取 `alerted_at` 落在该上海日、且 `last_window >= 1` 的行；
     同时统计 `pending_n`（未到期）。`matured_n < 10` → `sample_ready=FALSE`，报告头打「样本不成熟」并**跳过失配判定**（只展示不报警）。
  2. **多窗口指标**：对 1/4/12/24h 各算 胜率/赔率/PF/均收益/盈亏平衡胜率（公式见 §5）。
  3. **beta 对照**：同窗口取 `btc_ret_*` 的方向对齐胜率与均值，算出 `excess_avg_24h`。
  4. **行情环境**：从 `asset_klines`（BTCUSDT 1h）算当日 `btc_amp_pct`、`btc_1h_gt05_ratio`；
     从 `fear_greed_daily` / `global_metric_daily` 取 `fgi` / `cap_trend_pct`；
     按 §5.4 规则打 `regime_label`。
  5. **近 3 日滚动**：读 `scan_edge_daily` 前 3 行 + 当日，算 `roll3_*`。
  6. **分桶**：按 §4.3 的 8 个维度切桶，写 `scan_edge_bucket`，并挑出 `edge=TRUE` 的桶汇总为 `edge_buckets`。
  7. **失配判定**：跑 §5.5 的规则 A~E，写 `mismatch_flag` / `mismatch_rules` / `severity` / `conclusion`。
  8. `UPSERT` 进 `scan_edge_daily`，返回 brief dict（供脚本 3 渲染，也供 `--json` 调试）。

## 5. 计算公式

### 5.1 基础量（逐信号，窗口 w ∈ {1,4,12,24}h）

```
raw_w       = (px_w - px_0) / px_0 × 100            # 原始涨跌 %
aligned_w   = raw_w × (+1 if p_dir='up' else -1)     # 方向对齐
net_w       = aligned_w - COST,  COST = 0.1          # 扣双边费（与 backtest 同口径）
btc_net_w   = btc_raw_w × (same dir as p_dir) - COST # BTC 同方向同窗口
excess_w    = net_w - btc_net_w                      # 超额（alpha）
```

### 5.2 核心指标（按日/按桶聚合）

| 指标 | 公式 | 说明 |
|------|------|------|
| 胜率 `win_w` | `count(net_w > 0) / n` | 平盘（=0）计入负 |
| 平均盈利 `avg_win_w` | `mean(net_w \| net_w > 0)` | |
| 平均亏损 `avg_loss_w` | `mean(net_w \| net_w < 0)`（负值） | |
| **赔率 `odds_w`** | `avg_win_w / abs(avg_loss_w)` | **平均盈利 ÷ 平均亏损**；一侧为空记 NULL（**不得记 ∞**） |
| **盈亏平衡胜率 `be_w`** | `1 / (1 + odds_w)` | **胜率低于它 ⇒ 期望为负**（判定主指标） |
| **盈亏比 `pf_w`** | `sum(net_w \| >0) / abs(sum(net_w \| <0))` | 总盈利 ÷ 总亏损 |
| 均收益 `avg_w` | `mean(net_w)` | 期望值 |
| 期望判定 | `win_w < be_w` ⇔ `avg_w < 0` | 两者等价，报告中同时展示以互相校验 |

> **为何同时要赔率和 PF**：赔率是「单笔幅度比」，PF 是「总额比」，两者在样本量差异大时给出不同信号。
> 实测 09-22：T+1h 赔率 0.95（≈1:1）、PF 0.95 —— 说明**既不占幅度也不占频次**，是全面失效而非「少数大亏拖累」。
> 若只报 PF，会误判为「偶发大亏」。

### 5.3 样本量与置信

日样本 n=17~79，**单日胜率的标准误约 ±6~12 个百分点**，因此：

- 报告**同时给出**「当日值」与「近 3 日滚动值」；
- **失配判定只用滚动值**（`roll3_*`），当日值仅作展示与趋势参考；
- `roll3_win_1h < roll3_be_1h` 连续满足 → 才升级为 `severity='high'`。

### 5.4 行情环境分类 `regime_label`

| 标签 | 判据（当日 BTC） |
|------|------------------|
| `trend`（趋势） | `btc_amp_pct >= 4.0` **且** `btc_1h_gt05_ratio >= 0.35` |
| `range`（横盘低波动） | `btc_amp_pct < 3.0` **且** `btc_1h_gt05_ratio < 0.20` |
| `mixed` | 其余 |

> 依据：实测 09-18（振幅 6.49%、占比 44%）/ 09-21（7.21%、59%）胜率 56~64% ⇒ `trend`；
> 09-22（2.71%、16%）胜率 35%、09-23（1.01%、0%）⇒ `range`。
> **该维度是当前 `_build_regime` 缺失的「无趋势/低波动」判据**（现有只判 BTC 1h 方向、FGI、市值趋势，横盘时三者全不触发）。

### 5.5 失配判定规则

| ID | 规则 | 含义 |
|----|------|------|
| **A** | `roll3_alerts_avg > 前 7 日均值 × 1.5` 且 `roll3_win_1h < roll3_be_1h` | **阈值-行情失配**：告警量激增 + 期望转负（09-22 的典型形态） |
| **B** | `regime_label='range'` 且 `alerts_n >= 前 7 日均值` 且 `roll3_pf_1h < 1.0` | **横盘市信号天然失效**：应在横盘时抑制/收紧 |
| **C** | 存在桶满足 `n >= 5` 且 `win_1h < be_1h` 且 `share >= 0.2` | **边缘桶**：给出「该收紧哪个阈值」的具体坐标 |
| **D** | `timeframe='15m'` 桶连续 2 日 `win_1h < be_1h` | **周期退化**：建议横盘期抑制 15m 通道 |
| **E** | `btc_win_24h - win_24h < 0.10` 且 `excess_avg_24h < 0.5%` | **纯 beta 贡献**：中长窗口胜率不构成信号质量证据 |

`severity`：命中 A 或 B → `high`；仅命中 C/D/E → `watch`；均未命中 → `ok`。
`conclusion` 示例：`"阈值-行情失配：横盘低波动(range)下告警量升至 3 日均值 1.8 倍，3 日滚动胜率 38% 低于盈亏平衡线 52%，PF 0.94；边缘桶 vol_ratio<2.5(占 22%)、price_chg 3-5%(占 18%)"`。

## 8. 风险与注意

| 风险 | 说明 | 对策 |
|------|------|------|
| **样本量小** | 日 n=17~79，单日胜率标准误 ±6~12pt | 判定只用近 3 日滚动；`matured_n < 10` 时 `sample_ready=FALSE` 只展示不报警 |
| **选择偏置** | 样本限 `alerted_at IS NOT NULL`，而告警本身依赖 regime 顺风（`_scenario_priors` docstring 已自述「正期望是该口径的必然结果」） | 报告中显式标注「仅含已告警样本，非无偏基准」；beta 对照行强制并列 |
| **beta 混淆** | T+24h 胜率 61.5% 大部分来自 BTC 方向 | 强制输出 `btc_win_24h` / `excess_avg_24h`，规则 E 拦截「纯 beta」误判 |
| **`stop_loss_pct` 覆盖不全** | 该列 2026-09-21 08:40 UTC 才落库，之前样本恒 NULL | `sl_hit_24h` 留 NULL 并在报告标注「失效位样本 6/79」；不参与胜率口径 |
| **时区** | `report_date` 必须固定 Asia/Shanghai，而结算用 UTC | 表内只存 DATE（已按上海日切分）；SQL 用 `AT TIME ZONE 'Asia/Shanghai'` 切日 |
| **未到期行混入** | 会系统性高估胜率（未到期样本天然偏「还没跌」） | `last_window` 闸门 + `pending_n` 显式展示（同 `catalyst_outcome` 教训） |
| **跨区链路超时** | `asset_klines` 整表拉取 240s+ 不返回 | 取价一律 `LATERAL` 子查询在 SQL 侧算好（§4.4） |
| **「报警」变「噪声」** | 天天 `high` 会脱敏 | 规则 A/B 用滚动值 + 前 7 日均值倍数，且同一规则连续 3 日命中才升级 `high`（P2 再评估） |
| **阈值改动** | 本方案**不改任何阈值常量** | 只输出「哪个桶负期望、占多少」，阈值调整仍走人工决策（与轧空影子模式同原则） |
