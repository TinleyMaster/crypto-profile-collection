# 项目完整逻辑、数据库表关系与当前状态（2026-07-31）

***

## 一、项目概述

本项目是一套**加密货币投研资料采集与沉淀系统**，采用 **n8n 调度中枢 + Python 数据处理引擎 + Web 工作台** 的混合架构。

核心思路：把"从多数据源抓取币种/协议资料，找到官网/白皮书/文档，再将文档变成可沉淀资产"这件事，拆成**层层可维护的流水线**。

***

## 二、数据分层架构（5 层）

```
┌─────────────────────────────────────────────────────────┐
│  biz    业务消费层  doc_source_entry / doc_asset          │
│                    / research_url / coin_basic            │
│                    / github_repo_activity                 │
├─────────────────────────────────────────────────────────┤
│  core   统一实体层  asset / asset_source_map          │
├─────────────────────────────────────────────────────┤
│  src_*  来源解析层  src_cmc / src_cg / src_dl        │
├─────────────────────────────────────────────────────┤
│  raw    原始响应层  api_response                     │
├─────────────────────────────────────────────────────┤
│  sys    系统元数据  ingest_run / source_platform      │
└─────────────────────────────────────────────────────┘
```

**关键原则**：

- 每个数据源独立存事实，不跨源互相覆盖
- `core.asset_id` 是全局统一主键，外部 ID（cmc_id/coin_id/slug）降级为 source key
- 文档链路：入口发现 → 深度爬取 → 资产识别 → 下载 → 健康检查+AI筛选 → 知识库同步/生成投研资料

## 六、重复数据检查结果

### 6.1 源表层：无主键重复

| 表                        | 主键           | 重复数 |
| ------------------------ | ------------ | --- |
| `src_cmc.cmc_asset_map`  | cmc_id       | 0   |
| `src_cmc.cmc_asset_info` | cmc_id       | 0   |
| `src_cg.coin_list`       | coin_id      | 0   |
| `src_dl.protocol_list`   | protocol_id  | 0   |

### 6.2 core.asset：存在 symbol 重复（非 bug，是数据特性）

- **总资产数**：18,109
- **唯一 symbol**：16,204（约 1,905 个重复 symbol）
- **重复最多的 symbol**：PEPE x16, CAT x16, DOGE x11, X x10, TRUMP x8, BTC x8

**原因**：CG 的 `coin_list` 有大量同 symbol 不同链的 bridged token（如 WETH 有 63 个 coin_id 变体，USDC 60 个，USDT 49 个）。当批量 bootstrap 时，symbol 匹配逻辑将所有这些变体都映射到了同一个 `asset_id`。

**影响评估**：

- **正面**：自动完成了跨链代币聚合，WETH/USDC/USDT 等主流跨链资产无需手动合并
- **负面**：部分确实是不同资产但同 symbol 的代币（如不同的 PEPE meme 币）被错误合并
- **结论**：当前阶段可接受，后续需要引入 chain/platform 维度的匹配逻辑来区分

### 6.3 core.asset_source_map：无约束违例

- `(source_code, source_asset_key)` 唯一约束有效，**没有同一 source_key 映射到多个 asset_id 的情况**
- 同一 `asset_id` 在同一 `source_code` 下有多个 `source_asset_key` 是**预期行为**（bridged token 合并）

### 6.4 biz.doc_source_entry：无重复

- `ON CONFLICT (entity_type, COALESCE(asset_id, -1), COALESCE(protocol_id, -1), entry_url)` 去重有效
- 深度爬取发现的新链接通过同一约束去重

## 十一、关键约束与注意事项

1. **去重机制已就位**：所有 INSERT 均使用 `ON CONFLICT DO UPDATE`，Python 层有 `seen.set()` 辅助去重
2. **无孤儿数据**：source_map 和 doc_source_entry 的 asset_id 均有效指向 core.asset
3. **CG API 不可用**：所有 CG 的 doc_source_entry 均来自 CMC 交叉引用，非 CG 原生数据
4. **DL API 端点已迁移**：从 `api.defillama.io` 改为 `api.llama.fi`
5. **symbol 不是唯一标识**：同 symbol 可能是不同链的不同资产，后续需要 chain 维度区分
6. **content_hash 唯一约束**：`biz.doc_asset.content_hash` 有 UNIQUE，相同 PDF 不同 URL 会被正确去重
7. **B2 深度爬取噪声过滤**：通过 `DOC_URL_KEYWORDS` + `EXCLUDE_DOMAINS` + `EXCLUDE_PATH_PATTERNS` 三层过滤，避免无关链接入库
8. **数据库部署在 Zeabur**：所有脚本可在本地或云端运行，只要 `DATABASE_URL` 指向同一 PostgreSQL
9. **GitHub API 限流**：无 Token 60 次/小时（~2,000+ 仓库），设置 `GITHUB_TOKEN` 环境变量可升到 5,000 次/小时；脚本内置 rate-limit 自动等待
10. **GitHub API 墙**：与 CoinGecko 一样，`api.github.com` 在境内被 GFW 墙，需通过代理或从 Zeabur 云端运行
