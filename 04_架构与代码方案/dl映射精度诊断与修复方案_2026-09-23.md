## 1. 结论

`core.asset_source_map` 中 `source_code='dl'` 的 **4244** 条映射全部由 `bootstrap_dl` 建立。其匹配判据只有两条（Priority 1 `p.cmc_id` 精确命中 / Priority 2 `symbol` 相等，名称仅作并列时的 tie-break），而 `matched` 分支的留痕是**硬编码** `match_status='confirmed'`、`match_confidence=100`。

结果：**「一手 id 精确命中」与「symbol 撞车」在库里长得完全一样**。用一手判据（协议自带 `cmc_id` / `gecko_id`）分层后：

| 层 | 判据 | 数量 |
|---|---|---|
| **A** | 一手判据**矛盾**（证伪） | **505** |
| ├ A1 | 协议有 `cmc_id`，落点资产**有** cmc 映射但不含该 id | 261 |
| ├ A2 | 协议有 `gecko_id`，落点资产**有** cg 映射但不含该 key | **418**（全库 442） |
| └ — | 两者同时矛盾（去重） | 174 |
| **V** | 一手判据**证实**（可作重建基线） | **1065** |
| B | 仅 symbol 相等，无一手判据（既不能证实也不能证伪） | 1342 |
| C | 名称与 symbol 皆不等 | 2 |

- **Tier A 505 条**中 **393 条**的留痕是 `confirmed` / `confidence=100` —— 即「被盖章为已确认，但一手 id 与之矛盾」。
- 上表可复算：本层 A2 = 全库 442 − 24（这 24 条同时被 `cmc_id` 精确命中，按分层优先级归入 Tier V）；`505 = 261 + 418 − 174`。
- **Tier A 涉及 451 个落点资产、505 个协议**（有 54 个资产被 ≥2 个无关协议映射，形态与 P1-4 的「壳」同类）。
- 危害比 P1-4 更隐蔽：P1-4 的落点是**无 symbol 的壳**（一眼可辨），而这里的落点是**看起来合理的真实代币**。

**为何必须单独立项**：涉及 505 条映射及其下游 TVL / 事件 / AI 画像，且 Tier B 1342 条**缺乏判据**——顺手改会把「未知」当「已知」处理。

## 2. 缺陷机制

三处叠加，使错误映射不可辨识：

1. **判据弱**：[select_dl_assets_for_core_bootstrap.sql](file:///e:/瞎搞乱搞/web3/加密货币研究报告/05_代码与脚本/scripts/sql/src_dl/select_dl_assets_for_core_bootstrap.sql#L15-L39) 的 Priority 2 是 `UPPER(a.canonical_symbol) = UPPER(p.symbol)`。`symbol` 在全库**不唯一**，任何同符号代币都会被命中。
2. **留痕假**：[bootstrap_dl_assets_batch.py](file:///e:/瞎搞乱搞/web3/加密货币研究报告/05_代码与脚本/scripts/bin/bootstrap_dl_assets_batch.py) 的 `matched` 分支统一写 `match_status='confirmed'`、`match_method='bootstrap_dl'`、`match_confidence=100`、`verified_by='agent'` —— 该 `confidence` 表示「进入了 matched 分支」，**不表示已核验**。
3. **无一手判据优先**：协议自带的 `cmc_id` / `gecko_id` 是**权威标识**，却被降级为「与 symbol 并列匹配」的候选之一，未作为否决条件。

| `0.exchange`(ZERO) | 8293 | `Analysoor`(ZERO) | 28803 | 两个不同的 ZERO 项目，被 symbol 撞车 |
| `Agility LSD`(AGI) | 24364 | `Delysium`(AGI) | 24007 | 同上 |

## 3. 诊断口径

分层定义（`diag_dl_map_precision.py` 的 `BASE_CTE`，可复核）：

- **A1（`cmc_id` 矛盾）**：`p.cmc_id IS NOT NULL` **且** 落点资产**持有** cmc 映射（键集非空）**且** 该 id 不在键集中。
- **A2（`gecko_id` 矛盾）**：`p.gecko_id IS NOT NULL` **且** 落点资产**持有** cg 映射（键集非空）**且** 该 key 不在键集中。
- **V（证实）**：`p.cmc_id` 或 `p.gecko_id` **命中**落点资产的对应映射键集（`cmc_id` 优先）。
- **B**：仅 symbol 相等、名称不等，且 A/V 均未命中。
- **C**：名称与 symbol 皆不等。

分层优先级：`X`（协议已不在 `protocol_list`）→ `V`（`cmc_id` 命中）→ `A`（负向一手证据优先于名称/符号表象）→ `V`（`gecko_id` 命中）→ `B` → `C` → 对照（名称与 symbol 皆相等）。

**为何不用更弱的变体**：若把 A1/A2 放宽为「协议有 `cmc_id` 而资产**完全没有** cmc 映射」，命中数会放大到 **934 / 1248**，其中大量是「资产只是没被 CMC 收录」的假阳性，不构成矛盾。**故不作主张。**

**A1/A2 是否等于「一定错」**：不等于。理论上的合法例外是「协议自身的 CMC 条目 ≠ 其代币的 CMC 条目」。但抽查样本（上表四例）均为**同符号不同项目**，属真错配。故 A 层定位为「**需人工研判的可证伪清单**」，而非「自动删除清单」。

## 6. 修复方案

分三阶段，**每阶段独立可验、可停**。

### 阶段 0：只读诊断（已完成）

`diag_dl_map_precision.py`，零写入。

### 阶段 1：改判据重建匹配（代码）

在 `select_dl_assets_for_core_bootstrap.sql` 与 `bootstrap_dl_assets_batch.py` 中：

1. 把 `p.cmc_id` / `p.gecko_id` 从「候选之一」提升为**否决条件**——协议带一手 id 时，落点资产必须持有同一 id 才可判 `confirmed`。
2. `symbol` 相等降级为 `candidate`（不再是 `confirmed`）。
3. `match_confidence` 语义改为「已被一手来源核验」：一手命中 = 高，仅 symbol = 低。
4. 新增 `match_method` 取值区分 `bootstrap_dl_cmc` / `bootstrap_dl_gecko` / `bootstrap_dl_symbol`，使留痕**可回溯判据**。

### 阶段 2：存量重映射（数据，需人工研判）

1. **Tier V（1065）**：作为基线锚定，不动。
2. **Tier A（505）**：逐条研判后重指到协议自带的 `cmc_id` / `gecko_id` 对应资产；无对应资产则**删除该映射**（不保留错配）。
3. **Tier B（1342）**：**保守不动**——无判据即无依据，动它等于用猜测替换猜测。
4. **Tier C（2）**：逐条确认。

### 阶段 3：语义与展示修正

把存量 `match_status='confirmed'` 中**未被一手判据证实**的（即 Tier B/C 全量 + Tier A 的 393 条）降级为 `candidate`，避免下游把「进了 matched 分支」误读为「已核验」。

### 明确不做

- 不用名称相似度、不用 symbol 猜测回填（违反项目铁律「不做名称猜测」，且 P1-4 已证其危害）。
- 不批量删除 Tier B。
- 不在本阶段改动 `core.asset` 本体或 TVL 序列。

复核 SQL：

```sql
-- Tier A1 的落点资产应持有「另一个」cmc id
SELECT COUNT(*) FROM core.asset_source_map asm
JOIN src_dl.protocol_list p ON p.protocol_id = asm.source_asset_key
WHERE asm.source_code='dl' AND p.cmc_id IS NOT NULL
  AND EXISTS (SELECT 1 FROM core.asset_source_map c
              WHERE c.source_code='cmc' AND c.asset_id=asm.asset_id)
  AND NOT EXISTS (SELECT 1 FROM core.asset_source_map c
                  WHERE c.source_code='cmc' AND c.asset_id=asm.asset_id
                    AND c.source_asset_key = p.cmc_id);
-- 期望 261

-- 留痕分布：505 条 Tier A 中 393 条被盖章 confirmed
SELECT match_status, COUNT(*) FROM core.asset_source_map WHERE source_code='dl'
GROUP BY 1;
-- 期望 confirmed=2476 / candidate=1768
```

## 8. 生效条件与风险

- 本方案当前**不产生任何数据变更**；阶段 1 的 SQL 改动需 **redeploy** 才生效，阶段 2 是对数据库的直接写入。
- 阶段 2 的每次写入需**先备份**（沿用 `fix_*` 脚本约定：默认 dry-run、`--apply` 执行、自动备份表）。
- **顺序要求**：阶段 1（写入侧）必须先于阶段 2（存量），否则清理完会被重新写入——与 P1-4 的处置顺序一致。
- 主要风险：Tier B 1342 条「未知」在阶段 3 被降级为 `candidate` 后，若下游有逻辑依赖 `confirmed` 计数会出现跳变，需同步检查消费方。
