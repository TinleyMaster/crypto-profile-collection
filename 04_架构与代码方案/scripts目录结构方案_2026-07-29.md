# `scripts/` 目录结构方案（2026-07-29）

## 1. 目标

这份方案不是为了把整个系统一下子“代码化”，而是为了给后续抽离 `n8n Code` 节点提供一个稳定骨架。

目标只有 3 个：

1. 让复杂逻辑有固定归属
2. 让 `n8n` 调用代码时有统一入口
3. 让以后加新来源、新解析器、新映射规则时不会乱长

---

## 2. 总体原则

推荐采用：

## `脚本入口 + 可复用模块 + SQL 文件分离`

也就是不要把所有逻辑都写在一个 `scripts/foo.py` 里，而是分成：

- `bin/`：给 n8n 调用的入口脚本
- `src/`：真正的业务逻辑
- `sql/`：SQL 模板
- `tests/`：后续测试
- `tmp/`：临时输出

## 4. 每一层的职责

## `bin/`

这里放“入口脚本”。

特点：

- 被 `n8n Execute Command` 直接调用
- 参数简单
- 不写复杂业务逻辑

比如：

- `ingest_cmc_map.py`
- `refresh_core_mapping.py`

这些脚本只做：

1. 读参数
2. 初始化配置
3. 调用 `src/` 里的模块
4. 输出结果 / 错误码

一句话：

**`bin/` 是门面，不是内核。**

---

## `src/crypto_research/clients/`

这里放外部 API 客户端。

比如：

- `cmc_client.py`
- `coingecko_client.py`
- `defillama_client.py`

职责：

- 统一 base URL
- headers / key 管理
- timeout / retry
- request 参数拼装

不要在这里做解析，只负责“把数据拿回来”。

---

## `src/crypto_research/parsers/`

这里放来源解析器。

比如：

- `cmc_map.py`
- `cmc_info.py`
- `cg_coin_detail.py`
- `llama_protocols.py`

职责：

- 把 API 响应转换成标准 Python dict / list
- 对应数据库 `src_*` 表字段
- 做空值兼容和字段裁剪

这里就是现在很多 `Code` 节点未来最该搬家的地方。

---

## `src/crypto_research/mapping/`

这里是最核心的一层。

建议放：

- 域名标准化
- 合约地址标准化
- 资产匹配
- 协议匹配
- 候选评分

这是后面真正会越来越“像引擎”的地方。

如果只选一层重点维护，优先维护这一层。

---

## `src/crypto_research/refresh/`

这里放“消费层刷新器”。

比如：

- `coin_basic.py`
- `doc_source_entries.py`
- `asset_market_daily.py`

职责：

- 从 `src_*` / `core.*` 聚合成 `biz.*`
- 统一封装刷新逻辑

这里本质上是“业务投影层”。

---

## `src/crypto_research/docs/`

这里放文档相关逻辑。

比如：

- 入口链接发现
- 文档类型识别
- URL 规范化
- 元数据提取
- 内容哈希

这层建议尽早独立出来，因为文档流最容易越做越复杂。

---

## `src/crypto_research/db/`

这里放数据库交互封装。

比如：

- 连接管理
- ingest run 写入
- raw response 写入
- upsert 包装

目的不是 ORM 化，而是避免：

- 每个脚本都自己写一遍连接代码
- SQL 文件路径到处散落

---

## `sql/`

这里非常重要。

建议把 SQL 文件单独存，不要长 SQL 全塞 Python 字符串里。

原因：

1. diff 更清楚
2. SQL 可以单独调试
3. Python 负责参数和流程，SQL 负责数据操作

尤其对你这种 PostgreSQL 驱动很强的系统，这样后面维护会轻松很多。

## 5. n8n 应该怎么调用这些脚本

最推荐两种方式。

## 方式 A：`Execute Command`

适合早期。

例如：

```bash
python "E:\瞎搞乱搞\web3\加密货币研究报告\scripts\bin\ingest_cmc_map.py" --mode run
```

优点：

- 简单
- 不需要额外服务
- 适合先把复杂 `Code` 节点抽出去

缺点：

- 并发控制一般
- 运行日志要自己整理

## 方式 B：本地轻量 HTTP 服务

适合中期。

例如：

- 用 `FastAPI`
- n8n 通过 HTTP 调用本地服务

优点：

- 更适合复用
- 更方便统一日志、错误码、调试

缺点：

- 需要维护一个服务进程

### 建议

- **阶段1 用 `Execute Command`**
- **阶段2 再考虑 HTTP 服务**

## 6. 第一批最值得真的建出来的脚本

不要一上来建满整棵树。  
第一批最值得落地的只有下面这些。

### 第一组：来源采集入口

- `bin/ingest_cmc_map.py`
- `bin/ingest_cmc_info.py`
- `bin/ingest_llama_protocols.py`

### 第二组：解析器

- `parsers/cmc_map.py`
- `parsers/cmc_info.py`
- `parsers/llama_protocols.py`

### 第三组：映射核心

- `mapping/normalize_domain.py`
- `mapping/normalize_contract.py`
- `mapping/asset_matcher.py`
- `mapping/candidate_builder.py`

### 第四组：刷新器

- `refresh/coin_basic.py`
- `refresh/doc_source_entries.py`

## 7. 文件命名建议

建议统一用：

- 动词 + 对象
- 不要夹杂太多业务缩写

推荐风格：

- `ingest_cmc_map.py`
- `parse_cmc_info.py`
- `refresh_coin_basic.py`
- `normalize_domain.py`
- `build_mapping_candidate.py`

不推荐：

- `run1.py`
- `new_code.py`
- `cmc_final_v2.py`

---

## 8. 参数风格建议

入口脚本参数尽量统一。

例如：

```text
--run-id
--limit
--offset
--asset-id
--cmc-id
--mode
--dry-run
```

这样 n8n 里调用时也更规律。

例如：

```bash
python scripts/bin/ingest_cmc_info.py --limit 100 --offset 0
```

## 9. 先不要做成什么样

你现在最不需要的是：

### 不要一开始就微服务化

没必要先拆成：

- parser service
- mapping service
- doc service

这会让系统复杂度先爆炸。

### 不要一开始就搞 ORM

你的系统是 SQL 主导型的，先用：

- `psycopg`
- SQL 文件

就够了。

### 不要一开始就搞太深的抽象

先让目录结构稳定，比先做“完美架构”更重要。

## 10. 最适合你的落地顺序

### 第一步

先建一个最小 `scripts/` 骨架：

- `bin/`
- `src/crypto_research/clients/`
- `src/crypto_research/parsers/`
- `src/crypto_research/mapping/`
- `src/crypto_research/refresh/`

先落第一个真实脚本：

- `bin/ingest_cmc_map.py`

对应抽离：

- `CODE_BUILD_RAW_RESPONSE`
- `CODE_PARSE_CMC_MAP`

### 第三步

再落：

- `bin/ingest_cmc_info.py`
- `parsers/cmc_info.py`

### 第四步

等 `WF_CORE_MAPPING_REFRESH` 开始做时，再重点建设：

- `mapping/asset_matcher.py`
- `mapping/candidate_builder.py`

## 11. 这份目录方案和你当前系统最匹配的地方

它本质上对应了我们前面定下来的新分层：

- `clients/` 对应外部 API
- `parsers/` 对应 `src_*`
- `mapping/` 对应 `core.*`
- `refresh/` 对应 `biz.*`
- `sql/` 对应数据库执行层
- `bin/` 对应 n8n 的调用入口

所以它不是为了“代码看起来专业”，而是为了和你的数据库、工作流、后续维护节奏对齐。
