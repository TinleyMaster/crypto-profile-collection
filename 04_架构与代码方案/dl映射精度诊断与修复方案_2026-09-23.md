## 1. 结论

`core.asset_source_map` 中 `source_code='dl'` 的 **4244** 条映射全部由 `bootstrap_dl` 建立。其匹配判据只有两条（Priority 1 `p.cmc_id` 精确命中 / Priority 2 `symbol` 相等，名称仅作并列时的 tie-break），而 `matched` 分支的留痕是**硬编码** `match_status='confirmed'`、`match_confidence=100`。

结果：**「一手 id 精确命中」与「symbol 撞车」在库里长得完全一样**。用一手判据（协议自带 `cmc_id` / `gecko_id`）分层后：

| 层 | 判据 | 数量 |
|---|---|---|
| **A** | 一手判据**矛盾**（证伪） | **505** |
| ├ A1 | 协议有 `cmc_id`，落点资产**有** cmc 映射但不含该 id | 261 |
| ├ A2 | 协议有 `gecko_id`，落点资产**有** cg 映射但不含该 key | **418**（全库 442） |
| └ — | 两者同时矛盾（去重） | 174 |
| **V** | 一手判据**证实**（可作重建基线） | **1065** |
| B | 仅 symbol 相等，无一手判据（既不能证实也不能证伪） | 1342 |
| C | 名称与 symbol 皆不等 | 2 |

- **Tier A 505 条**中 **393 条**的留痕是 `confirmed` / `confidence=100` —— 即「被盖章为已确认，但一手 id 与之矛盾」。
- 上表可复算：本层 A2 = 全库 442 − 24（这 24 条同时被 `cmc_id` 精确命中，按分层优先级归入 Tier V）；`505 = 261 + 418 − 174`。
- **Tier A 涉及 451 个落点资产、505 个协议**（有 54 个资产被 ≥2 个无关协议映射，形态与 P1-4 的「壳」同类）。
- 危害比 P1-4 更隐蔽：P1-4 的落点是**无 symbol 的壳**（一眼可辨），而这里的落点是**看起来合理的真实代币**。

**为何必须单独立项**：涉及 505 条映射及其下游 TVL / 事件 / AI 画像，且 Tier B 1342 条**缺乏判据**——顺手改会把「未知」当「已知」处理。

## 2. 缺陷机制

三处叠加，使错误映射不可辨识：

1. **判据弱**：修复前 [select_dl_assets_for_core_bootstrap.sql](file:///e:/瞎搞乱搞/web3/加密货币研究报告/05_代码与脚本/scripts/sql/src_dl/select_dl_assets_for_core_bootstrap.sql#L50-L53) 只有 `cmc_id` 精确命中与 `UPPER(a.canonical_symbol) = UPPER(p.symbol)` 两条，且 `symbol` 在全库**不唯一**，任何同符号代币都会被命中。（修复后该文件已重写为「cmc → gecko → symbol」三级 + 硬否决，见 §6.1。）
2. **留痕假**：[bootstrap_dl_assets_batch.py](file:///e:/瞎搞乱搞/web3/加密货币研究报告/05_代码与脚本/scripts/bin/bootstrap_dl_assets_batch.py) 的 `matched` 分支统一写 `match_status='confirmed'`、`match_method='bootstrap_dl'`、`match_confidence=100`、`verified_by='agent'` —— 该 `confidence` 表示「进入了 matched 分支」，**不表示已核验**。
3. **无一手判据优先**：协议自带的 `cmc_id` / `gecko_id` 是**权威标识**，却被降级为「与 symbol 并列匹配」的候选之一，未作为否决条件。

## 3. 诊断口径

分层定义（`diag_dl_map_precision.py` 的 `BASE_CTE`，可复核）：

- **A1（`cmc_id` 矛盾）**：`p.cmc_id IS NOT NULL` **且** 落点资产**持有** cmc 映射（键集非空）**且** 该 id 不在键集中。
- **A2（`gecko_id` 矛盾）**：`p.gecko_id IS NOT NULL` **且** 落点资产**持有** cg 映射（键集非空）**且** 该 key 不在键集中。
- **V（证实）**：`p.cmc_id` 或 `p.gecko_id` **命中**落点资产的对应映射键集（`cmc_id` 优先）。
- **B**：仅 symbol 相等、名称不等，且 A/V 均未命中。
- **C**：名称与 symbol 皆不等。

分层优先级：`X`（协议已不在 `protocol_list`）→ `V`（`cmc_id` 命中）→ `A`（负向一手证据优先于名称/符号表象）→ `V`（`gecko_id` 命中）→ `B` → `C` → 对照（名称与 symbol 皆相等）。

**为何不用更弱的变体**：若把 A1/A2 放宽为「协议有 `cmc_id` 而资产**完全没有** cmc 映射」，命中数会放大到 **934 / 1248**，其中大量是「资产只是没被 CMC 收录」的假阳性，不构成矛盾。**故不作主张。**

**A1/A2 是否等于「一定错」**：不等于。理论上的合法例外是「协议自身的 CMC 条目 ≠ 其代币的 CMC 条目」。但抽查样本（上表四例）均为**同符号不同项目**，属真错配。故 A 层定位为「**需人工研判的可证伪清单**」，而非「自动删除清单」。

### 6.1 阶段 1：写入侧判据重建（代码，已改）

[select_dl_assets_for_core_bootstrap.sql](file:///e:/瞎搞乱搞/web3/加密货币研究报告/05_代码与脚本/scripts/sql/src_dl/select_dl_assets_for_core_bootstrap.sql)：

- 一手判据升级为**独立的候选来源**：Priority 1 `cmc_id` 精确命中 → Priority 2 `gecko_id` 精确命中（**新增**，原实现只有 cmc）→ Priority 3 `symbol` 相等。
- 输出 `match_kind`（`cmc` / `gecko` / `symbol` / NULL），供写入侧决定留痕。
- **硬否决**：仅靠 symbol 命中、协议带一手 id、而落点资产**持有同源映射却不含该 id** → 该协议不进入候选池（既不映射、也不新建资产）。判据用 `EXISTS` 表达而非数组聚合，避免 `GROUP BY` 展开全部列。
- 「未证伪」边界：落点资产**没有**该来源映射时**不**否决，只在写入侧降级为 `candidate` —— 否则会把「资产只是没被 CMC 收录」误杀，即 §3 已否定的 934/1248 弱变体。

[bootstrap_dl_assets_batch.py](file:///e:/瞎搞乱搞/web3/加密货币研究报告/05_代码与脚本/scripts/bin/bootstrap_dl_assets_batch.py)：

| 判据 | `match_status` | `match_method` | `match_confidence` |
|---|---|---|---|
| `cmc_id` 精确命中 | `confirmed` | `bootstrap_dl_cmc` | 95 |
| `gecko_id` 精确命中 | `confirmed` | `bootstrap_dl_gecko` | 90 |
| 仅 `symbol` 相等 | `candidate` | `bootstrap_dl_symbol` | 40 |
| 无既有资产可复用（新建） | `candidate` | `bootstrap_dl_new` | 80 |

- `bootstrap_dl_new` 是计划三个取值的必要补充：新建资产的映射由协议自身创建，**不含**任何匹配判断，不能复用 `bootstrap_dl_symbol`。
- 输出 `by_kind` 分桶，使「一手命中占比」可见（避免只看到总数）。
- 顺带修好 `--dry-run` 仍会落库的缺陷：原 dry-run 分支位于「新建资产 INSERT」之后，而 `get_connection` 成功退出即 commit。

**为何必须是硬否决（实测依据）**：[run_dl_pipeline.py:94-108](file:///e:/瞎搞乱搞/web3/加密货币研究报告/05_代码与脚本/scripts/bin/run_dl_pipeline.py#L94-L108) 每日 04:00 重跑本脚本，候选池条件是 `asm.asset_id IS NULL`。删除映射后协议会重新入池，实测 **430/430** 会被 symbol 重新命中并写回。否决后复验：在刻意去掉「未映射」过滤的镜像查询中，否决数恒为 **453**，候选池规模删除前后均为 **10** —— 被删协议稳定不再回流。

## 8. 生效条件与风险

### 8.1 生效条件

- **必须 redeploy**：阶段 2 的删除（430 条）与阶段 3 的降级只能靠阶段 1 的新 SQL 保住。生产容器若仍跑旧 SQL，次日 04:00 的 `run_dl_pipeline.py` 会以 `symbol` 把这 430 条重新写回（且留痕是旧口径的 `confirmed` / `confidence=100`）。未 redeploy 前观察到回流属**预期现象**，redeploy 后重跑 `fix_dl_map_precision.py --apply` 即可复原（脚本幂等）。
- 阶段 2 / 3 的写入均为**数据库直接写入**，与容器部署无关，已生效。
- 顺序不可颠倒：阶段 1（写入侧）先于阶段 2（存量），否则清理完会被重新写入——与 P1-4 的处置顺序一致，本次已按此顺序执行。
