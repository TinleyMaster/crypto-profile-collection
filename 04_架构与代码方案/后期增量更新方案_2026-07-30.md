# 后期增量更新方案（2026-07-30）

## 1. 这份方案解决什么问题

当前这套代码已经能跑通：

- `CMC_MAP -> src_cmc.cmc_asset_map`
- `CMC_INFO -> src_cmc.cmc_asset_info`
- `src_cmc -> core.asset`
- `src_cmc -> biz.doc_source_entry`
- `doc_source_entry -> biz.doc_asset`

但目前的增量能力，主要还是：

- 补缺型增量
- 小批次回填
- `upsert` 覆盖更新

它适合当前重构初期快速起量，但后期如果要长期稳定运行，还需要补成“变化驱动增量”。

---

## 2. 当前已经具备的增量能力

### 2.1 `CMC_MAP`

当前方式：

- 每次抓一轮 `/map`
- 通过 `upsert` 更新 `src_cmc.cmc_asset_map`

特点：

- 本质上是“全量抓取 + 增量覆盖”
- 适合做上游主清单基线

### 2.2 `CMC_INFO`

当前方式：

- 通过 `--from-map-missing`
- 只抓 `map` 里有、`info` 里还没有的 `cmc_id`

特点：

- 这是“补缺型增量”
- 还不是“老数据刷新型增量”

### 2.3 `core.asset`

当前方式：

- 默认只处理未映射资产
- 通过 `--include-mapped` 才会刷新已有映射

特点：

- 适合 bootstrap
- 不适合长期自动刷新老资产画像

### 2.4 `doc_source_entry`

当前方式：

- 只处理还没有 `doc_source_entry` 的资产

特点：

- 能补新资产入口
- 不能自动处理“老资产 URL 发生变化”

### 2.5 `doc_asset`

当前方式：

- 只处理还没转成 `doc_asset` 的入口
- 当前优先发现明显是 PDF / whitepaper 的 URL

特点：

- 能持续补新文档
- 不能系统处理“旧文档链接失效 / 跳转变化 / 内容更新”

---

## 3. 后期应该升级成什么样

建议把后期增量拆成两条通道：

### A. 新增通道

负责处理：

- 新币
- 新资产映射
- 新文档入口
- 新文档文件

这条通道基本可以沿用当前脚本。

### B. 刷新通道

负责处理：

- 老币资料更新
- 官网 / docs / Github 链接变化
- 白皮书地址变化
- 文档重新探测

这条通道是后期必须补上的主能力。

---

## 4. 推荐的后期增量主链路

```text
定时全量抓 CMC_MAP
  -> 更新 src_cmc.cmc_asset_map
  -> 识别新增 / 变化的 cmc_id
  -> 写入增量刷新队列

增量刷新队列
  -> 驱动 CMC_INFO 刷新
  -> 驱动 core.asset 刷新
  -> 驱动 doc_source_entry 重建
  -> 驱动 doc_asset 重探测
```

也就是：

```text
全量 map 负责发现变化
队列表负责传递变化
下游脚本只消费“脏资产”
```

这是后期最稳的模式。

---

## 5. 为什么要引入“刷新队列”

如果后面还是沿用现在这种：

- 每层都自己扫 missing
- 或者全表轮询

问题会越来越明显：

- 数据量大了以后扫描成本高
- 每层都自己判断，逻辑会分散
- 某个资产一旦上游变化，下游不容易统一联动

所以建议增加一个统一的脏数据队列，例如：

- `sys.entity_refresh_queue`

它的作用是：

- 记录哪个来源对象变了
- 记录应该刷新到哪一层
- 记录状态、重试次数、最后错误

---

## 6. 推荐新增的队列表

建议增加一张表：

### `sys.entity_refresh_queue`

建议字段：

- `queue_id`
- `source_code`，例如 `cmc`
- `entity_type`，例如 `asset`
- `source_entity_key`，例如 `cmc_id`
- `asset_id`
- `refresh_stage`
  - `cmc_info`
  - `core_asset`
  - `doc_source_entry`
  - `doc_asset`
- `refresh_reason`
  - `new_map_entity`
  - `map_changed`
  - `info_stale`
  - `doc_url_changed`
  - `doc_asset_stale`
- `priority`
- `status`
  - `pending`
  - `processing`
  - `done`
  - `failed`
- `attempt_count`
- `last_error`
- `scheduled_at`
- `started_at`
- `finished_at`
- `created_at`
- `updated_at`

核心思想：

- 不是每层都自己扫全表
- 而是由上游把“需要刷新谁”明确写下来

## 7. 每一层后期怎么做增量

### 7.1 `CMC_MAP`

建议策略：

- 每天固定全量抓一次
- 继续保留 `raw.api_response`
- 对比 `src_cmc.cmc_asset_map` 的关键字段是否变化

变化判定建议至少包括：

- `name`
- `symbol`
- `slug`
- `listing_status`
- `is_active`
- `platform_name`
- `token_address`

如果是新资产或关键字段变化：

- 写入 `sys.entity_refresh_queue`
- 下游阶段至少投递：
  - `cmc_info`
  - `core_asset`
  - `doc_source_entry`

### 7.2 `CMC_INFO`

后期应该拆成两种模式：

1. `missing` 模式
   - 沿用现在的补缺逻辑
2. `stale` 模式
   - 刷新最近一段时间未更新的 `cmc_id`
   - 或直接消费 `refresh_queue`

推荐新增脚本能力：

- `ingest_cmc_info.py --from-refresh-queue`
- `ingest_cmc_info.py --from-stale --stale-hours 168`

### 7.3 `core.asset`

后期不建议只靠 `--include-mapped` 全表刷新。

建议改成：

- 只刷新 refresh queue 中命中的资产
- 或刷新最近 `updated_at` 变化的 CMC 资产

推荐新增脚本：

- `refresh_core_assets_from_refresh_queue.py`

### 7.4 `doc_source_entry`

这里后期要支持“重建某个资产的入口集合”。

因为老资产的：

- 官网可能会换
- docs 链接可能会换
- Github 仓库可能会迁移

所以建议：

- 不只做 missing
- 要支持按 `asset_id` 全量重算该资产入口，再 `upsert`

推荐新增脚本：

- `refresh_doc_source_entries_for_assets.py`

### 7.5 `doc_asset`

这里后期建议分两种：

1. 新入口发现
   - 沿用当前逻辑
2. 老文档重探测
   - 根据 `last_seen_at` 做周期重扫
   - 处理 404 / 跳转 / MIME 变化 / 链接替换

推荐新增脚本：

- `refresh_doc_assets_from_stale_entries.py`

建议规则：

- `last_seen_at > 30天` 的文档重探测
- 曾经失败过但近期没再试的入口重试

## 8. 推荐增加的状态字段

为了让增量更新真正可控，建议后期补下面几类状态字段。

### A. `src_cmc.cmc_asset_info`

建议补：

- `last_success_fetched_at`
- `last_attempt_fetched_at`
- `fetch_status`
- `payload_hash`

### B. `biz.doc_source_entry`

建议补：

- `last_discovered_at`
- `last_checked_at`
- `check_status`

### C. `biz.doc_asset`

当前已有：

- `last_seen_at`

后期建议再补：

- `last_probe_at`
- `probe_status`
- `http_status_code`
- `content_hash`（后期若要比对文档是否变化）

## 9. 推荐的调度频率

### 每天固定任务

1. `CMC_MAP` 全量抓一次
2. 生成刷新队列
3. 消费 `cmc_info`
4. 消费 `core_asset`
5. 消费 `doc_source_entry`
6. 消费 `doc_asset`

### 高频补缺任务

可以每 1 到 3 小时跑一次：

- `backfill_cmc_info.py`
- `backfill_doc_source_entries_from_cmc.py`
- `backfill_doc_assets_from_entries.py`

### 低频重扫任务

可以每天夜里跑：

- `stale cmc_info`
- `stale doc_asset`

## 10. 推荐的脚本演进清单

### 第一阶段：沿用现有脚本先跑稳

- `ingest_cmc_map.py`
- `backfill_cmc_info.py`
- `backfill_core_assets_from_cmc.py`
- `backfill_doc_source_entries_from_cmc.py`
- `backfill_doc_assets_from_entries.py`

### 第二阶段：补刷新能力

建议新增：

- `bin/build_refresh_queue_from_cmc_map.py`
- `bin/ingest_cmc_info_from_queue.py`
- `bin/refresh_core_assets_from_queue.py`
- `bin/refresh_doc_source_entries_from_queue.py`
- `bin/refresh_doc_assets_from_stale_entries.py`

### 第三阶段：补跨源联动

等 CoinGecko / DefiLlama 接进来后：

- 各来源都写自己的 refresh queue
- 最终统一消费到 `core.asset`

---

## 11. 最推荐的落地顺序

如果按投入产出比来排，我建议顺序是：

1. 保持 `CMC_MAP` 全量抓取不变
2. 新增 `sys.entity_refresh_queue`
3. 先把 `CMC_INFO` 改成支持 `queue + stale`
4. 再把 `core.asset` 改成按队列刷新
5. 再把 `doc_source_entry` 改成按资产重建
6. 最后给 `doc_asset` 增加定期重探测

这个顺序比较稳，因为：

- 上游变化先能被识别
- 中游实体先能稳定刷新
- 下游文档链路再逐步变聪明

---

## 12. 一句话结论

当前代码已经适合：

- 初始化建库
- 持续补新增

后期如果要长期运营，建议升级成：

- `全量 map 抓取`
- `变化识别`
- `refresh queue`
- `下游按脏资产刷新`

这样后面接入：

- CoinGecko
- DefiLlama
- 文档解析
- 知识库同步

都会顺很多。
